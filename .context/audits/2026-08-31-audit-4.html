Y porque el eje que siempre brilló —Arquitectura— es justo donde viven las dos.

04 BLOCKER 1 — Pro gratis, para cualquiera, con una petición

El trigger que protege la suscripción es BEFORE UPDATE. El camino de INSERT lleva abierto desde julio.

BlockerA4-B1 · Arquitectura / Seguridad · bypass de pago

El code review de la PR #100 (FRESCO-228) encontró que profiles_update_own no restringe columnas y que grant update … to authenticated es de tabla entera, así que cualquier usuario autenticado podía hacer .from('user_profiles').update({ plan: 'pro' }) sobre su propia fila. El arreglo fue un trigger BEFORE UPDATE que rechaza cambios a las 5 columnas de suscripción salvo si el rol JWT es service_role. El comentario de la migración lo dice con todas las letras:

-- any authenticated user could already call the Supabase client SDK
-- directly (`.from('user_profiles').update({ plan: 'pro' })…`) and
-- self-grant Pro — this predates this PR
…
create trigger protect_subscription_columns
  before update on public.user_profiles

supabase/migrations/20260818190000_prevent_client_subscription_column_writes.sql

El problema: el trigger cubre UPDATE, no INSERT. Y el camino de INSERT está abierto de par en par:

  • authenticated tiene INSERT de tabla sobre user_profiles (20260729120000_grant_authenticated_table_privileges.sql).
  • La política profiles_insert_own es with check ((select auth.uid()) = id) — acota la fila, no las columnas.
  • No hay ningún trigger on auth.users que cree la fila de perfil por defecto (verificado: pg_trigger sobre auth.* está vacío). La fila no existe hasta que el usuario termina el onboarding — que la escribe con client.from('user_profiles').upsert(...) desde el navegador (lib/api/user-profile.ts:91, app/onboarding/page.tsx).
  • El cron de reconciliación de Stripe solo mira filas con stripe_subscription_id IS NOT NULL (app/api/cron/stripe-reconcile/route.ts:67), así que nunca ve una fila con plan:'pro' puesta a mano.
  • generate-meal-plan y toda la UI de Pro se gatean solo con profile.plan === 'pro', nunca con plan_expires_at (A4-L8).

Exploit, sin tocar la app:

# 1. La anon key está en el bundle del cliente. Registra un anónimo:
curl -s "$SUPABASE_URL/auth/v1/signup" -H "apikey: $ANON" \
  -H 'content-type: application/json' -d '{}'   # o POST /auth/v1/token?grant_type=anonymous

# 2. Con el JWT devuelto, INSERTA tu propio perfil como Pro:
curl -s "$SUPABASE_URL/rest/v1/user_profiles" \
  -H "apikey: $ANON" -H "authorization: Bearer $JWT" \
  -H 'content-type: application/json' -H 'prefer: return=representation' \
  -d '{"id":"","plan":"pro","plan_expires_at":"2099-01-01T00:00:00Z",
       "num_personas":2,"adultos":2,"ninos":0,
       "dias_planificar":["lunes"],"comidas_planificar":["comida"]}'
# → fila creada. Sin UPDATE, el trigger no dispara. plan='pro' persiste.
# Pro para siempre, gratis, para cualquiera — incluido un invitado sin email.

Impacto: el ingreso del producto no existe. Tres auditorías externas y un code review de PR —que vio el hueco de UPDATE y solo tapó UPDATE— no lo cogieron.

Arreglo: añade una rama BEFORE INSERT a prevent_client_subscription_writes() (forzar plan='free', NULL en las columnas stripe / plan_expires_at / payment_failed_at salvo service_role) y re-apunta el trigger a BEFORE INSERT OR UPDATE. O REVOKE INSERT ON user_profiles FROM authenticated y crea la fila con una RPC SECURITY DEFINER con lista blanca de columnas. Además: el cron de reconciliación debería barrer plan IN ('pro','family') AND stripe_subscription_id IS NULL para limpiar lo que ya se haya colado.

AltoA4-H3 · el mismo hueco de INSERT permite denegar Pro a un cliente que paga

stripe_customer_id y stripe_subscription_id son UNIQUE. Un atacante que consiga un cus_… real lo pre-ocupa en su propia fila en el INSERT. Cuando ese cliente completa el checkout, el .update({ stripe_customer_id }) del webhook (app/api/stripe/webhook/route.ts:125) choca con la constraint única → loguea error, devuelve 200 → el cliente que ha pagado nunca recibe Pro. Confianza menor (los ids de Stripe no son enumerables) pero el daño —cliente pagando sin servicio— es real. Lo tapa el mismo arreglo de A4-B1.

05 BLOCKER 2 — La seguridad alimentaria es un único punto de fallo sin un test

Desde que se fue Gemini, get_filtered_recipes es lo único que separa a una celíaca de un plato con gluten. Nadie comprueba que funcione.

BlockerA4-B2 · Arquitectura / Verificación · seguridad alimentaria

Tres defectos que se componen:

1 · El campo de texto libre de alérgenos no lo lee nadie

El onboarding ofrece "¿Algún otro alérgeno?" → alergenos_texto_libre (app/onboarding/page.tsx:547). Se persiste. Y no lo lee get_filtered_recipes ni ningún punto de la generación o la lista de la compra — solo se filtra por v_profile.alergenos, la lista estructurada de 6 ítems. La lista estructurada (lib/constants/dietary-options.ts:15) omite cacahuete, leche como alérgeno, soja, sésamo, crustáceos, moluscos, mostaza, altramuz — 8 de los 14 alérgenos de declaración obligatoria en la UE. Cualquier usuario con uno de esos es empujado justo al campo que se ignora.

Usuaria escribe "cacahuete" en "¿Algún otro alérgeno?" → termina onboarding →
menú generado con una receta de cacahuete → renderizada en /menu sin advertencia.

2 · El match es exacto y sensible a mayúsculas, sin backstop

ADR-0005 quitó la "Layer 2" de Gemini que repetía la exclusión. Ahora coalesce(r.alergenos,'[]') ?| v_profile.alergenos (20260804010000_…:35) es el único enforcement — comparación de strings exacta entre el vocabulario curado del onboarding y el campo recipes.alergenos generado por IA en la migración del catálogo. Ningún test verifica que los valores de recipes.alergenos se ajusten al conjunto canónico. Una receta sembrada con ["Gluten"] (mayúscula) o ["lacteos"] se sirve a alguien con "gluten". Y el comentario de la migración 20260725120100_…:257 todavía afirma que "el system prompt de Gemini (Layer 2)… repite la misma exclusión" — describe una red que ya no existe.

3 · Cero cobertura de comportamiento

get_filtered_recipes se ha redefinido ≥4 veces (4 migraciones). No hay supabase/tests/. No hay pgTAP. menu-selector.test.ts recibe candidatos ya filtrados y solo asserta estructura — no hay una sola aserción de alergenos o dieta en todo el fichero. Los 3 escenarios @seguridad del e2e testean propiedad de RPC (aislamiento de tenant), no correctitud del filtro (tests/steps/aislamiento-datos.steps.ts:53). El escenario de "no hay receta segura para el hueco" (AC-4 / FR-8.2) está marcado @verificado-manual-2026-07-31 — verificado a mano, una vez, hace cinco semanas, contra un catálogo distinto.

Un pipeline verde no te dice que el filtro de alérgenos funciona. Como @seguridad corre en el e2e, la capa parece cubierta.

Arreglo: (a) pgTAP o un e2e dedicado — perfil con alérgeno + receta de catálogo que lo lleva + generar + assertar que la receta está ausente — y gatear sobre él; (b) CHECK / validación al sembrar que todo elemento de recipes.alergenos ∈ el conjunto canónico, y lower() en el filtro; (c) decidir qué hacer con *_texto_libre: parsearlo contra un vocabulario ampliado, o quitarlo y mostrar un bloqueo honesto "no podemos garantizar seguridad para X"; (d) ampliar ALERGENO_OPTIONS hacia los 14 de la UE que el catálogo pueda soportar; (e) borrar el comentario de la Layer 2.

AltoA4-H1 · update-recipe-status mete alérgenos por la puerta de la sustitución

El endpoint aplica nueva_recipe_id if (nueva_recipe_id !== undefined) sin importar el estado, sin comprobar que esa receta es segura para el usuario, que existe, o que no está ya en el plan (update-recipe-status/index.ts:36,44). Luego el cambio de estado dispara el trigger global recipe_learning_trigger. El endpoint está vivo aunque ninguna UI lo use. Un usuario autenticado POSTea {estado:'sustituida', nueva_recipe_id: X} para los 21 huecos con una receta X que lleva un alérgeno, luego {estado:'cocinada', rating:5} ×21 → su calendario y su lista de la compra contienen la receta con alérgeno sin advertencia, y recipes.veces_cocinada[X] += 21, rating_promedio[X] sesgado — el agregado exacto que ADR-0002 prohíbe tocar a un swap de posición, corruptible directamente y sin rate limit (5 planes/hora × 21). Arreglo: validar estado === 'sustituida' antes de tocar recipe_id; pasar nueva_recipe_id por get_filtered_recipes para el llamante; rechazar receta ya en el plan; rate-limitar el endpoint.

AltoA4-H2 · reassign_guest_data mueve menús sin re-validarlos contra el perfil de destino

Cuando un invitado convierte con un email que ya tiene cuenta (path email_exists), reassign_guest_data mueve los meal_plans del invitado a la cuenta destino sin re-filtrarlos contra el perfil de alérgenos del destino (20260731140000_…:23) — se generaron contra el perfil del invitado. El data-map presenta "el perfil del destino nunca se toca" como una feature de seguridad; para el menú movido es lo contrario. Invitado sin alergias genera una semana con gluten, convierte con el email de una celíaca → la celíaca abre /calendar y ve recetas con gluten sin advertencia. Arreglo: al reasignar, re-filtrar cada hueco de cada plan movido contra el perfil destino y anular + advertir cualquier hueco ahora inseguro, o descartar los planes que no pasen.

06 BLOCKER 3 y 4 — El producto no se está midiendo, y no se puede vender

La maquinaria de monetización está entera. Lo que falta es la parte que da miedo: ponerlo delante de diez personas.

BlockerA4-B3 · Producto · el blocker legal lleva un mes sin moverse

Verificado en vivo en fresco-pro.vercel.app: el footer → "Términos" abre un modal con el banner "Borrador — pendiente de revisión legal antes de producción" y el placeholder [Titular del Servicio — nombre legal y NIF/CIF pendientes] (components/legal/legal-modal.tsx:22,153). En agosto el borrador se endureció bien (8 huecos GDPR cerrados), pero endurecer contenido no es la firma de un abogado, y Stripe necesita una entidad registrada real para cobrar. Todo el Master Sprint 2 del plan maestro está gateado en esto. Es la única tarea de la lista que no es de ingeniería, y es la que lleva un mes parada mientras se shipeaban fixes de contraste WCAG y caché de CI. Ese orden de prioridades es el síntoma, no el bug.

BlockerA4-B4 · Producto / Verificación · la métrica del MVP no es medible + funnel a ciegas

El charter del MVP (mvp-scope.md) define el go/no-go: "≥3 de 10 usuarios concierge tanto pagan como repiten uso 3+ semanas consecutivas, o pivota antes de escribir más código". Hoy:

  • "Pagan" — no medible. SUBSCRIPTION_STARTED dispara en checkout.session.completed para un trial de 7 días sin tarjeta — marca inicio de trial, no pago. No hay evento trial_converted_to_paid, no hay subscription_renewed, y handleSubscriptionUpdated no emite ningún evento PostHog en el primer cobro (webhook/route.ts:154). La conversión se leería de Stripe a mano.
  • "Repiten 3+ semanas" — débilmente medible. SESSION_STARTED (dispara también para invitados) alimenta el retention report de PostHog, pero ni SESSION_STARTED ni MENU_GENERATION_COMPLETED llevan semana_iso ni flag de tier — "semanas consecutivas" y "solo Pro" requieren aritmética de fechas frágil en PostHog.
  • Cohorte — imposible desde properties. identify() se llama con el uid pelado; no hay ni un posthog.people.set en todo el código. No hay property plan, signup_method, is_guest ni fecha-de-inicio-de-trial. No puedes definir la cohorte "empezó trial Pro en la semana de la cohorte".
  • Churn — invisible. webhook/route.ts:157 hace return temprano en canceled sin evento.

El funnel entero (20 etapas mapeadas) tiene 6 nombres de evento, 5 sin propiedades. Cero eventos de: onboarding iniciado / paso / completado, lista de la compra generada, plato descartado (¡la señal primaria del moat!), prompt de registro progresivo mostrado, checkout iniciado, CTA de landing. ADR-0013 prometió "el retention report nativo de PostHog, sin SQL de cohortes" — esa promesa solo cubre un retorno-de-sesión crudo, no la cohorte de ingreso-y-retención que el charter especifica.

Arreglo: antes de correr cualquier cohorte, instrumentar: eventos servidor trial_started (distinto), trial_converted_to_paid, subscription_renewed, subscription_cancelled; sincronizar plan / is_guest / signup_method como person properties en identify; etiquetar MENU_GENERATION_COMPLETED con semana_iso + tier; instrumentar las 15 etapas de funnel que faltan; y el reverse-proxy de PostHog (/ingest) que ADR-0013 difirió, porque un 15–30% de pérdida a ad-blockers sobre una cohorte de 10 distorsiona el go/no-go.

El moat es una bomba de tiempo

ADR-0001: el aprendizaje necesita semanas de señal. Trazado semana a semana (menu/page.tsx:194, index.ts:175, calendar-grid.tsx:300):

  • Semana 1 (cualquier tier): menú desde el perfil declarado. explicacionAprendizaje es null (sin historial). /menu no muestra ninguna superficie de aprendizaje. Free ve una caja de texto gris. Payoff percibido: cero.
  • Semana 2 (solo Pro): si y solo si el usuario encontró el toggle de 16px (A4-M27) y marcó ≥1 plato → primera explicación real. Requiere engagement activo en la semana 1.
  • Semana 4+ (solo Pro): destacadas + el nudge de scoreRecipe (ADR-0008) empiezan a morder. Aquí aterriza el "empieza a conocerte" de learns-pro.tsx — un mes dentro.
  • ¿Sembrado para usuarios nuevos? No — genuinamente vacío. Nada pre-poblado. El timeline de la landing ("Semana 4: vimos que descartas el pescado los miércoles") describe una capacidad que el producto no puede demostrar en semanas y que Free nunca demuestra.

El modelo concierge hace 3–4 semanas de seguimiento precisamente porque el dolor recurre — pero un usuario que no percibe valor en las semanas 1–2 se va antes de que el moat exista. No hay puente: ni ejemplo sembrado, ni "esto es lo que Pro hará cuando marques unos platos", ni indicador de progreso. La sección Consequences de ADR-0001 marca este riesgo exacto; la mitigación (hacer visible la mejora de Pro) está infra-construida.

09 El meta-proceso: la cinta de correr de auditorías

Tres auditorías profundas en 15 días, ~40 tickets de remediación, dos épicas meta. Y la validación del producto no ha empezado.

Desde el 20 de agosto: 110 commits docs contra 28 feat. Casi todo ticket completado desde el 27 de agosto es remediación de auditoría o infra de tests, no capacidad de usuario. La remediación es real donde es barata y verificable —cabeceras de seguridad, required checks, fixes de a11y, stack local en CI, el ledger de migraciones, ADR-0014→0018, el ratio de automatización 23%→56%, todo genuinamente hecho y confirmado en código—. Pero los tres hallazgos más difíciles se cerraron forward-only (§08), y la validación del núcleo —¿alguien paga y se queda?— sigue sin tocarse.

El modo de fallo del bucle se ve entero en el hilo de e2e-CI (A4-M20): un ticket de ratchet dispara un umbral que tú mismo pusiste en un ADR, que engendra un ticket de paralelización (−45s), luego uno de caché (−27s), luego "rediseñar todo el ciclo de vida del stack" (FRESCO-358). ~72 segundos perseguidos con 3 PRs, 1 ADR y 5 entradas de bitácora, en un proyecto que tu propio log llama "no urgente (un committer)". Y ADR-0018 puso un umbral de wall-clock que el siguiente ticket cruzó de inmediato — un umbral que atraviesas con tu propia siguiente tarea no es un umbral.

Las épicas post-MVP (FRESCO-330/331/332, 19 historias) se crearon el mismo día que esta auditoría y están sin refinar, sin AC, sin estimar, mientras el aparato de auditoría se come el calendario. La ingeniería es genuinamente buena. Se está gastando en la pregunta equivocada.

Recomendación de proceso

  • Cadencia mensual, no semanal. Una auditoría cada 4–6 semanas, no cada 5 días.
  • Una épica de remediación abierta a la vez, y tiene que cerrar —de verdad, no forward-only— antes de abrir la siguiente auditoría.
  • Congela la optimización de CI en "verde bajo ~7 min" hasta que haya usuarios de pago o un segundo committer. Cierra FRESCO-358 como diferido.
  • Las semanas recuperadas van a refinar y shipear FRESCO-330 para que exista uso real que auditar la próxima vez.

11 Lo que está bien — y es mucho

Los seis frentes lo dijeron por separado: la ingeniería es genuinamente buena.

  • El flujo de Stripe es sólido — verificación de firma con tolerancia de timestamp, fail-closed si falta el secreto, secreto de webhook por entorno, price-id verificado antes de cada concesión de Pro, entrega fuera de orden guardada por cross-check de stripe_subscription_id, client_reference_id server-side. El único hueco es el de INSERT (A4-B1), no el webhook.
  • El endurecimiento de la base de datos está hecho — todas las funciones SECURITY DEFINER con search_path pinneado; todas las políticas RLS con (SELECT auth.uid()) (sin re-evaluación por fila); pg_trgm/pg_net fuera de public; un event trigger rls_auto_enable que pone RLS deny-all a cualquier tabla nueva. FRESCO-27/28/29 realmente cerrados.
  • El aislamiento del e2e ya es arquitectónicamente correcto — stack Supabase local efímero por run (FRESCO-310) + factory users desechables por escenario con cascade-delete. La clase de carreras de estado compartido genuinamente desapareció.
  • Los tests que existen son de calidad real — lógica de verdad, edge cases con criterio (NaN, límites de año, anti-enumeración, scoping RLS aserido vía call args), bun test hermético (270 aserciones, 271 ms, fetch stubbeado en todo test networked).
  • El aislamiento de seguridad del e2e es la parte más fuerte de la suite — aislamiento-datos.steps.ts hace llamadas REST reales con tokens de atacante/víctima y asserta tanto el status rechazado como el estado de datos sin cambiar.
  • El motor determinista es un activo real — generación sub-segundo, cero coste de API, sin superficie de prompt-injection, sin alérgenos alucinados. Retiró entero el riesgo "la generación puede ser lenta/genérica" del PRD. El marketing debería dejar de esconderlo detrás de "con IA".
  • La higiene de defectos es excelente — ~93% cerrados, 7 abiertos y todos menores. La lectura de "180 tickets desordenados" es errónea: es un bucle de remediación de alto throughput bien llevado. El problema es la trazabilidad, no el volumen.
  • La seguridad alimentaria es lo construido con más cuidado — prefiltro SQL en capas + selector determinista + alérgenos implicados por dieta bloqueados en el onboarding (impliedAlergenos). El requisito no negociable recibió ingeniería no negociable — le falta la red de tests (A4-B2), no el diseño.
  • Los ADRs son disciplinados — 18 registros reales con alternativas y consecuencias; ADR-0014→0018 es un modelo de cómo hacer una supersesión.
  • El bloque git_strategy de project.yaml es inusualmente honesto — documenta que la estrategia "enterprise" declarada nunca se practicó y baja a solo-main para coincidir con git log.
  • Jira en vivo + token con Administer Jira ya funcionan, y branch-protection.md + .context/audits/*.html dan visibilidad real a un lector que solo tiene el clon.

La app autenticada sigue sin ejercerse — /menu, /calendar, /shopping-list, /perfil, /admin nunca se han abierto en ninguna de las cuatro pasadas. Con las credenciales PRE_USER_* por un canal privado, la quinta cubre la UX autenticada, la a11y del lado logueado y el flujo de admin de verdad. La rúbrica se queda fija en v1.
