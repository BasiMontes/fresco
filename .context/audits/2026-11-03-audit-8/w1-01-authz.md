## 2. Findings (sorted by severity)

### A8-AUTHZ-01 - `reassign_guest_data` neutralizes only allergen matches; diet, disliked ingredients and inactive recipes still land in the account's menu
- Severity: MEDIUM. Confidence: CONFIRMED (live function body read; not executed, it writes).
- Evidence: live `pg_get_functiondef('public.reassign_guest_data')` (SECURITY DEFINER, service_role only). The `neutralized` CTE keeps a moved slot unless `lower(ra.val) = any (ta.al)` where `ta.al` is the TARGET profile's `alergenos`; it sets `estado='excluida', recipe_id=null` only for that case. No call to `get_filtered_recipes`, no `r.activo` test, no `dieta_*` or `ingredientes_odiados` comparison. Sibling of A7-AUTHZ-01: `copy_meal_plan_to_week` now builds `v_allowed` from `get_filtered_recipes(v_user_id)` filtered by `f.activo` and blanks every slot outside it (live body, verified), so the two DEFINER paths that move whole plans into an account no longer enforce the same rule (ADR-0001 single enforcement point).
- Impact: a person who plays as a guest, then signs in to an existing account (the only caller path of `reassign-guest-data`) gets the guest's plans for weeks the account has no plan for, with recipes that break the account's declared vegetarian/vegan/sin gluten/sin lactosa/sin huevo/halal/keto diet, contain an ingredient the account marked as disliked, or were deactivated after being planned (for example after a catalogue retag). They are presented as the normal current menu. Allergens (the hard safety class) are covered; diet toggles for coeliac or lactose intolerance are only covered if the account also declared the matching allergen.
- Reproduction: local stack only (writes). Guest session generates week W; account A has `dieta_vegano=true` and no plan for W; call `reassign-guest-data`; A's W plan contains non-vegan recipes. Not run on the shared DB.
- Fix: in the `neutralized` CTE replace the allergen-only test by "recipe not in `get_filtered_recipes`-equivalent set for `p_to_user_id` or `not r.activo`" (the function is service-role, so `get_filtered_recipes` cannot be called as is because of its `auth.uid()` guard: extract the predicate into a `private.recipe_fits_profile(profile, recipe)` shared by both). Test: DB-integration test that reassigns a guest plan holding a non-vegan recipe to a vegan account and asserts the slot is `excluida`, plus one for an inactive recipe.
- Status vs audit 7: NEW (sibling of A7-AUTHZ-01).

### A8-AUTHZ-02 - `authenticated` can still UPDATE `meal_plan_recipes.dia`/`meal_plan_id` and `meal_plans.semana_iso`/`user_id`/`advertencias`/`explicacion_aprendizaje`/`coste_estimado`; no client code writes them
- Severity: LOW. Confidence: CONFIRMED (live column grants + trigger body + client code).
- Evidence: live `information_schema.column_privileges`: `meal_plan_recipes` UPDATE = `dia, estado, meal_plan_id, rating, recipe_id, sustitucion_ingrediente`; `meal_plans` UPDATE = `advertencias, coste_estimado, explicacion_aprendizaje, semana_iso, user_id`. Migration `20261019120000_revoke_surplus_grants_and_validate_inputs.sql` re-granted `dia`, `meal_plan_id` and the five `meal_plans` columns. `protect_meal_plan_recipes_integrity` only guards `estado, rating, recipe_id, sustitucion_ingrediente`. Client code: `rg "from\('(meal_plan_recipes|meal_plans)'\)"` shows exactly one client write, `lib/menu/snapshot-weekly-cost.ts:41` `.update({ coste_estimado })`, and one `.delete()` (`lib/api/meal-plan.ts:364`); no client update of `meal_plan_recipes` exists.
- Impact: self-only (RLS `USING` is reused as check, so nothing leaves the caller's own data). A direct PostgREST PATCH can (a) set `dia` of a past slot to a later weekday and so defeat the "slot is in a past day" guard of `assign_recipe_to_slot` (the guard derives the date from `fecha_inicio + position(dia)`), (b) relabel `semana_iso` of an old plan to the current week so `update-recipe-status` treats it as `esSemanaActual` and allows taking marks back, (c) erase or rewrite the `advertencias` allergen/skipped-slot notices shown to the user. Learning counters are now bounded by `recipe_user_feedback` (PK `user_id, recipe_id`), so the A7-AUTHZ-02 amplification is gone.
- Reproduction: signed-in session, `PATCH /rest/v1/meal_plan_recipes?id=eq.<own slot>` body `{"dia":"domingo"}` -> 204 (not executed: it would edit real rows).
- Fix: `revoke update on public.meal_plan_recipes from authenticated;` and `revoke update on public.meal_plans from authenticated; grant update (coste_estimado) on public.meal_plans to authenticated;` (swap/assign/confirm are INVOKER but their writes only touch `recipe_id/estado/rating/sustitucion_ingrediente` on slots; verify `assign_recipe_to_slot` and `confirm_ingredient_substitution` still work, they need UPDATE on those four columns, so keep exactly `grant update (recipe_id, estado, rating, sustitucion_ingrediente)`). Test: PostgREST PATCH of `dia`, `meal_plan_id`, `semana_iso`, `advertencias` as `authenticated` returns 403/42501.
- Status vs audit 7: STILL-OPEN A7-AUTHZ-03 (partially fixed: `tipo_plato`, `fecha_inicio`, `id`, timestamps are gone; the rest remains).

### A8-AUTHZ-03 - `get_safe_ingredient_substitutes` still executable by `anon`
- Severity: LOW. Confidence: CONFIRMED.
- Evidence: live `select proname, proacl, has_function_privilege('anon',oid,'execute') from pg_proc where pronamespace='public'::regnamespace` with anon = true returns exactly 3 rows: `get_safe_ingredient_substitutes` (`{=X/postgres,postgres=X/postgres,authenticated=X/postgres}`, PUBLIC grant present), `recipe_ingredient_names_distinct`, `recipe_ingredient_quantities_valid` (pure CHECK helpers, harmless). Migration `20261019120000` section 2 revoked PUBLIC/anon only on `confirm_ingredient_substitution` (now fixed live) and left the sibling that A7-AUTHZ-04 named.
- Impact: none today (INVOKER, joins `user_profiles on id = auth.uid()` so an anonymous call returns zero rows; `ingredient_substitutions` is public by design). Surface hygiene only; the entry point should not exist.
- Reproduction: `select proacl from pg_proc where proname='get_safe_ingredient_substitutes'`.
- Fix: `revoke execute on function public.get_safe_ingredient_substitutes(text) from public, anon; grant execute ... to authenticated;`. Test: anon RPC returns 401/42501.
- Status vs audit 7: STILL-OPEN A7-AUTHZ-04 (half fixed: allergen vocabulary CHECK `user_profiles_alergenos_vocab` live, `confirm_ingredient_substitution` revoked; `get_safe_ingredient_substitutes` not).

### A8-AUTHZ-04 - Password change and guest e-mail change are enforced only by the app; server-side enforcement depends on hosted Auth settings that cannot be read
- Severity: MEDIUM (A7-AUTHZ-05 kept) . Confidence: PLAUSIBLE (code CONFIRMED, hosted state unreadable).
- Evidence: `supabase/config.toml:240` now has `secure_password_change = true` (local only) and `lib/client-api/auth.ts:106` sends `current_password` to `auth.updateUser`, with `app/update-password/page.tsx` asking for it when `needsCurrentPassword(amr)` (`lib/auth/password-change.ts`). The file itself says "The app only asks; the Auth server enforces it once 'Require current password' is on in the project's Auth settings." Nothing in the repo or `docs/` records that the hosted toggle is on, and a caller holding a token can call `PUT /auth/v1/user {password}` directly, skipping the page. Same shape for FRESCO-1006: `app/api/auth/guest-email/route.ts` adds captcha + `check_and_increment_rate_limit` (3/h), but a guest JWT can still call `PUT /auth/v1/user {email}` straight at GoTrue, bypassing both (only Auth's own quota applies).
- Impact: stolen or left-open session can lock the owner out (password) or a guest session can aim code e-mails at third parties outside the route's captcha and limit (ADR-0021 Gmail cap). Capability needs a live session; no cross-user data.
- Reproduction: not run (would change the shared test account's password / send mail). Check: Dashboard > Authentication > Providers > Email, "Secure password change" / "Require current password".
- Fix: confirm the hosted toggle and record it in an ADR or `docs/` with the verification date; for the guest e-mail path, decide whether to disable client `updateUser({email})` for anonymous users at the Auth level (hosted "Secure email change" + captcha on) or accept it explicitly. Test: a post-deploy smoke that does `updateUser({password})` with a password-session lacking `current_password` and expects `current_password_required`/`reauthentication_needed`.
- Status vs audit 7: STILL-OPEN A7-AUTHZ-05 (app-side fix shipped, server-side unverifiable).

## 4. Checklist items that found NOTHING

1. Tables / RLS: 30 `public` tables all `relrowsecurity=true`; no views or matviews (so no `security_invoker` issue). Tables with RLS and no policy have no anon/authenticated grant at all (`account_erasures, billing_mode, ip_rate_limits, job_heartbeat, pending_confirmation_emails, rate_limit_*, recipe_season_exceptions, recipe_user_feedback, stripe_webhook_events, supermarket_price_history, supermarket_chain, waitlist_signups`). Every owner policy keys on `auth.uid() = user_id|id` or an EXISTS on `meal_plans.user_id`; `recetas_propias_update_own` and `shopping_update_own` carry WITH CHECK. `USING true` only on `recipes` and `ingredient_substitutions` (public catalogue, known). `meal_plans` has no INSERT policy or grant (rows come from `create_meal_plan` via service role).
2. Anon-reachable RPCs: only the three listed in A8-AUTHZ-03. All 25 DEFINER functions: client-callable ones check `auth.uid()` (`get_filtered_recipes`, `get_catalog`, `check_and_increment_rate_limit`, `jsonb_*`, `swap`, `copy`, `get_user_*`, `get_recent_recipe_marks`); service-only ones have only `service_role`/postgres in the ACL. `search_path` is pinned on all; `copy_meal_plan_to_week`, `jsonb_add_item` and `prevent_client_subscription_writes` pin `public` without `pg_temp`, but every table reference inside is schema-qualified and PostgREST offers no way to create temp objects, so not exploitable (INFO).
3. Pro/Free bypass: `prevent_client_subscription_writes` (BEFORE INSERT OR UPDATE on `user_profiles`) rejects any change of `plan, plan_expires_at, stripe_customer_id, stripe_subscription_id, payment_failed_at, stripe_livemode` unless `auth.role()='service_role'` or a superuser session; the Pro gate (learning applied to generation) lives only in `generate-meal-plan` via `isProEntitlementActive` on those protected columns; no Pro data is reachable by a direct table or RPC read (Free users' behaviour is recorded by design, ADR-0001). `rate_limit_exempt_users` has 0 rows (A4-H9 holds).
4. Cross-user access (meal plans, lists, profiles, consents, push, learning): `user_consents` SELECT own only, no write grant (`record_consents` is service-only and `/api/consents` binds `user.id` from the verified session); push insert also blocks anonymous JWTs; `get_push_subscriptions_without_current_plan` and `get_supermarket_demand` are service-only; `jsonb_add_item/clear/set_comprado` scope by `user_id = auth.uid()` and `jsonb_remove_item` is INVOKER under RLS.
5. Admin: `ADMIN_USER_ID` allowlist enforced in `proxy.ts` (404 rewrite), the admin page, and `delete-catalog-recipe` via `requireAdminUser`; no `is_admin` column; `recipes` has no authenticated write grant.
6. Storage: one bucket `recipe-photos` (public read; INSERT/UPDATE/DELETE policies for `service_role` only); `storage.objects` has no other policy. `realtime.messages` has RLS and no policy (private channels denied).
7. Edge Functions: `verify_jwt` matches the intent on all 9; user functions bind `user.id` from `auth.getUser()`; the two `verify_jwt=false` functions fail 401/500 closed on a missing or wrong `apikey`; CORS allowlist unchanged (explicit origins).
8. Route handlers: `profile/export`, `stripe/checkout`, `stripe/portal`, `consents`, `auth/guest-email` read the user from `auth.getUser()`, never from the body; the cron route uses `timingSafeEqual` on `Bearer ${CRON_SECRET}` and fails closed when unset; waitlist endpoints are anon by design with a 256-bit token and an IP limit.
9. Default privileges: `pg_default_acl` for role `postgres` in `public` grants functions only to `postgres` (no auto-grant to anon), so new migration functions are not exposed by default; `supabase_admin`-created objects are not used by the repo.
