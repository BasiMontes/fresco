## 2. Findings

### A7-PRIV-01 - Cookie consent carries no version and no date: the banner never re-asks when the cookie policy changes, and a visitor's consent cannot be proven
- Severity: MEDIUM. Confidence: CONFIRMED.
- Evidence: `lib/consent/cookie-consent.ts:13` `export type CookieConsentDecision = 'accepted' | 'rejected';` and `:39` `document.cookie = \`${COOKIE_CONSENT_COOKIE}=${decision}; path=/; max-age=${COOKIE_CONSENT_MAX_AGE}; samesite=lax\`` (value is the bare word, 1-year max-age). `components/legal/cookie-consent-context.tsx` exposes `bannerVisible: decision === null`, so any stored decision, from any policy version, suppresses the banner. No version constant is compared anywhere (`rg -n -i "version" .context/ADR/ADR-0025-cookie-consent-gate-strategy.md` returns nothing). For a signed-in user the only server copy is `user_profiles.analytics_consent boolean` (migration `20261014120000_user_profiles_analytics_consent.sql`), again with no version and no timestamp. Contrast: the registration consents ARE versioned (`lib/legal/consent.ts:19` `LEGAL_TEXTS_VERSION`).
- Impact: the cookie and privacy texts are provisional and will change after the lawyer's review (already known); when they do, every visitor who accepted the old text keeps being tracked by PostHog without being asked again (LSSI art. 22.2 and AEPD Guía de cookies 2024: renew consent when purposes or third parties change). Fresco cannot show when or to which text an analytics consent was given (GDPR art. 7.1).
- Reproduction: open https://fresco-pro.vercel.app, click "Aceptar", note cookie `fresco_cookie_consent=accepted`. Ship any change to the cookie table in `components/legal/legal-content-data.ts`; reload: no banner. Code-only reproduction (no production mutation done).
- Fix: store `accepted|rejected:<COOKIE_POLICY_VERSION>:<iso-date>` in the cookie, treat a different version as `null` (banner reappears), and mirror version + timestamp into a `user_consents` row of kind `analytics` (append-only, like the others) instead of a bare boolean. Test: unit test that `parseCookieConsent('accepted:v1:...')` returns `null` when the current version is `v2`, plus an e2e that the banner shows after a version bump.

### A7-PRIV-02 - No signed-up account has any age, Terms or Privacy consent on record (9 of 9), and nothing ever asks an account without one
- Severity: MEDIUM. Confidence: CONFIRMED (counts); PLAUSIBLE that the live UI signup records them (not executed: no account creation allowed).
- Evidence: read-only query `select kind, version, count(*) from public.user_consents group by 1,2` -> only `health_data/provisional-2026-10-06: 2`, `withdrawal_waiver/provisional-2026-10-04: 1`, `withdrawal_waiver/provisional-2026-10-06: 2`; zero rows of `age_14`, `terms`, `privacy`. `auth.users` non-anonymous = 9, all 9 without a `privacy` and an `age_14` row; 3 were created on or after 2026-10-06 (all 3 test identities), none carries `raw_user_meta_data.consent_pending` (count 0), so they were not created through the UI path that parks the consents. The only code that records registration consents for an existing session is `flushPendingConsents` (`lib/legal/consent-client.ts:50-59`), which acts only when `user_metadata.consent_pending` is present and is called only from `/onboarding` (`components/onboarding/use-onboarding-session-gate.ts:67`, `components/onboarding/identity-step.tsx:173`). There is no gate that asks a signed-in user lacking `terms`/`privacy`/`age_14` (or holding an older version) to accept, although `lib/legal/consent.ts:10-11` says "a new version is what lets a later flow ask the user to consent again" - that later flow does not exist.
- Impact: the two real (non-test) accounts and every account created by tooling have used the service with no recorded acceptance of the Terms, the Privacy Policy or the 14+ age declaration; when the lawyer's final texts bump `LEGAL_TEXTS_VERSION`, no existing user will be asked to accept them, so Fresco cannot demonstrate acceptance (GDPR art. 7.1, art. 8 + LOPDGDD art. 7 for the age).
- Reproduction: run the two SELECTs above with `supabase db query --linked`. For the missing re-ask: `rg -n "LEGAL_TEXTS_VERSION" app components lib --glob '!**/*.test.*'` shows it is only stamped on writes, never compared on read.
- Fix: a server-side check on the authenticated layout (or `/api/...` profile read) that returns the consent kinds missing at the current `LEGAL_TEXTS_VERSION`, and a blocking re-consent dialog that POSTs them. Test: an integration test where a user with only `provisional-2026-10-06` rows sees the dialog after the constant is bumped; and an e2e that the real `/signup` flow produces three rows after email confirmation.

### A7-PRIV-03 - The landing waitlist collects emails on production with no privacy-policy disclosure, no confirmation (double opt-in), no retention and no way to leave
- Severity: MEDIUM. Confidence: CONFIRMED.
- Evidence: production `GET https://fresco-pro.vercel.app/` HTML contains `waitlist_email_input`, `waitlist_consent_checkbox`, `waitlist_submit` (form is live). `lib/legal/waitlist.ts:13` consent copy: "Acepto que Fresco use mi correo solo para avisarme del lanzamiento."; `:57` `.insert({ email, consent_version: LEGAL_TEXTS_VERSION })`. `supabase/migrations/20261011140000_waitlist_signups.sql:40` `grant insert (email, consent_version) ... to anon, authenticated` (no select/delete for browser roles, no retention job, no FK so account deletion never touches it). `rg -i -c "lanzamiento|lista de espera|waitlist" components/legal/legal-content-data.ts app/legal` -> 0 matches, and `GET /legal/privacidad` on production (200) lists no waitlist purpose. `app/api/waitlist/route.ts` sends no confirmation email; anyone can enrol any address. Current rows: `select count(*) from public.waitlist_signups` -> 0.
- Impact: the first launch email to this list is a commercial communication (LSSI art. 21): without a confirmed opt-in Fresco cannot prove the address owner consented, the privacy policy does not tell enrolees the purpose, legal basis, retention or how to withdraw (GDPR art. 13), and there is no unsubscribe path built for that email. Rows also survive the person's account deletion.
- Reproduction: view the landing form and the privacy page on production (GET only; no submission made).
- Fix: add a "Lista de espera" paragraph to the privacy policy (purpose, art. 6.1.a, deletion after the launch email or N months, how to withdraw); send a confirmation link and only count confirmed rows; schedule deletion after launch; include a one-click unsubscribe (List-Unsubscribe header + link) in the launch email; delete matching waitlist rows in `delete-account`. Test: unit test of the policy copy section; db test that a cron removes rows older than the retention.

### A7-PRIV-04 - Guest data is deleted 3 days after creation (not "after inactivity" as the policy says) and the guest's PostHog person is never erased
- Severity: LOW. Confidence: CONFIRMED.
- Evidence: `supabase/migrations/20260823160000_shorten_guest_cleanup_retention_to_3_days.sql:12` `delete from auth.users where is_anonymous = true and created_at < now() - interval '3 days'` (by creation date, pure SQL: no PostHog erasure, no `account_erasures` row). Privacy policy (`components/legal/legal-content-data.ts:177`, live on production): "tus datos se eliminan automáticamente pasado un período de inactividad". The PostHog provider identifies guests too (`app/providers/posthog-provider.tsx` `identifyWithProperties`, keyed on `${user.id}:${user.is_anonymous === true}` and `$set`s `is_guest`), while erasure of the PostHog person exists only in `supabase/functions/delete-account/index.ts:174` `deletePostHogPerson(user.id)`.
- Impact: a guest who accepted analytics keeps a PostHog person and events indefinitely after Fresco deletes her data, contrary to the retention statement; and an active guest loses her data on day 3 even if she used it that morning, which the policy wording does not describe.
- Reproduction: code path only (creating a guest on production is out of scope). Query `select count(*) from auth.users where is_anonymous` returned 0 today, consistent with the 3-day sweep.
- Fix: either change the policy text to "3 días después de crear la sesión de invitada" or sweep on `last_sign_in_at`; and route the sweep through the same erasure helper (queue each deleted guest id into `account_erasures.pending_posthog_distinct_id`, which the existing retry cron `20261014130000_retry_posthog_erasures.sql` already drains). Test: db test that the cleanup inserts one pending erasure per deleted guest.

### A7-PRIV-06 - The halal diet flag reveals religious belief (GDPR art. 9) but the health consent and the policy describe only health data
- Severity: LOW. Confidence: CONFIRMED.
- Evidence: `user_profiles.dieta_halal boolean` (`lib/supabase/types.ts` Row). Consent copy `lib/legal/consent.ts:24` "Consiento el tratamiento de mis datos de alergias y dieta para excluir recetas no seguras." Policy `components/legal/legal-content-data.ts:161`/`:165` qualifies only allergies/ingredients as special category "por su relación con la salud". The server trigger (`supabase/migrations/20261014100000_require_health_data_consent.sql`) does cover `dieta_halal`, so the gate exists; the gap is that the consent is not specific to the religious category, and the trigger accepts a `health_data` row of ANY version (comment in that migration: "this proves 'the user consented once', not 'to today's text'").
- Impact: explicit consent under art. 9.2.a must name the category and purpose; a user marking halal never consents to the processing of a religious belief. Distinct from the already-known "texts provisional with the lawyer": this is a missing category, worth giving the lawyer explicitly.
- Reproduction: read the three quoted texts.
- Fix: reword the consent and policy to "alergias, intolerancias y preferencias de dieta, que pueden revelar datos de salud o creencias religiosas (p. ej. halal)", bump `LEGAL_TEXTS_VERSION`, and make the trigger require the current version (pass it via a settings table). Test: db test that a `health_data` row of an old version no longer satisfies the trigger after the bump.
