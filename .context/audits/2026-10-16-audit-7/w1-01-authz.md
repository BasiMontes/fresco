## 2. Findings (sorted by severity)

### A7-AUTHZ-01 - `copy_meal_plan_to_week` re-plants recipes without the allergen/diet filter
- Severity: HIGH. Confidence: CONFIRMED (live function body read; not executed, it writes).
- Evidence: live `pg_get_functiondef('public.copy_meal_plan_to_week')` (SECURITY DEFINER, EXECUTE to `authenticated`):
  ```sql
  insert into public.meal_plan_recipes (meal_plan_id, recipe_id, dia, tipo_plato, estado)
  select v_new_id, recipe_id, dia, tipo_plato, 'pendiente'
  from public.meal_plan_recipes
  where meal_plan_id = p_source_meal_plan_id;
  ```
  No call to `get_filtered_recipes`, no `recipes.activo` check, no profile read. Every other path that puts a recipe in a slot goes through the filter: `assign_recipe_to_slot` (`get_filtered_recipes(auth.uid(), p_recipe_id)`), `update-recipe-status` (`supabase/functions/update-recipe-status/index.ts:94`), `reassign_guest_data` (A4-H2 re-filter). Caller: `lib/api/meal-plan.ts:277-289` (`copyMealPlanToCurrentWeek`, button "Usar este menú en la semana actual", FRESCO-427); no client-side re-check either (`rg -i alerg components/historial/reuse-menu-button.tsx` = 0 hits). Not in prior audits (`rg copy_meal_plan .context/audits` only hits A5-H6, the non-disclosure fix).
- Impact: a user who declared a new allergen, diet or disliked ingredient after week N (or a recipe that was retagged/deactivated since, e.g. `20261012100000_fix_recipe_allergen_and_diet_tags.sql`) reuses week N and gets a current-week menu with recipes that contain that allergen, presented as a normal safe menu. Food-safety, the product's core promise (ADR-0001 single enforcement point is bypassed by a DEFINER RPC).
- Reproduction (local stack, not run on the shared DB): profile with `alergenos='{}'`, generate week W1 containing a recipe tagged `cacahuetes`; record `health_data` consent and set `alergenos='{cacahuetes}'`; call `rpc('copy_meal_plan_to_week', {p_source_meal_plan_id: W1, p_semana_iso: <current>, p_fecha_inicio: <monday>})`; the new plan contains the peanut recipe.
- Fix: in the INSERT ... SELECT, join `public.get_filtered_recipes(v_user_id, null) f on f.id = src.recipe_id` and insert the unsafe/inactive slots as an empty `pendiente` slot (or `excluida`) plus an `advertencias` entry; keep it atomic. Also add the rate limit `swap_meal_plan_slots` already has. Test: DB-integration test (real session, automation identity) that copies a plan containing a recipe matching a newly declared allergen and asserts it is absent from the target week.

### A7-AUTHZ-02 - One account can move the GLOBAL recipe ranking every user's menu is built from
- Severity: MEDIUM. Confidence: PLAUSIBLE (every step read in code/live DB; not executed because it writes shared `recipes` rows).
- Evidence:
  - Live trigger `recipe_learning_trigger AFTER UPDATE ON meal_plan_recipes` -> `update_recipe_learning()` (SECURITY DEFINER) does `update public.recipes set veces_cocinada = veces_cocinada + 1, ... rating_promedio = round((coalesce(rating_promedio,0)*veces_calificada + new.rating)/(veces_calificada+1),2)` and `veces_descartada = veces_descartada + 1` on every per-user estado change. No per-user dedupe, no weighting.
  - `supabase/functions/generate-meal-plan/menu-selector.ts:123-125`: `score += (recipe.rating_promedio ?? 0) * 2`, `score += Math.min(recipe.veces_cocinada, 10) * 0.3`, `if (recipe.veces_descartada > 2) score -= 4`; this global score ranks recipes for every user, Free and Pro.
  - Supply of slots is unbounded for one account: `copy_meal_plan_to_week(p_source_meal_plan_id, p_semana_iso, p_fecha_inicio)` takes the target week from the caller, has no rate limit (`rate_limit_endpoints` live: `generate-meal-plan=5, update-recipe-status=60, ..., swap_meal_plan_slots=120, assign_recipe_to_slot=60`; no `copy_*` row and no call in the body), and `meal_plans.semana_iso` only has a format CHECK, so one account can mint plans for hundreds of weeks containing a chosen recipe; `update-recipe-status` then allows 60 marks/hour (`cocinada` + `rating=1`, or `descartada`).
- Impact: a single free account (or a few captcha-gated guest accounts) can bury any catalog recipe for all households (3 discards trigger the -4 penalty, which is about two rating stars) or push one up with fake 5-star ratings. Cross-tenant integrity of the recommendation, not a data leak.
- Reproduction: local stack only: one user, copy a plan containing recipe R into 3 future weeks, mark R `descartada` in each via `update-recipe-status`; `select veces_descartada from recipes where id=R` = 3 and R's score drops for a second user. Not run on the shared DB.
- Fix: count learning per (user, recipe) once (e.g. a `recipe_user_feedback` table with a unique key, aggregates derived from it), cap `copy_meal_plan_to_week` to the current/next ISO week and add a rate-limit row for it. Test: DB-integration test where the same user discards R in 3 plans and `veces_descartada` increments by 1.

### A7-AUTHZ-05 - Password can be changed from any live session, no current password, no recent login
- Severity: MEDIUM. Confidence: PLAUSIBLE (code CONFIRMED; the hosted GoTrue setting could not be read).
- Evidence: `app/update-password/page.tsx:19-22` claims the page is "Only reachable with a real recovery session", but the only gate is `getSession().then(session => setHasSession(session !== null))` (`:42-44`); the submit calls `updatePassword(password)` = `createClient().auth.updateUser({ password })` (`lib/client-api/auth.ts:82-83`), no current password, no reauthentication nonce. `supabase/config.toml:240`: `secure_password_change = false` ("users will need to reauthenticate or have logged in recently to change their password" is OFF). Leaked-password protection is also off on the hosted project (`get_advisors`: `auth_leaked_password_protection` WARN; known, HIBP needs Pro, the page does a client-side HIBP check instead).
- Impact: anyone holding a session for a few seconds (shared family tablet left signed in, a stolen access/refresh token) opens `/update-password` (or calls `PUT /auth/v1/user` directly) and sets a new password, locking the owner out until she notices and uses the reset email; payment/Pro state then sits on an account she no longer controls. The comment's "recovery only" belief is false.
- Reproduction: signed-in non-recovery session on fresco-pre (automation identity) -> visit `/update-password` -> the form renders (not executed: it would change the shared test account's password).
- Fix: enable "Secure password change" on the hosted Auth settings (and set it in `config.toml` so local matches); in the page, require the current password (re-`signInWithPassword` before `updateUser`, same pattern as `delete-account-dialog.tsx:80`) unless the session's AMR is `recovery`/`otp`. Test: e2e with a normal password session expects the page to ask for the current password; API test: `updateUser({password})` on a session older than the window returns `reauthentication_needed`.

### A7-AUTHZ-03 - Integrity triggers leave scope columns client-writable (self-only)
- Severity: LOW. Confidence: CONFIRMED (live grants + trigger body).
- Evidence: `information_schema.column_privileges` live: `authenticated` UPDATE on `meal_plan_recipes(created_at,dia,estado,id,meal_plan_id,rating,recipe_id,sustitucion_ingrediente,tipo_plato,updated_at)` and on `meal_plans(advertencias,coste_estimado,created_at,explicacion_aprendizaje,fecha_inicio,id,semana_iso,updated_at,user_id)`. `protect_meal_plan_recipes_integrity()` only blocks `estado, rating, recipe_id, sustitucion_ingrediente`; `dia`, `tipo_plato`, `meal_plan_id`, `id` pass. RLS (`mpr_update_own`, `meal_plans_update_own`, no WITH CHECK so USING is reused) keeps every change inside the caller's own data.
- Impact: a user can, via a direct PostgREST PATCH, change a slot's `tipo_plato` (defeating the tipo_plato match in `assign_recipe_to_slot` and `swap_meal_plan_slots`), move `fecha_inicio` forward to reopen past days (defeats the "slot is in a past day" guard), rewrite `advertencias`/`explicacion_aprendizaje`/`coste_estimado` shown back to them. Self-only; it feeds A7-AUTHZ-02.
- Reproduction: signed-in session, `PATCH /rest/v1/meal_plan_recipes?id=eq.<own slot>` body `{"tipo_plato":"postre"}` -> 204 (not executed; grant + trigger read).
- Fix: `revoke update on meal_plan_recipes, meal_plans from authenticated` and grant only the columns the UI writes directly (if none, revoke UPDATE entirely: all writes already go through RPCs or the Edge Function). Test: PostgREST PATCH of `tipo_plato`/`fecha_inicio` as `authenticated` returns 401/403.

### A7-AUTHZ-04 - Two substitution RPCs keep the default PUBLIC EXECUTE; allergen overlap is case-sensitive
- Severity: LOW. Confidence: CONFIRMED.
- Evidence: live `pg_proc.proacl`: `confirm_ingredient_substitution` and `get_safe_ingredient_substitutes` = `{=X/postgres,...}` (PUBLIC, so `anon` can call them), unlike every other client RPC (`revoke ... from public, anon`, e.g. `20261014140000_jsonb_remove_item_rpc.sql:71`). `get_safe_ingredient_substitutes` filters with `not (s.alergenos && coalesce(p.alergenos,'{}'))` (exact-case), while `get_filtered_recipes` was hardened to `lower()` on both sides (FRESCO-361 / A4-B2); `user_profiles.alergenos` has no vocabulary CHECK (only size bounds), whereas `ingredient_substitutions.alergenos <@ ARRAY['altramuces',...]`. Live count: 0 of 4 profiles hold an upper-case or off-vocabulary allergen today.
- Impact: today nothing leaks (both are INVOKER; anon has no UPDATE on `meal_plan_recipes` and no profile row). The case-sensitive compare is a latent food-safety gap: a profile written as `Soja` would be offered a soy substitute.
- Reproduction: `select proacl from pg_proc where proname in ('confirm_ingredient_substitution','get_safe_ingredient_substitutes')`.
- Fix: `revoke execute ... from public, anon` on both; add `CHECK (alergenos <@ ARRAY[...14 slugs])` on `user_profiles` (or compare with `lower()`). Test: anon RPC call returns 401/42501; profile insert with `Soja` is rejected.


## 3. Checklist items that found NOTHING (evidence that the absence was looked for)

1. **Tables / RLS / policies.** 24 relations in `public`, all `relkind='r'`, all `relrowsecurity=true` (none forced; no table owner is a client role, so not needed). No views, no matviews (so no `security_invoker` issue). 8 tables with RLS and zero policies (`account_erasures, job_heartbeat, rate_limit_endpoints, rate_limit_exempt_users, rate_limits, stripe_webhook_events, supermarket_chain, supermarket_price_history`) have no `anon`/`authenticated` table grant at all. `USING true` only on `recipes` and `ingredient_substitutions` SELECT (public catalog, known C-25) and `waitlist_signups` INSERT `WITH CHECK true` (column grant `(email, consent_version)` only; known C-21). Every owner policy keys on `auth.uid() = user_id|id` or an `EXISTS` on `meal_plans.user_id`; UPDATE policies without WITH CHECK (`meal_plans_update_own`, `mpr_update_own`, `profiles_update_own`) reuse USING on the new row, so `user_id`/`id`/`meal_plan_id` cannot be moved to another user. No policy keys on a user-editable column other than the owner id. Storage: one bucket `recipe-photos` (public, read for all, write/update/delete `service_role` only).
2. **Grants.** `anon`: SELECT `recipes`, `ingredient_substitutions`; INSERT `waitlist_signups(email, consent_version)`; EXECUTE only on `confirm_ingredient_substitution`, `get_safe_ingredient_substitutes` (A7-AUTHZ-04) and the two pure CHECK helpers `recipe_ingredient_names_distinct` / `recipe_ingredient_quantities_valid` (IMMUTABLE-style, no table access, harmless). `authenticated` has no INSERT on `meal_plans`/`meal_plan_recipes`; `user_consents` INSERT only `(kind, version)` with `user_id default auth.uid()`; no UPDATE/DELETE on consents.
3. **SECURITY DEFINER bodies** (all read live): `check_and_increment_rate_limit`, `get_catalog`, `get_filtered_recipes` raise on `p_user_id <> auth.uid()`; `get_recent_recipe_marks`, `get_user_cooked_recipe_ids`, `get_user_recipe_engagement` scope rows with `mp.user_id = auth.uid()`; `jsonb_add_item`, `jsonb_clear_comprados`, `jsonb_set_comprado` scope on `user_id = auth.uid()`; `jsonb_remove_item`, `assign_recipe_to_slot`, `confirm_ingredient_substitution` are INVOKER (RLS applies); `swap_meal_plan_slots`, `copy_meal_plan_to_week` bind ownership per slot/plan with one generic error. All have a pinned `search_path` incl. `pg_temp` (only Supabase's `rls_auto_enable` uses `pg_catalog`). Service-only: `create_meal_plan`, `reassign_guest_data`, `get_push_subscriptions_without_current_plan`, `get_supermarket_demand`. `auth.uid() IS NULL` path of the `<>` checks is unreachable for clients (anon has no EXECUTE). The only DEFINER gaps are row CONTENT (A7-AUTHZ-01) and the learning side effect (A7-AUTHZ-02), not cross-user reads/writes.
4. **Entitlement fields.** `authenticated` has column UPDATE/INSERT on `plan, plan_expires_at, stripe_customer_id, stripe_subscription_id, payment_failed_at`, but `prevent_client_subscription_writes` (BEFORE INSERT OR UPDATE, DEFINER) rejects any change unless `auth.role()='service_role'` or a superuser `session_user`; client JWTs cannot carry `service_role` without the secret. Health-data columns require a `health_data` consent row (`require_health_data_consent`). Cross-user reads of profiles, allergens, plans, lists, push subscriptions, consents, favorites and own recipes: all blocked by owner policies (no notifications/feedback tables exist; notifications are push only). Pro gate lives only in `generate-meal-plan` (`entitlement.ts:28`) reading the protected columns.
5. **Migrations.** Since the 2026-10-12 definitive audit: 3 new tables (`account_erasures`, `job_heartbeat`, `waitlist_signups`) all closed correctly; `jsonb_remove_item` revokes PUBLIC/anon; `retry_posthog_erasures` uses Vault + `apikey`. No migration re-opens A6-S1 (`apply_recipe_status_update` absent from `pg_proc`), A4-B1 (subscription trigger is BEFORE INSERT OR UPDATE) or drops a policy without replacement.
6. **Edge Functions.** Live `verify_jwt=true` on 7 user-facing functions; `false` only on `send-weekly-reengagement-push` and `retry-posthog-erasures`, both gated by `requireServiceRoleCaller` (timing-safe compare, `_shared/auth.ts:47-62`). User functions resolve the user with `auth.getUser()` and bind `user.id` from the JWT (`generate-meal-plan` passes `user.id` to every RPC; `generate-shopping-list:49-50` `.eq('user_id', user.id)`; `update-recipe-status:74` ownership check before the service-role write). `delete-catalog-recipe` behind `requireAdminUser` allowlist; `reassign-guest-data` requires an anonymous caller + recent target token; `delete-account` requires a recent re-auth token for non-guests. CORS: explicit 3-origin allowlist, localhost only on the local stack.
7. **Next.js.** `proxy.ts` does session refresh only (access control in `(app)/layout.tsx:34-36` via `getUser()`), `/admin` double-gated. Every route handler takes the user from `auth.getUser()`, none from the body (`consents`, `profile/export`, `stripe/checkout` with `client_reference_id: user.id`, `stripe/portal`). Cron route uses `timingSafeEqual` on `Bearer ${CRON_SECRET}` and fails closed when unset. `/dev/skeleton-capture` calls `notFound()` in production (live `GET` = 404). No server actions exist. `/api/health`, `/api/health/jobs`, `/qa` public by design (known C-20).
8. **Session.** `/auth/confirm` uses `safeNextPath` (open redirect closed, A4-L1); `double_confirm_changes = true`; anonymous upgrade checks `email_exists` at OTP step (GoTrue-inherent); login shows "email not confirmed" only after GoTrue validates the password; logout uses default `signOut()` (global scope). Supabase SSR cookies are not `httpOnly` by library design (INFO; mitigated by the nonce CSP).
