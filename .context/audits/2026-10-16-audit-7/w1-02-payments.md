### A7-PAY-01 - Once production goes live, any user can get production Pro for free with a Stripe test card on fresco-pre (no `livemode` guard anywhere)
- Severity: HIGH (paywall bypass on the day Stripe goes live; BLOCKER for "charge real users" unless C-04's fix lands first). Confidence: PLAUSIBLE (every code link read; end-to-end not executable: needs live keys and a payment).
- Relation: new consequence of the already-known C-04 (`.context/audits/2026-10-12-definitive/04-critical-audit.md:78-81`, "entorno compartido"), still unfixed: `rg -i livemode` over the repo returns only `docs/workflows/stripe-refunds.md:38` and a comment in `lib/stripe-checkout-branding.ts:5`; no code reads `event.livemode`, `session.livemode` or `subscription.livemode`. C-04 described the denial-of-service side (test `cus_` breaks real checkout); this is the inverse, free-Pro side.
- Evidence:
  - One Supabase project for all environments: `.agents/project.yaml` `environments.*.db_project_ref: jdqemhewjrjuopssdurn`; fresco-pre is public ("`fresco-pre` itself is exempt [from Deployment Protection] and reachable without a Vercel account", same file, staging `web_url` comment). Same auth users on pre and pro.
  - The pre webhook verifies with its own secret (`lib/stripe.ts:49-52`, `STRIPE_WEBHOOK_SECRET_PRE`) and then writes the shared row with no mode check: `app/api/stripe/webhook/route.ts:153-155` -> `lib/billing/grant-pro.ts:71-76` `activateProPlan(... plan: 'pro' ...)` (`lib/billing/subscription.ts:56-61`).
  - Pro gate reads only the row: `supabase/functions/generate-meal-plan/entitlement.ts:32-40` (`plan` + `plan_expires_at`), `lib/api/user-profile/plan.ts:45-55` (`plan` only).
  - A returning user is sent to a card checkout, which on pre accepts test card 4242: `app/api/stripe/checkout/route.ts:106-108` (`payment_method_collection: 'always'`).
  - The only thing that undoes it is the production cron (live key) getting `resource_missing` for a test-mode subscription id and downgrading (`app/api/cron/stripe-reconcile/route.ts:119-123`), once a day; the user repeats.
- Impact: after the switch to live keys, any production account holder can open fresco-pre, sign in with their normal credentials, pay with a public test card and be Pro in production (same row) until the next daily reconcile, indefinitely repeatable (10 checkouts/hour allowed, route.ts:19). Revenue leak and a corrupted `stripe_customer_id` (C-04) on the same account.
- Reproduction: not executed (needs live keys + a payment). Steps once live: sign in on https://fresco-pre.vercel.app with a production account -> /profile -> "Pásate a Pro" -> card 4242 4242 4242 4242 -> back on https://fresco-pro.vercel.app the account shows Pro and generate-meal-plan returns the learning explanation.
- Fix: store the mode with the ids (`stripe_livemode boolean`) and in the webhook/grant refuse any event whose `livemode` differs from the mode of `STRIPE_SECRET_KEY` of the environment that owns production data (prefix `sk_live_`); refuse checkout on non-production deploys for accounts that are not test identities; or (C-04's real fix) split the production Supabase project. Test: webhook unit test that a `livemode:false` `checkout.session.completed` processed with a live-mode config writes nothing.

### A7-PAY-02 - Two checkouts before the webhook lands create two paid subscriptions; the app tracks one, and refunding the duplicate cancels the one the user keeps
- Severity: HIGH (double charge to a real customer, then the support remedy removes their access while the untracked duplicate keeps billing). Confidence: PLAUSIBLE for the double subscription (not reproduced: needs payments); CONFIRMED for the refund mis-targeting (exact code path read).
- Evidence:
  - The only "already subscribed" guard is the DB row, which the webhook writes later: `app/api/stripe/checkout/route.ts:93-95` (`if (profile?.plan === 'pro') ... 409`). No `stripe.subscriptions.list({customer})` check, no idempotency key on `stripe.checkout.sessions.create` (route.ts:103-116), sessions stay open 24 h by default (no `expires_at`).
  - The client double-click guard is per tab only: `components/profile/use-pro-checkout.ts:22-33` (`isRedirecting` React state). The success return lands on `/profile?checkout=success` (route.ts:114) and nothing reads that parameter (`rg "checkout=success"` matches only route.ts:114), so until the webhook arrives /profile still shows the Free upsell and the CTA.
  - A returning customer is sent with `customer: stripeCustomerId` and `payment_method_collection: 'always'` (route.ts:106-109), so a second completed session adds a second paid subscription on the same customer. The second `checkout.session.completed` overwrites `stripe_subscription_id` (`lib/billing/subscription.ts:53-61`); from then on every event of the first subscription is dropped as "out-of-order" (`app/api/stripe/webhook/route.ts:224-227`, `312-315`) and the reconcile cron only reads the stored id (`lib/billing/reconcile.ts:24-28`). Nothing ever notices the orphan; it renews monthly.
  - Refund handler maps charge -> customer -> the subscription on file, never -> the charge's own subscription/invoice: `app/api/stripe/webhook/route.ts:357-369` then `lib/billing/refund.ts:37-40` cancels `subscription.id` (the stored one) whenever `charge.created >= current_period_start`. A full refund of the duplicate's charge (the obvious support action, `docs/workflows/stripe-refunds.md`) therefore cancels the subscription the person meant to keep (`route.ts:378-382`, immediate, no proration) and `customer.subscription.deleted` downgrades them, while the duplicate keeps charging.
  - First-time buyers have no `stripe_customer_id`, so two sessions create two Stripe customers; account deletion cancels only the subscriptions of the one customer it finds (`supabase/functions/delete-account/index.ts:108-143`), so the other keeps billing a deleted account (narrow reopening of known C-01). Without a card (trial) the orphan cancels itself at trial end (`lib/legal/pro-terms.ts:18`), so the money risk is on card checkouts.
- Impact: a paying user who opens the upgrade twice (two tabs, back button from Stripe, retry after a slow redirect) is charged twice every month; when support refunds the extra charge, the user loses Pro and is still billed by the subscription the app cannot see.
- Reproduction: not executed (payments forbidden). In Stripe test mode with a profile that already has `stripe_customer_id`: open two tabs on /profile, start checkout in both, pay both with 4242 -> Stripe customer shows 2 active subscriptions, `user_profiles.stripe_subscription_id` = the second. Refund in full the second subscription's first charge... (or the first's) -> observe the stored one is cancelled.
- Fix: (1) in the checkout route, before creating a session, list the customer's subscriptions with status in (trialing, active, past_due) and return 409; pass an idempotency key per user+interval+10-minute bucket; set a short `expires_at`; (2) in `handleChargeRefunded` resolve the charge's own subscription (via `invoice_payments`/`charge.payment_intent` -> invoice -> `parent.subscription_details.subscription`) and cancel only that one, ignoring when it differs from the stored id; (3) on `checkout.session.completed` for a user whose stored subscription is still live and different, alert (Sentry) instead of silently overwriting. Tests: route test "existing live subscription -> 409"; refund unit test "refund of a charge from a different subscription -> ignore".

### A7-PAY-04 - Disputes (chargebacks) are not handled: the disputing customer stays Pro and is charged again next cycle
- Severity: MEDIUM. Confidence: PLAUSIBLE (code path CONFIRMED; Stripe-side behaviour per Stripe's model, where a dispute does not end the subscription; not reproduced).
- Evidence: `app/api/stripe/webhook/route.ts:73-79` `HANDLED_EVENT_TYPES` = checkout.session.completed, checkout.session.async_payment_succeeded, customer.subscription.updated, customer.subscription.deleted, charge.refunded; every other type is a no-op (route.ts:166-168). `rg -i "dispute|chargeback|contracargo"` over app/lib/docs/ADR finds only a comment listing `payment_disputed` as a possible cancellation reason (route.ts:323) and the account-deletion refund error codes (`supabase/functions/_shared/stripe-billing.ts:146`). - Fix: handle `charge.dispute.created`: cancel the subscription of that charge (same targeting as the corrected A7-PAY-02 refund handler, `cancellation_details.comment: dispute:<id>`), report to Sentry, and subscribe the endpoints to it; add the case to the refunds runbook. Test: webhook unit test "dispute created -> stripe.subscriptions.cancel called for that charge's subscription".

### A7-PAY-05 - A late `customer.subscription.updated` (status active) after `deleted` puts a cancelled account back on Pro
- Severity: LOW (self-heals at the next daily reconcile). Confidence: CONFIRMED (code path), not reproduced.
- Evidence: `handleSubscriptionUpdated` acts on the event's snapshot `event.data.object` (`app/api/stripe/webhook/route.ts:158`, `205-283`), not on the live subscription. Its out-of-order guard only compares ids (route.ts:224), and `downgradeToFree` keeps `stripe_subscription_id` (`lib/billing/subscription.ts:105-109`), so after a `deleted` the guard still matches. A stale `active` snapshot -> `resolvePaymentStatusUpdate` returns `recovered` (`lib/stripe.ts:358-360`) -> `applyRenewal` writes `plan: 'pro'` and the snapshot's `current_period_end` (`subscription.ts:121-125`). For an immediate cancellation mid-period (refund, FRESCO-900; account deletion) that date is in the future, so the Edge gate (`entitlement.ts:35-40`) also says Pro. Stripe does not guarantee delivery order (the code itself says so, route.ts:217-223); `grantProFromCheckoutSession` already re-reads the subscription live for this reason (`lib/billing/grant-pro.ts:54`).
- Impact: a refunded or cancelled user can get Pro back for up to a day; the funnel may also fire a spurious renewal event.
- Reproduction: replay from the Stripe dashboard an earlier `customer.subscription.updated` (active) of a subscription after its `customer.subscription.deleted` was processed (event ids differ, so the claim table does not stop it) -> profile returns to `pro`.
- Fix: in `handleSubscriptionUpdated` (and `deleted`), `stripe.subscriptions.retrieve(subscription.id)` and decide on the live status. Test: unit test "updated snapshot active but live subscription canceled -> no write".

### A7-PAY-06 - The withdrawal waiver is not required by the server, yet the confirmation email states the customer waived
- Severity: LOW. Confidence: CONFIRMED.
- Evidence: the waiver is recorded only by the client before calling the route: `components/profile/use-pro-checkout.ts:37` `postConsents(['withdrawal_waiver'])`. `app/api/stripe/checkout/route.ts:49-129` never reads `user_consents`; a direct `POST /api/stripe/checkout` creates the session without any waiver row. The waiver row is also not linked to the session/subscription (kinds only, `supabase/migrations/20261004120000_user_consents.sql:27`). The durable-medium email then asserts it unconditionally: `lib/email/templates/subscription-confirmation.ts:181-182` ("solicitaste expresamente que la prestación comenzara antes de que finalizara el plazo legal de desistimiento de 14 días").
- Impact: for a subscription started without the dialog, the business has no proof of the waiver (TRLGDCU art. 103.m needs prior express consent) and the email states something false, so the customer keeps the 14-day withdrawal right with a full refund. Low exposure (needs a hand-made request), but the evidence chain the legal design relies on (ADR-0040 / FRESCO-794) is not enforced.
- Reproduction: as a signed-in non-Pro user, `fetch('/api/stripe/checkout',{method:'POST'})` from the console -> 200 with a Stripe URL, no new `user_consents` row (not executed on production; read from code).
- Fix: in the checkout route, require a `withdrawal_waiver` row for the user created in the last N minutes (or record it server-side in the same request) and put its id in the session `metadata`; the email should cite it. Test: route test "no recent waiver -> 400".

### A7-PAY-07 - A paid checkout for a user without a `user_profiles` row is acknowledged as success and never grants Pro

### A7-PAY-09 - A transient failure while handling `charge.refunded` is answered 200 and nothing ever retries it: the refunded customer keeps the subscription and is charged again
- Severity: LOW (Sentry is notified; recovery is a manual dashboard resend). Confidence: CONFIRMED (code path).
- Evidence: any throw in a handler is caught and the route still answers 200 (`app/api/stripe/webhook/route.ts:182-198`), so Stripe does not redeliver; the claim is released, but only a manual resend would use it. For checkouts the cron sweep compensates (`lib/billing/checkout-sweep.ts`), for renewals/deletions the reconcile loop does; for refunds nothing does: `handleChargeRefunded` makes two network calls (`stripe.subscriptions.retrieve`, route.ts:369; `stripe.subscriptions.cancel`, route.ts:378) and the reconcile cron does not look at refunds.
- Impact: a customer who was refunded in full (the documented way to end their access, `docs/workflows/stripe-refunds.md`) stays Pro and is billed next cycle if Stripe or the network blipped during that one delivery.
- Reproduction: not executed. Unit-level: make `stripe.subscriptions.cancel` reject once in `route.test.ts` and observe the response is 200 with no retry path.
- Fix: answer 500 for transient errors (Stripe 5xx/connection/rate-limit, Supabase errors) so Stripe retries; handlers are already idempotent (the cancel can carry an idempotency key `refund-cancel:<charge.id>`). Keep 200 only for deterministic refusals. Test: route test "handler throws a StripeConnectionError -> 500 and claim released".

### A7-PAY-10 - Payment-failure grace has no app-side bound: a subscription left `past_due` keeps Pro indefinitely
- Severity: LOW. Confidence: PLAUSIBLE (depends on the Stripe dunning setting "if all retries fail", which is not readable here).
- Evidence: `supabase/functions/generate-meal-plan/entitlement.ts:35-38`: an expired `plan_expires_at` does not lapse while `payment_failed_at` is set; the reconcile cron keeps `past_due` as `pro` (`lib/stripe.ts:411-432`, `paymentFailed: true`). The webhook only downgrades on `unpaid` or `deleted` (`app/api/stripe/webhook/route.ts:248-255`, `303-319`); its comment covers "Cancel subscription" and "Mark uncollectible" but not Stripe's third option "leave the subscription past-due" (route.ts:249-254).
- Impact: if the dashboard is set (or reset in live mode) to leave subscriptions past-due, a customer whose card fails keeps Pro without paying, with no limit.
- Reproduction: not executed (needs a failing renewal). Read path above.
- Fix: bound the grace in the gate (`payment_failed_at` older than e.g. 21 days -> lapsed) and add the dunning setting to the go-live checklist (A7-PAY-08). Test: entitlement unit test "past_due for 30 days -> not entitled".
