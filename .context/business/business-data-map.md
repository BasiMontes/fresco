## 1. Executive Summary

### What does this system do?

Fresco turns "what do I cook this week?" into a generated weekly menu (21 meals) and an aisle-grouped shopping list in under 30 seconds, from a 3-step onboarding (`.context/PRD/mvp-scope.md` EPIC-FRESCO-1/2/4). Its defensible differentiator is not recipe content but **behavioral learning**: a lightweight "cooked / discarded" toggle per recipe that, for Pro subscribers only, feeds back into the next week's generation so the product measurably improves the longer a household uses it — a mechanism a stateless AI chat tool cannot replicate (`ADR-0001-behavioral-learning-moat.md`). Free tier delivers the full menu-generation promise every week but stays stateless by design; Pro (€4.99/mo) is sold specifically as "the product knows you better every week" (`.context/business/business-model.md` — Revenue Streams).

The product is pre-implementation: no `/project-bootstrap` has run, and only one database table (`recipes`) is actually live in Supabase today. Everything else described in this map — `user_profiles`, `meal_plans`, `meal_plan_recipes`, `shopping_lists`, all three Edge Functions, the learning trigger — is a specified design, not yet built code.

### Main Actors

| Actor | Description |
|---|---|
| Guest visitor | Unauthenticated first-time user; can generate exactly one menu without signing up (EPIC-FRESCO-6). |
| Free-tier registered user | Signed up, generates a fresh menu every week from scratch — no history is ever read into generation (ADR-0001). |
| Pro-tier registered user (€4.99/mo) | Same generation capability, plus the last-2-weeks cooked/discarded history is read into every generation, with a visible in-product explanation of what changed (FR-5.4, FR-5.5). |
| Founder (operator) | Runs the manual food-safety checklist before every concierge-stage menu delivery (FR-8.3), and manually curates/reviews each batch of AI-generated recipes before inserting them into the catalog (`fresco-core-tecnico.md` §4–5). |
| Gemini Flash (external system) | The only third-party service in the system; called for menu selection, shopping-list aisle classification, and (offline, founder-operated) batch recipe generation. |

### Value Proposition

- **Guest/Free**: a full week of realistic meals and a ready-to-shop grocery list, faster than doing nothing, at zero cost (`.context/PRD/user-personas.md` — Laura's willingness-to-pay threshold: under 60 seconds, saves 30+ minutes/week).
- **Pro**: the same, plus a menu that gets measurably better every week because it remembers what the household actually cooked versus discarded — the one thing a generic AI chat session cannot do without the user re-typing their history every session (`.context/business/market-context.md` — Competitive Landscape).
- **Founder**: a product whose entire personalization moat is enforced in one auditable place (a prompt-building `isPro` branch plus one SQL history fetch — ADR-0001, "Positive" consequences), keeping the implementation surface small enough for a solo, part-time founder to own.

### Entities and Their Business Role

| Entity | Status | Business Role | Why It Exists |
|---|---|---|---|
| `recipes` | **LIVE** — `schema_supabase.sql`, confirmed executed 2026-07-25, ~35 recipes seeded (`architecture.md` §4) | The shared catalog every menu is selected from; the JSONB shape (`meta`, `clasificacion`, `dieta`, `alergenos`, `ingredientes_principales`, `temporada`, `pasos_resumen`) mirrors the founder's conceptual recipe schema 1:1 (`fresco-core-tecnico.md` §1) | Recipes must exist independently of any one user so the same catalog can be filtered per-household and reused across every meal plan; a curated/photographed library was explicitly cut from MVP scope for cost reasons, so AI-generated + manually-reviewed catalog rows are the only source (`.context/PRD/mvp-scope.md` — Deferred to P1) |
| `user_profiles` | **Designed, not yet live** (`fresco-schema-sql.md` BLOQUE 3; column-shape decision deferred to `/project-bootstrap`, `architecture.md` §4) | The onboarding output: household size, diet flags, allergens, disliked ingredients, favorite cuisines, budget, time limits — the minimum input a menu generation call needs (FR-1.1) | One row per authenticated user (PK = `auth.users.id`) because every generation call and every SQL pre-filter is keyed to it; without it, `get_filtered_recipes()` has nothing to filter against |
| `meal_plans` | **Designed, not yet live** (`fresco-schema-sql.md` BLOQUE 4) | One row per user per ISO week — the container for a generated menu, its warnings, and its completion state | Separated from the 21 individual slots because plan-level metadata (`semana_iso`, `advertencias`, `completado`) is a property of the whole week, not of any single meal; `unique(user_id, semana_iso)` enforces FR-2.1's "no silent overwrite" rule (`architecture.md` §3.1 step 4) |
| `meal_plan_recipes` | **Designed, not yet live** (`fresco-schema-sql.md` BLOQUE 5) | A join table: one row per (day, meal-type) slot inside a plan, each carrying its own lifecycle state (`estado`) | This is a join table rather than a 21-element array column on `meal_plans` specifically **because each of the 21 slots needs its own independent state machine** (`pendiente → cocinada / descartada / sustituida`, FR-5.1) — a shared array column cannot express "this one slot is cocinada while the other 20 are still pendiente" without reinventing row-level semantics inside JSON. The `unique_slot` constraint on `(meal_plan_id, dia, tipo_plato)` (`fresco-schema-sql.md` BLOQUE 5) further requires per-slot addressability that only a real row gives you. |
| `shopping_lists` | **Designed, not yet live** (`fresco-schema-sql.md` BLOQUE 6) | One aisle-grouped shopping list per meal plan, stored as `items` jsonb | Deliberately **jsonb, not normalized**, per the founder's own reasoning: "es un artefacto que se genera, se consulta y se actualiza... no se cruza con otras tablas" (`fresco-schema-sql.md` — Notas Importantes) — unlike `meal_plan_recipes`, individual shopping items never need their own foreign-key relationships to other tables, only a targeted `jsonb_set` toggle on `comprado` (FR-4.4) |

### Key Relationships

- **`user_profiles` → `meal_plans` (1:N)**: every generation call is scoped to exactly one user and one ISO week; the FK plus the `unique(user_id, semana_iso)` constraint together are what make FR-2.1's `409` ("plan already exists for this week") enforceable at the database level, not just in application logic (`architecture.md` §3.1 step 4).
- **`meal_plans` → `meal_plan_recipes` (1:21, fixed)**: not a variable-length relationship — every valid plan has exactly 21 child rows (7 days × 3 meal types), enforced by FR-2.9's server-side validation before persistence, not by a DB constraint alone.
- **`recipes` → `meal_plan_recipes` (1:N)**: a recipe can be selected into many different users' plans; this is also the join surface the `recipe_learning_trigger` uses to feed aggregate statistics back onto `recipes` regardless of which user cooked or discarded it (global aggregation, FR-5.3).
- **`meal_plans` → `shopping_lists` (1:0..1)**: a shopping list is optional and generated on demand, not automatically — `generate-shopping-list` is a separate, independently-invoked Edge Function from `generate-meal-plan` (`architecture.md` §3.3), which is also why NFR-PERF-1's 30-second budget applies to menu generation alone, not the combined pitch-level promise (`non-functional-requirements.md` NFR-PERF-1).

**Flow Narrative:**

1. The user completes the 3-step onboarding, or an existing user requests a regeneration for a new ISO week (`.context/PRD/mvp-scope.md` EPIC-FRESCO-1/2).
2. The `generate-meal-plan` Edge Function authenticates the caller via a Supabase Auth JWT; missing/invalid returns `401` (`api-contracts.md` §0, §1).
3. The user's `user_profiles` row is loaded (`404` if not found).
4. The system checks no plan already exists for the requested `semana_iso` — `409` if one does, since regeneration is never a silent overwrite (`architecture.md` §3.1 step 4).
5. `get_filtered_recipes(user_id)` runs as a cheap SQL pre-filter: excludes any recipe whose `alergenos` overlaps the user's declared allergens, whose diet flags don't match active restrictions, or whose `ingredientes_principales` overlaps `ingredientes_odiados` — this is Layer 1 of the two-layer food-safety invariant (FR-8.1). If fewer than 21 recipes survive, the catalog is too small for this profile and the call fails with `422` (`architecture.md` §3.1 step 5).
6. **Pro tier only**: `get_recent_recipe_ids(user_id, weeks=2)` fetches the last-2-weeks cooked/discarded history. Free tier never calls this — `recentRecipeIds` stays `[]` by construction (FR-2.5, ADR-0001).
7. The backend builds a fixed system prompt plus a dynamically-built user prompt (profile + filtered catalog + history section) and calls Gemini Flash with `responseMimeType: 'application/json'`, `temperature: 0.7` (`fresco-edge-function-generate.md` — prompt.ts, index.ts step 7).
8. The raw model output is parsed and validated: JSON well-formed, `semana` matches the request, all 7×3 slots present, every `recipe_id` exists in the filtered catalog, no lunch/dinner repeat, breakfast repeats ≤ 3 (FR-2.9). Invalid output triggers a retry, up to `MAX_RETRIES = 2`; exhausting retries returns `502` and nothing is persisted (`api-contracts.md` §1, error table).
9. On success, a `meal_plans` row is inserted, then 21 `meal_plan_recipes` rows. Because Supabase Edge Functions have no native multi-table transaction, a failed second insert triggers a manual compensating delete of the orphaned `meal_plans` row — a documented reliability gap, not an oversight (`non-functional-requirements.md` NFR-REL-2; `architecture.md` §3.1 step 9).
10. The response is enriched with full recipe objects (not bare IDs) and returned to the frontend, which renders the editable calendar (`api-contracts.md` §1, `GenerateResponse`).

**Business Rules:**

- **Allergen and hated-ingredient exclusion is a hard, two-layer constraint** (SQL pre-filter + Gemini system-prompt "REGLAS ABSOLUTAS" rules 1–2) — neither layer is trusted alone, because a single leakage incident is a trust/safety failure, not an ordinary bug (FR-8.1, `ADR-0001` §Security Architecture, `non-functional-requirements.md` NFR-SEC-4).
- **Free tier structurally cannot see history** — `historial_semanas`/`recentRecipeIds` is never passed to the prompt for a Free user; this is the entire technical basis for the Free/Pro pricing distinction (FR-2.5, ADR-0001 Decision section: "no code path may pass Free-tier history into a generation prompt").
- **A non-empty `advertencias` array reporting an unmet mandatory filter is a P0 safety signal**, not a log line — it must trigger a prominent warning, never be silently discarded (FR-2.10, FR-8.2).
- **Budget is a hard ceiling**, computed as the sum of each selected recipe's `coste_estimado` bucket across all 21 slots (FR-2.6).
- **Quality rules are soft/best-effort**: category variety, seasonal preference, richness balancing, prioritizing high-`veces_cocinada`/`rating_promedio` recipes, avoiding `veces_descartada > 2` recipes unless no alternative exists, weekday/weekend time budgets, breakfast repeat cap of 3 (FR-2.8).

### Flow 2: Cooked / Discarded Feedback Loop (the learning mechanism)

```

calendar slot               (spec: fresco-aprendizaje.md)
     │                              │                          │                     │                  │
     │ 1. PATCH estado              │                          │                     │                  │
     ├──────────────────────────────▶                          │                     │                  │
     │                              │ 2. auth + verify slot     │                     │                  │
     │                              │    belongs to caller      │                     │                  │
     │                              │    (403 otherwise)        │                     │                  │
     │                              │ 3. reject if already      │                     │                  │
     │                              │    terminal (409)         │                     │                  │
     │                              │ 4. UPDATE estado ─────────▶                     │                  │
     │                              │                          │ 5. AFTER UPDATE      │                  │
     │                              │                          │    fires trigger ────▶                  │
     │                              │                          │                     │ 6. veces_cocinada │
     │                              │                          │                     │    or              │

     │                              │                          │                     │    promedio)  ─────▶
     │  7. { ok: true, estado }     │                          │                     │                  │
     │◀──────────────────────────────┤                          │                     │                  │
     ▼                                                                                                    │
  (if Pro: this history feeds Flow 1, step 6, on the user's NEXT generation)
```

**Flow Narrative:**

1. The user marks a calendar slot ✓ Cocinada, ✗ Descartar, or ↔ Cambiar, optionally with a 1–5 rating after marking cooked (`fresco-aprendizaje.md` — Flujo de feedback).
2. `update-recipe-status` authenticates the caller and verifies the slot's parent `meal_plan` belongs to them (join through `meal_plans.user_id`); mismatch returns `403` (`api-contracts.md` §4, error table).
3. A slot already `cocinada` or `descartada` is terminal and rejected with `409` — this is a one-way state boundary (FR-5.1).
4. `meal_plan_recipes.estado` (and `rating`, if present) is updated via a direct `UPDATE` (`fresco-aprendizaje.md` — Edge Function `update-recipe-status`).
5. The Postgres trigger `recipe_learning_trigger` fires `AFTER UPDATE` on `meal_plan_recipes` whenever `estado` actually changes (`fresco-schema-sql.md` BLOQUE 5).
6. On `cocinada`: `veces_cocinada += 1`, `ultima_vez_en_menu = today`, and if a rating was given, `rating_promedio` is recomputed as a running average. On `descartada`: `veces_descartada += 1`. On `sustituida`: **no statistics effect at all** — explicitly neutral (`fresco-aprendizaje.md`: "No afecta estadísticas — es neutral").
7. The Edge Function returns `{ ok: true, estado }`; the aggregate update is entirely the database trigger's responsibility, not the API's (`api-contracts.md` §4).

This recording path is **universal across every tier** — Free users' toggles are captured exactly the same way as Pro's. What differs is only *application*: only when a Pro user's *next* generation runs (Flow 1, step 6) does `get_recent_recipe_ids()` read this history back in (`architecture.md` — "Reading the diagram" note under §1).

**Business Rules:**

- **Recording is unconditional across every tier; application is Pro-only** — the single hardest-to-reverse bet in the architecture (FR-5.1, FR-5.4, `ADR-0001`).
- **Terminal states cannot be re-patched** — once `cocinada` or `descartada`, a slot is locked; `sustituida` is the one non-terminal outcome and can itself later transition to `cocinada`/`descartada` (see State Machines below).
- **Statistics are global, not per-user, by deliberate MVP-scale trade-off** — more robust with a small (8–10 user) concierge cohort than sparse per-user data would be; a future `user_recipe_stats` table is explicitly deferred to "Fase 2" (`fresco-schema-sql.md` — Notas Importantes; `architecture.md` §4).
- **A visible Pro-only explanation must accompany history-informed menus** — 2–3 warm, first-person-plural sentences, generated only when real history exists, never on a Pro user's first week (FR-5.5). This is the direct mitigation for the named risk that "the Free tier cannibalizes Pro conversion if learning isn't communicated" (`.context/business/market-context.md` — Risks).

```

**Flow Narrative:**

1. The user requests the shopping list for an existing `meal_plan_id`, typically right after menu generation or on first tap of "Ver lista de la compra" (`fresco-shopping-list.md` — LÓGICA GENERAL; `architecture.md` §3.3 step 1).
2. `generate-shopping-list` verifies the plan belongs to the caller (`404` otherwise) and that no list already exists for it (`409` — one list per plan, `unique_plan_lista`).
3. All 21 slots' recipes and their `ingredientes_principales` are loaded.
4. **Consolidation happens entirely in application code, never in the model**: ingredient names are normalized (lowercase, accent-stripped), looked up against a base-quantity table, scaled by `num_personas / raciones`, and duplicates merged by summing compatible units (`g`↔`kg`, `ml`↔`l` auto-convert; incompatible unit types are kept separate rather than silently merged) (`fresco-shopping-list.md` — `consolidator.ts`, FR-4.1).
5. Only the already-consolidated list — never raw per-recipe ingredients — is sent to Gemini Flash, which is instructed only to assign aisles and normalize display units, never to invent or drop items, at `temperature: 0.2` (classification, not creative generation) (`fresco-shopping-list.md` — prompt.ts).
6. The model's response is validated: `pasillos` array present, and the total item count is ≥ 90% of the consolidated input count; below that threshold, retry up to `MAX_RETRIES = 2` (FR-4.1, the 10% tolerance is explicitly to allow legitimate model-side near-duplicate merges, e.g. "ajo" + "ajo fresco" → "ajo").
7. The result is persisted to `shopping_lists.items` (jsonb), grouped into the fixed 13-aisle walking order, only including aisles with ≥1 item (FR-4.2), and returned to the frontend.
8. Individual items can later be marked purchased via a direct, targeted `jsonb_set` client call that bypasses the Edge Function entirely — not routed through backend orchestration (FR-4.4, `api-contracts.md` §3).

**Business Rules:**

- **The model never estimates quantities** — that arithmetic is deterministic application code, before the model is ever called (`fresco-shopping-list.md` — "Gemini no adivina cantidades — eso lo hacemos nosotros").
- **Units are normalized to a fixed vocabulary** — no ambiguous abbreviations (FR-4.3).
- **The 13-aisle order is fixed** and represents the logical walking path through a standard Spanish supermarket (FR-4.2).
- **An ingredient must never be silently dropped or invented** — enforced by the 90% retention check, not merely requested in the prompt (FR-4.1).

   ├─────────────────────────▶                                  │                    │                       │
   │                        │ 2. calls Gemini with               │                    │                       │
   │                        │    curation criteria ───────────────▶                    │                       │
   │                        │                                   │ 3. returns array   │                       │

   ▼                                                                                                            │
(this is what already produced the ~35 live rows; 6 tandas × ~30-50 each = ~230 target)
```

**Flow Narrative:**

1. The founder runs the batch recipe-generation prompt manually for one themed "tanda" (batch) at a time — 6 planned batches totaling ~230 recipes at launch (`fresco-core-tecnico.md` §4, "Estrategia de ejecución batch").
2. The prompt specifies curation criteria: Spanish/Latin home cooking only, mandatory category variety, ≥60% tupper-suitable, ≥40% under 30 minutes, minimum vegetarian/vegan/gluten-free counts, no haute cuisine or hard-to-source ingredients (`fresco-core-tecnico.md` §4).
3. Gemini returns a JSON array of recipe objects matching the `recipes` write shape (minus the `aprendizaje` block, since new recipes start at zero cooked/discarded/rated) (`api-contracts.md` §5).
4. The founder manually reviews the batch against an 8-point checklist: allergen accuracy against the 14 EU-regulated allergens, vegetarian/vegan/gluten-free flag correctness, `tiempo_total_min` internal consistency, Spain-market cost realism, category variety within the batch, `pasos_resumen` step-count limits (`fresco-core-tecnico.md` §5).
5. Corrections are made by hand if needed; nothing is inserted without this review.
6. Approved rows are inserted via the `service_role` key, bypassing RLS from the backend — never from the client (`fresco-schema-sql.md` — Notas Importantes; NFR-SEC-2).

This is the exact process that already produced the ~35 live, seeded recipes as of 2026-07-25 and will produce the remaining rows toward the ~230-recipe target (`architecture.md` §4; NFR-SCALE-2).

**Business Rules:**

- **This is a human-in-the-loop gate, not a live validation function** — the same manual-safety posture as the food-safety checklist (FR-8.3), existing independently of and prior to any code-level guarantee (`api-contracts.md` §5).
- **Recipe writes are `service_role`-only** — the client (Next.js app) never has write access to `recipes` (NFR-SEC-2).
- **Curated/photographed content was explicitly cut from MVP scope for cost reasons** — this batch process, plus manual review, is the deliberate substitute (`.context/PRD/mvp-scope.md` — Deferred to P1).

## 4. State Machines

### `meal_plan_recipes.estado` (`estado_receta_menu` enum: `pendiente | cocinada | descartada | sustituida`)

```
                     ┌─────────────┐
        (created) ──▶│  pendiente  │
                     └──┬───┬───┬──┘
                        │   │   │
          mark cooked   │   │   │  mark discarded
          ┌─────────────┘   │   └─────────────┐
          │                 │ change meal      │
          ▼                 ▼                  ▼
   ┌─────────────┐   ┌─────────────┐    ┌──────────────┐
   │  cocinada   │   │ sustituida  │    │  descartada  │
   │  (TERMINAL) │   │ (neutral,   │    │  (TERMINAL)  │
   └─────────────┘   │  not final) │    └──────────────┘
                      └──┬───┬─────┘
          mark cooked    │   │  mark discarded
          on new recipe  │   │  on new recipe
                         ▼   ▼
                  (loops back into cocinada / descartada
                   / another sustituida, per FR-5.1's
                   terminal-state rule)
```

**Transitions:**

| From | To | Triggering Event | Effects |
|---|---|---|---|
| `pendiente` | `cocinada` | User taps ✓ Cocinada, optional 1–5 rating | `recipe_learning_trigger` fires: `veces_cocinada += 1`, `ultima_vez_en_menu = today`, `rating_promedio` recomputed if rated (FR-5.3) |
| `pendiente` | `descartada` | User taps ✗ Descartar | `recipe_learning_trigger` fires: `veces_descartada += 1` (FR-5.3) |
| `pendiente` | `sustituida` | User taps ↔ Cambiar, supplies `nueva_recipe_id` | `recipe_id` updated to the new recipe; **no statistics effect** — explicitly neutral (FR-3.2, `fresco-aprendizaje.md`) |
| `sustituida` | `cocinada` | User later marks the substituted recipe cooked | Same trigger effect as `pendiente → cocinada`, now applied to `nueva_recipe_id` |
| `sustituida` | `descartada` | User later marks the substituted recipe discarded | Same trigger effect as `pendiente → descartada` |
| `cocinada` | *(none)* | — | **Terminal** — any further `update-recipe-status` call on this slot is rejected with `409` (FR-5.1) |
| `descartada` | *(none)* | — | **Terminal** — same `409` rejection (FR-5.1) |

**Business Rules:**

- `cocinada` and `descartada` are the only terminal states — the product treats a definitive "I cooked this" or "I skipped this" signal as final and immutable, which is what makes the aggregate statistics trustworthy (no double-counting via repeated toggling) (FR-5.1).
- `sustituida` is deliberately **not** terminal and **not** a statistics-affecting event — swapping a disliked meal is treated as normal calendar editing (EPIC-FRESCO-3), distinct from the learning signal captured by cocinada/descartada (FR-3.2).
- A `rating` (1–5) is only meaningful attached to `cocinada` and is always optional — the system must still learn from the unrated cocinada/descartada signal alone (FR-5.2).

No cron jobs or scheduled tasks are specified in any source document. Menu generation is always a synchronous, on-demand user-triggered call, and recipe-catalog seeding is a founder-operated manual batch process (Flow 4), not a scheduled job.

### Async Workers / Incoming Webhooks

None specified. There are no background workers, message queues, or incoming webhooks in any source document. All three system entry points (`generate-meal-plan`, `generate-shopping-list`, `update-recipe-status`) are synchronous, authenticated, request/response Edge Functions (`api-contracts.md` §0).

## 6. External Integrations

### Gemini Flash (Google Generative Language API)

```
                    ┌───────────────────────────┐
                    │   Fresco backend            │
                    │   (Supabase Edge Functions) │
                    └──┬────────────┬─────────┬───┘
                       │            │         │
        generate-meal- │  generate- │  batch  │ (founder-operated,
        plan            │  shopping- │  recipe │  offline, not a
        (menu selection)│  list      │  gen    │  live Edge Function)
                       │  (aisle     │         │
                       │  classify)  │         │
                       ▼            ▼         ▼
                 ┌─────────────────────────────────┐
                 │   Gemini Flash                    │
                 │   generativelanguage.googleapis.com│
                 │   (gemini-1.5-flash:generateContent)│
                 └─────────────────────────────────┘
```

**What it does:** the only third-party service in the system. Called for three distinct purposes: (1) selecting 21 recipes into a personalized weekly menu, `temperature: 0.7`, `responseMimeType: 'application/json'` (`fresco-edge-function-generate.md`); (2) classifying a pre-consolidated ingredient list into supermarket aisles and normalizing units, `temperature: 0.2` (`fresco-shopping-list.md`); (3) generating batches of new candidate recipes for the catalog, founder-operated and reviewed offline (`fresco-core-tecnico.md` §4).

**How it affects data:**

- `meal_plans` / `meal_plan_recipes`: populated from the validated output of call (1) — `architecture.md` §3.1 step 9.
- `shopping_lists.items`: populated from the validated output of call (2) — `architecture.md` §3.3 step 7.
- `recipes`: populated (after founder review) from the output of call (3) — Flow 4 above.

**Flows that depend on this:** Flow 1 (Weekly Menu Generation), Flow 3 (Shopping List Generation), and Flow 4 (Batch Recipe-Catalog Seeding) all call Gemini Flash directly; Flow 2 (Cooked/Discarded Feedback Loop) does not call it at all — that flow is pure database logic.

**Failure behavior:** every Gemini-calling path retries on invalid or malformed output, bounded at `MAX_RETRIES = 2` (`non-functional-requirements.md` NFR-REL-1). If the HTTP call itself fails (non-2xx from Gemini), `generate-meal-plan` returns `502` immediately without retrying the transport failure (`fresco-edge-function-generate.md` — index.ts: `if (!geminiResponse.ok) return errorResponse(...)`); if the call succeeds but returns invalid/unparseable JSON or fails output validation, up to 2 additional attempts are made before returning `502` to the caller. No menu or shopping list is ever persisted in a partial or invalid state — a failure surfaces as an explicit error, never a silently degraded result (`api-contracts.md` §1, §2 error tables). The Gemini API key (`GEMINI_API_KEY`) is stored exclusively as a Supabase Edge Function secret and is never exposed to the client (NFR-SEC-3).

## 7. Discovery Gaps

- **Guest-mode authentication mechanism is undefined.** EPIC-FRESCO-6 requires unauthenticated menu generation, but the founder's own Edge Function draft requires a Supabase Auth `Authorization` header and returns `401` when absent. No source document resolves how a guest session is represented (anonymous Supabase session, client-side-only path, guest-scoped token) — flagged in `.context/SRS/functional-requirements.md` FR-6.1 and `non-functional-requirements.md` NFR-SEC-1, carried forward here unresolved. This blocks a literal reading of Flow 1 for guest users until `/project-bootstrap` or Stage-1 story planning resolves it.
- **No `production` environment is yet defined** in `.agents/project.yaml` — only `local` and `staging` exist, both pointing at the same Supabase project ref (`architecture.md` §6, Deployment Topology).
- **The column-shape decision for the four not-yet-created tables (`user_profiles`, `meal_plans`, `meal_plan_recipes`, `shopping_lists`) is unresolved** — `fresco-schema-sql.md` specifies a strongly-typed relational design (enums, individual boolean columns) while the one table that *is* live (`recipes`, via `schema_supabase.sql`) uses a JSONB-flexible shape instead. Which shape the remaining four tables will follow — typed, jsonb, or a hybrid — is explicitly deferred to `/project-bootstrap` (`architecture.md` §4).
- **The `aprendizaje` learning columns (`veces_cocinada`, `veces_descartada`, `rating_promedio`, `ultima_vez_en_menu`) are absent from the live `recipes` table.** This is a required schema migration before `recipe_learning_trigger` (§5 above) or Flow 2/Flow 1-step-6 can function at all — `ADR-0001` is `Status: Proposed`, not yet operable, for exactly this reason (`architecture.md` §4).
- **No cron/webhook infrastructure is specified anywhere** in the source material — Section 5's empty Cron Jobs and Async Workers tables reflect the actual absence of any such requirement in the current design, not an incomplete discovery pass.
- **The fate of an unsaved guest-generated menu is unspecified** (discarded, retained temporarily, tied to a session) — named as an open gap in both `.context/PRD/functional-requirements.md`-equivalent FR-6.2 and `user-journeys.md` Journey 1.
- **No numeric latency target exists for `generate-shopping-list` alone** — only the qualitative expectation that it should be faster than menu generation, since it is classification-only against a smaller payload (`non-functional-requirements.md` NFR-PERF-2).
