## 1. Executive Summary

### What does this system do?

Fresco turns "what do I cook this week?" into a generated 21-slot weekly menu (7 days × desayuno/comida/cena) and an aisle-grouped shopping list, from a 3-step onboarding, in under a second. Its defensible differentiator is not recipe content but **behavioral learning**: a per-slot `cocinada`/`descartada` toggle that, for Pro subscribers only, feeds the next week's generation so menus measurably improve the longer a household uses the product (`.context/ADR/ADR-0001-behavioral-learning-moat.md`, `ADR-0006`, `ADR-0008`). The Free tier delivers the full menu-generation promise every week but stays stateless by construction; Pro (€4.99/month, 7-day trial, no card at signup) is sold specifically as "the product knows you better every week" (`.context/business/business-model.md` — Revenue Streams; `ADR-0007`).

**The system is fully built and running.** As of this pass the live Supabase project holds 1000 catalog recipes, 23 `user_profiles`, 23 `meal_plans` / 462 slots, 2 `shopping_lists`, 47 `auth.users` (43 of them anonymous guest sessions), 0 Pro subscribers. The backend is **7 deployed Supabase Edge Functions** plus **Next.js Route Handlers** for Stripe and data export; menu selection and shopping-list classification are **deterministic in-process algorithms — Gemini / any external LLM was fully removed from production on 2026-08-01** (`ADR-0005`; commits `c5dd2fc`, `ae3b560`). Active third-party vendors: Stripe (subscriptions), Sentry (errors), PostHog (analytics, EU), browser Web Push services, and Supabase Auth (including anonymous sign-in).

### Main Actors

| Actor | Description |
|---|---|
| Guest visitor | First-time user on a real Supabase **anonymous** session (`signInAnonymously()`, `ADR-0003`). Generates a full menu with no signup; can later convert to a permanent account keeping the same `user_id`. |
| Free-tier registered user | Signed-up user (`user_profiles.plan = 'free'`). Full menu generation every week; her cooked/discarded marks are recorded but never read back into her own generation (`ADR-0001`). |
| Pro / Family-tier user | `plan = 'pro'` or `'family'`. Same generation plus: last-2-weeks cooked/discarded marks excluded from the candidate pool, personal all-time engagement nudges scoring, and a first-person-plural "what we learned" explanation card (`ADR-0006`, `ADR-0008`). Set only by the Stripe webhook. |
| Founder / operator | Manually seeds the recipe catalog via `service_role` and can hard-delete a catalog recipe through an env-allowlisted admin surface (`ADMIN_USER_ID`, `supabase/functions/delete-catalog-recipe/index.ts`, `app/(app)/admin/recipes/page.tsx`, FRESCO-237). Also the recipient of Sentry alerts and PostHog KPI dashboards. |
| Scheduled jobs (`pg_cron`) | Two DB-native jobs: nightly abandoned-guest cleanup, and a weekly re-engagement web-push send that calls an Edge Function over HTTP via `pg_net` (`ADR-0011`). |
| Stripe (inbound) | Calls `POST /api/stripe/webhook` on subscription lifecycle events — the **only** writer of subscription state onto `user_profiles` (`ADR-0007`). |

### Value Proposition

- **Guest / Free**: a full week of realistic meals and a ready-to-shop grocery list with cost estimate, in seconds, at zero cost, no signup required.
- **Pro / Family**: the same, plus a menu that avoids what the household discarded, leans on what it cooked, and says so in plain language — a compounding signal a stateless AI chat tool cannot replicate without the user re-typing their history every week (`.context/business/market-context.md` — Competitive Landscape).
- **Founder**: the whole personalization moat is enforced in a few auditable places (one `isPro` branch in `generate-meal-plan`, three SECURITY DEFINER history functions, one DB trigger), and there is zero external AI API cost or dependency in the Free-tier core path.

### Entities and Their Business Role

| Entity | Business Role | Why It Exists |
|---|---|---|

JSONB-flexible shape: `meta` (`raciones`, `tiempo_total_min`, `dificultad`, `coste_estimado`), `clasificacion` (`cocina`, `categoria`, `tipo_plato`, `es_contundente`, `es_ligero`, `apto_tupper`), `dieta` (boolean flags), `alergenos` / `ingredientes_principales` / `temporada` (JSON arrays), plus flat aggregate learning columns. | Recipes must exist independently of any user so the same catalog is filtered per-household and reused across every plan. Curated/photographed content was cut from MVP scope; the catalog is AI-generated + manually reviewed, inserted via `service_role` only. Source: `supabase/migrations/20260725120100_create_fresco_core_tables.sql` (`get_filtered_recipes` adaptation), `20260725120000_add_aprendizaje_columns_to_recipes.sql`, live schema. |
| `user_profiles` | One row per `auth.users` id. Carries (a) onboarding output — diet flags, allergens, disliked/favorite ingredients, favorite cuisines, household size, budget, time limits, cooking experience, goal, `planning_selection` (per-day meals to plan); (b) **subscription state** — `plan`, `plan_expires_at`, `stripe_customer_id`, `stripe_subscription_id`, `payment_failed_at`; (c) **Centro de Avisos** dismissal flags. | Every generation call and every SQL pre-filter is keyed to this row. `id` is FK to `auth.users(id) ON DELETE CASCADE`, so it is also the cascade root for account deletion and guest cleanup. Source: `20260725120100`, `20260802000000`…`20260819124500`, `20260817090000_replace_planning_arrays_with_selection.sql`. |
| `meal_plans` | One row per user per ISO week — the container for a generated menu's plan-level metadata: `semana_iso`, `fecha_inicio`, `advertencias` (safety/quality warnings, text[]), `explicacion_aprendizaje` (Pro learning card text, nullable), `completado` (boolean, currently unused by any read path). | Plan-level metadata is a property of the whole week, not any single slot. `unique (user_id, semana_iso)` enforces FR-2.1's "no silent overwrite" — regeneration is a `409` until the plan is explicitly deleted. Source: `20260725120100`, `20260731130000_add_explicacion_aprendizaje_to_meal_plans.sql`. |
| `meal_plan_recipes` | One row per menu slot (up to 21 per plan). Holds `recipe_id` (nullable — `null` for an excluded slot or a slot with no safe recipe), `dia`, `tipo_plato`, `estado` (`estado_receta_menu` FSM), `rating` (1–5, optional). | A real join row per slot is required because **each slot needs its own independent state machine** — an array column on `meal_plans` cannot express "this slot is `cocinada` while the other 20 are `pendiente`". `unique (meal_plan_id, dia, tipo_plato)` gives per-slot addressability for the swap/mark flows. This is where the behavioral-learning signal is physically recorded. Source: `20260725120100`, `20260817090100_add_excluida_estado_receta_menu.sql`, `20260731150000_allow_null_recipe_id_for_unsafe_slots.sql`. |
| `shopping_lists` | One aisle-grouped list per meal plan. `items` jsonb = `[{ nombre (pasillo), orden, items: [{ nombre, cantidad, unidad, comprado }] }]`. `coste_estimado_min` / `coste_estimado_max` computed deterministically. `user_id` is denormalized (own column, not derived). | Deliberately jsonb, not normalized: a shopping item never needs its own FK relationships, only a targeted `jsonb_set` toggle on `comprado` and an append via `jsonb_add_item`. `unique (meal_plan_id)` = one list per plan. Source: `20260725120100`, `20260731100000_add_coste_estimado_to_shopping_lists.sql`, `20260814170000_add_jsonb_add_item_rpc.sql`. |
| `recetas_propias` | Personal recipes a user creates for her own library (name, `ingredientes` text[], `pasos` text[]). RLS `own`. | Lets a user keep her own recipes alongside the catalog. **Never read by `get_filtered_recipes()` or menu generation** — a deliberate exclusion: a personal recipe carries no food-safety metadata. Create/read since FRESCO-68; update/delete policies added FRESCO-236 (`20260821120000`, `20260821120100`). Source: `20260803000000_create_recetas_propias_table.sql`. |

### Key Relationships

- **`auth.users` → everything (1:N, `ON DELETE CASCADE`)** — deleting one `auth.users` row cascades through `user_profiles` → `meal_plans` → `meal_plan_recipes`, plus `shopping_lists`, `recetas_propias`, `favorites`, `push_subscriptions`. This is why both `delete-account` (FRESCO-70) and the `cleanup-abandoned-guest-users` cron job need only a single `auth.users` delete — no per-table cleanup.
- **`user_profiles` → `meal_plans` (1:N)** — every generation is scoped to one user + one ISO week; the FK plus `unique (user_id, semana_iso)` make FR-2.1's `409` enforceable at the DB layer.
- **`meal_plans` → `meal_plan_recipes` (1:≤21)** — a full plan has one row per slot the user chose to plan (`planning_selection` can exclude specific day/meal combos, producing an `excluida` slot). `recipe_id` is `ON DELETE RESTRICT` against `recipes`, which is why `delete-catalog-recipe` pre-checks references and returns `409` if any exist.
- **`recipes` ← `meal_plan_recipes` (aggregation surface)** — `recipe_learning_trigger` walks this edge to update global `veces_cocinada` / `veces_descartada` / `rating_promedio` on `recipes` regardless of which user cooked or discarded (deliberate global, not per-user, MVP-scale aggregation — `ADR-0001`). Per-user history is read separately via three SECURITY DEFINER functions.
- **`meal_plans` → `shopping_lists` (1:0..1)** — the list is generated on demand by `generate-shopping-list`, independent of `generate-meal-plan`. `shopping_lists.user_id` is its own column (denormalized) so `reassign_guest_data` has to move it explicitly.
- **`user_profiles.stripe_subscription_id` ↔ Stripe** — Stripe is the source of truth for subscription state; the `user_profiles` columns are a projection written only by the webhook. Out-of-order webhook deliveries are guarded by cross-checking the event's subscription id against the stored one.

## 3. Business Flows

### Flow 1: Guest Onboarding + Anonymous Session (the signup-free entry)

```
Visitor            /onboarding (client)        Supabase Auth           user_profiles
   │                     │                          │                       │
   │ 1. lands on /       │                          │                       │
   │    CTA → /onboarding│                          │                       │
   ├────────────────────▶│                          │                       │
   │                     │ 2. ensureGuestSession()  │                       │
   │                     │    if no session:        │                       │
   │                     │    signInAnonymously() ──▶│ 3. issue anon JWT     │
   │                     │◀─────────────────────────┤   (is_anonymous=true)  │
   │ 4. steps 1-3        │                          │                       │
   │    (diet / cuisines │                          │                       │
   │     / household)    │                          │                       │
   │                     │ 5. upsertUserProfile() ──┼──────────────────────▶│ insert profile
   │                     │ 6. generateMealPlan() ───┼──▶ (Flow 2)            │
   │ 7. → /menu          │                          │                       │
```

**Flow Narrative:**

1. Every landing-page CTA routes to `/onboarding` (signup-free entry, EPIC-FRESCO-6). `/signup` is kept only as the returning-user escape hatch.
2. On mount, `ensureGuestSession()` (`app/onboarding/page.tsx`) checks for any existing session; a registered user or returning guest keeps hers.
3. Otherwise `supabase.auth.signInAnonymously()` issues a **real Supabase Auth JWT** with `is_anonymous = true` and a real `auth.uid()` (`ADR-0003`). No Edge Function or RLS policy special-cases this — an anonymous session satisfies `requireAuthenticatedUser()` unmodified.
4. The 3-step wizard collects diet flags (vegano ⇒ vegetariano lock), allergens, disliked ingredients, favorite cuisines, and household size; a draft is persisted to `sessionStorage` (zustand `persist`) so a mid-wizard reload doesn't wipe answers.
5. `upsertUserProfile()` writes the `user_profiles` row (RLS `profiles_insert_own`, `auth.uid() = id`).
6. Completion kicks off `generate-meal-plan` (Flow 2), then routes to `/menu`.

**Business Rules:**

- **A guest's anonymous session IS her account** — logging out loses her menu irrecoverably, so `GuestLogoutDialog` gates a guest's logout with an explicit confirmation (FRESCO-90); a registered logout stays a single click.
- **Anonymous sign-in has a real, observed failure mode** — rate limiting (`rate_limit_anonymous_users` defaults to 30/hour on this project); surfaced as an inline error, not a silent hang (`ADR-0003`).
- Abandoned guests are cleaned up by cron after 3 days (see §5).

**Code Involved:**

- `app/onboarding/page.tsx` — `ensureGuestSession()`, the 3-step wizard, `handleGenerate()`.
- `lib/store/onboarding-store.ts` — draft persistence.
- `lib/api/user-profile.ts` — `upsertUserProfile()`.
- `supabase/functions/_shared/auth.ts` — `requireAuthenticatedUser()` (accepts anonymous JWTs).

### Flow 2: Weekly Menu Generation (the core promise — deterministic since ADR-0005)

```
Client              generate-meal-plan Edge Fn                Postgres
  │  POST {semana_iso, fecha_inicio} + JWT   │                    │
  ├─────────────────────────────────────────▶│                    │
  │                          1. requireAuthenticatedUser() — 401  │
  │                          2. load user_profiles ──────────────▶│ 404 if absent
  │                          3. reject if meal_plans row exists ──▶│ 409 for that week
  │                          4. get_filtered_recipes(user_id) ────▶│ SQL pre-filter
  │                             (allergen ∩, diet flags,          │ (FR-8.1 Layer 1)
  │                              disliked ∩); < 21 rows → 422     │
  │                          5. isPro?  ── yes ──▶ Promise.all([   │
  │                               get_recent_recipe_marks(2w),    │ Pro history
  │                               get_user_recipe_engagement() ]) │ (ADR-0006/0008)
  │                             ── no  ──▶ recentRecipeIds = []    │
  │                          6. selectMenu()  — deterministic      │
  │                             scored heuristic, in-process       │ (menu-selector.ts)
  │                             · cocinada/descartada last 2w      │
  │                               removed from candidate pool      │
  │                             · empty pool → NO_SAFE_RECIPE_     │
  │                               SENTINEL + advertencia           │
  │                          7. isPro & history → buildLearning    │
  │                             Explanation() — deterministic      │
  │                             template (no LLM)                  │
  │                          8. insert meal_plans ───────────────▶│
  │                          9. insert up to 21 meal_plan_recipes ▶│ on error:
  │                             (excluida for planning_selection   │ compensating
  │                              opt-outs, pendiente otherwise)    │ delete of plan
  │  10. enriched menu + advertencias +      │                    │ (NFR-REL-2)
  │      explicacion_aprendizaje             │                    │
  │◀─────────────────────────────────────────┤                    │
```

**Flow Narrative:**

1. Onboarding completion, `GenerateWeekButton` on `/calendar`, or a re-generation for a new ISO week calls `generate-meal-plan` with `{ semana_iso, fecha_inicio }`.
2–3. Auth, profile load (`404` if the user skipped onboarding), and the no-silent-overwrite check (`409` if a plan already exists — the user must delete it first, Flow 5b).
4. `get_filtered_recipes(user_id)` is **FR-8.1 Layer 1** — a SQL pre-filter that structurally removes any recipe whose `alergenos` overlaps the user's declared allergens (`?|` jsonb operator), whose active `dieta_*` flags aren't satisfied, or whose `ingredientes_principales` overlaps `ingredientes_odiados`. Fewer than 21 survivors → `422` (catalog too small for this profile — never a degraded menu).
5. **The Free/Pro fork.** For `plan in ('pro','family')` the function runs two concurrent SECURITY DEFINER reads: `get_recent_recipe_marks(user_id, 2)` (recipes the user personally marked `cocinada`/`descartada` in the last 2 weeks, `ADR-0006`) and `get_user_recipe_engagement(user_id)` (all-time personal cooked/discarded counts per recipe, `ADR-0008`). Free never calls either — `recentRecipeIds` stays `[]` by construction (`ADR-0001` invariant).
6. `selectMenu()` (`menu-selector.ts`) fills each slot with a deterministic scored heuristic: time-limit fit (weekday vs weekend), no lunch/dinner repeat within the week, breakfast repeat cap of 3, category/contundencia variety against the preceding slot, seasonal-match and rating/history bonuses, `veces_descartada > 2` soft penalty, personal-engagement nudge (Pro only), and a small jitter. Pro's recent `cocinada`/`descartada` recipes are **removed from the candidate pool before scoring** (a hard filter, not a prompt instruction — `ADR-0005`). A slot with an empty pool gets `NO_SAFE_RECIPE_SENTINEL` and a templated `advertencias` entry.
7. For Pro users with real history, `buildLearningExplanation()` produces 2–3 first-person-plural sentences from the recipe stats already in hand — **a deterministic template, not an LLM call** (the last Gemini call, removed 2026-08-01, `ae3b560`). `null` for Free and for a Pro user's first week.
8–9. Insert the `meal_plans` row, then the slot rows (`excluida` estado for day/meal combos the user opted out of via `planning_selection`, `pendiente` otherwise). Edge Functions have no multi-table transaction, so a failed slot insert triggers a manual compensating delete of the orphaned plan (NFR-REL-2).
10. The response enriches slots with full recipe objects and returns `advertencias` + `explicacion_aprendizaje`.

**Business Rules:**

- **Allergen / disliked-ingredient exclusion is a hard SQL constraint.** Since Gemini was removed there is no second semantic layer — `get_filtered_recipes()` is the single enforcement point, and it fails closed (`422`) rather than degrading (`ADR-0005`; `business-feature-map.md` FEAT-058, which flags this as now single-layer).
- **Free structurally cannot see history** — no code path passes Free-tier marks into `selectMenu()` (`ADR-0001`).
- **A non-empty `advertencias` entry is a P0 signal**, surfaced prominently on `/menu` and `/calendar` (`AlertBanner`), never silently dropped (FR-2.10, FR-8.2).
- **Sub-second latency** is the point of `ADR-0005` — the prior Gemini call ran 20–110 s (thinking-model latency), the live user complaint that triggered the rewrite.

**Code Involved:**

- `supabase/functions/generate-meal-plan/index.ts` — orchestration.
- `supabase/functions/generate-meal-plan/menu-selector.ts` — `selectMenu()`, `scoreRecipe()`.
- `supabase/functions/generate-meal-plan/prompt.ts` — `buildLearningExplanation()` (deterministic).
- `supabase/migrations/20260725120100_create_fresco_core_tables.sql` — `get_filtered_recipes()`.
- `supabase/migrations/20260808010000_replace_get_recent_recipe_ids_with_marks.sql`, `20260823170000_add_get_user_recipe_engagement.sql`, `.../add_get_user_recipe_engagement`, `get_user_cooked_recipe_ids` — Pro history reads.
- `lib/api/edge-functions.ts` — `generateMealPlan()`.

### Flow 3: Shopping List Generation (separate, on-demand, deterministic)

```
Client            generate-shopping-list Edge Fn        consolidator.ts / aisle-pricing.ts
  │  POST {meal_plan_id} + JWT   │                          (pure in-process, no LLM)
  ├─────────────────────────────▶│                              │

  │                  3. list already exists — 409               │

  │                     ingredientes_principales                 │
  │                  5. consolidateIngredientes() ──────────────▶│ scale by
  │                     · normalize names                        │ num_personas /
  │                     · scale by household size                │ raciones, merge
  │                     · sum compatible units (g↔kg, ml↔l)      │ compatible units
```

**Flow Narrative:**

1–3. Ownership check (`404`) and one-list-per-plan check (`409`, also backed by `unique_plan_lista`).
4. All planned slots' recipes and their `ingredientes_principales` (a plain name array) are loaded; servings come from `recipes.meta.raciones` (JSONB), defaulting to 4.
5. `consolidateIngredientes()` normalizes names (lowercase, accent-strip), scales by `num_personas / raciones`, and merges duplicates by summing compatible units — **entirely deterministic app code**. Empty result → `422`.
6. `classifyShoppingList()` assigns each item a supermarket aisle from a static map (the aisle classification **used to be a Gemini call — now a static map**, killed alongside menu selection: ingredient names are a controlled vocabulary, so a lookup table is a reliable zero-cost substitute) and a per-unit price, producing `coste_estimado_min`/`_max`.
7. Persisted to `shopping_lists.items` in fixed walking order, only aisles with ≥1 item.
8. Items can later be toggled purchased via `jsonb_set_comprado()` RPC (direct client call, bypasses the Edge Function) or an item added via `jsonb_add_item()` (from the favorites-based suggestions carousel, `get-shopping-list-suggestions`).

**Business Rules:**

- **The system never estimates quantities via a model** — deterministic base-quantity table (`fresco-shopping-list.md` heritage; `consolidator.ts`).
- **An ingredient is never silently dropped or invented** — consolidation is 1:1 with the recipes' declared ingredients.
- **13 fixed aisles in walking order** (FR-4.2).

**Code Involved:**

- `supabase/functions/generate-shopping-list/index.ts`, `consolidator.ts`, `aisle-pricing.ts`.
- `supabase/functions/get-shopping-list-suggestions/index.ts` — favorites-derived suggestions (FRESCO-194).
- `supabase/migrations/20260725120100_...` (`jsonb_set_comprado`), `20260814170000_add_jsonb_add_item_rpc.sql`.
- `lib/api/shopping-list.ts`.

### Flow 4: Cooked / Discarded Learning Loop (the moat's write path)

```
User taps ✓ / ✗ on a       update-recipe-status Edge Fn      meal_plan_recipes    recipe_learning_trigger    recipes
calendar slot                     │                               │                     │                       │
  │  POST {meal_plan_recipe_id,   │                               │                     │                       │
  │        estado, rating?} + JWT │                               │                     │                       │
  ├──────────────────────────────▶│                               │                     │                       │
  │              1. auth — 401     │                               │                     │                       │
  │              2. load slot + join meal_plans.user_id            │                     │                       │
  │              3. slot.user_id != caller → 403                   │                     │                       │
  │              4. estado already cocinada/descartada → 409       │                     │                       │
  │              5. UPDATE estado (+ rating / recipe_id) ─────────▶│ 6. AFTER UPDATE     │                       │
  │                                                                │    (old != new) ───▶│ 7. cocinada:          │
  │                                                                │                     │    veces_cocinada++   │
  │                                                                │                     │    ultima_vez_en_menu │
  │                                                                │                     │    rating_promedio    │
  │                                                                │                     │    (running avg)  ───▶│
  │                                                                │                     │  descartada:          │
  │                                                                │                     │    veces_descartada++ │
  │  8. { ok: true, estado }       │                               │                     │  sustituida: no-op    │
  │◀──────────────────────────────┤                               │                     │                       │
  │
  (if Pro: this history feeds Flow 2 step 5 on the user's NEXT generation)
```

**Flow Narrative:**

1. `CalendarGrid` check/X buttons call `update-recipe-status` with `{ meal_plan_recipe_id, estado, rating? }` (and `nueva_recipe_id` for `sustituida`).
2–3. The Edge Function joins the slot back to `meal_plans.user_id` and rejects `403` on mismatch — **the security-critical step**: without it any authenticated user could mutate any slot and pollute the global aggregate every Pro user's next generation reads.
4. A slot already `cocinada` or `descartada` is terminal — re-patch rejected `409` (prevents double-counting a signal).
5. A direct `UPDATE` on `meal_plan_recipes.estado` (and `rating` / `recipe_id`).
6–7. `recipe_learning_trigger` fires `AFTER UPDATE` when `old.estado != new.estado`: on `cocinada`, `veces_cocinada += 1`, `ultima_vez_en_menu = current_date`, `rating_promedio` recomputed as a running average if rated; on `descartada`, `veces_descartada += 1`; on `sustituida`, no statistics effect.
8. Response is `{ ok, estado }` — the aggregate update is the DB's responsibility, not the API's, so it fires identically regardless of which future caller performs the `UPDATE`.

**Business Rules:**

- **Recording is unconditional across every tier; application is Pro-only** (`ADR-0001`). Free users' toggles are captured identically; only a Pro user's next generation reads them back (Flow 2 step 5). A `learning_free_tier_notice` on the calendar frames this as upsell.
- **`cocinada` / `descartada` are terminal; `sustituida` is neutral and non-terminal.** (See §4.)
- **Aggregate stats are global, not per-user** — deliberate MVP-scale trade-off (`ADR-0001`). Per-user history is read separately (`ADR-0006`, `ADR-0008`).

**Code Involved:**

- `supabase/functions/update-recipe-status/index.ts`.
- `supabase/migrations/20260725120200_create_recipe_learning_trigger.sql` — `update_recipe_learning()` + trigger.
- `components/calendar/calendar-grid.tsx` — the ✓/✗ buttons and `learning_free_tier_notice`.

### Flow 5a: Calendar Slot Swap (learning-neutral, bypasses the trigger)

```
User drags a slot onto another slot of the SAME tipo_plato
  │  supabase.rpc('swap_meal_plan_slots', { p_slot_a_id, p_slot_b_id })
  ▼
swap_meal_plan_slots()  (SECURITY DEFINER, ADR-0002)
  1. both slots found, same meal_plan_id, same tipo_plato (else raise)
  2. caller owns the plan (auth.uid() check — DEFINER bypasses RLS)
  3. ALTER TABLE meal_plan_recipes DISABLE TRIGGER recipe_learning_trigger
  4. swap (recipe_id, estado, rating) between the two rows
  5. ENABLE TRIGGER  (same txn — a mid-function error rolls back the disable)
```

**Why:** a position swap must never change any recipe's learning state. Swapping the full `(recipe_id, estado, rating)` bundle is the correct data model but makes the trigger fire spuriously (double-counting an already-recorded cook), so the trigger is explicitly disabled for that one transaction (`ADR-0002`). Cross-`tipo_plato` drops are rejected both client-side and in the RPC (`20260801000000_restrict_slot_swap_to_same_tipo_plato.sql`). Optimistic local swap, background persist, revert-on-failure (`components/calendar/calendar-grid.tsx`).

### Flow 7: Pro Subscription Lifecycle (Stripe Checkout + webhook-driven state)

```
/profile  "Pásate a Fresco Pro"
   │  POST /api/stripe/checkout  (server-side Supabase session)
   ▼
Next.js Route Handler → stripe.checkout.sessions.create({
     mode: 'subscription', price = STRIPE_PRICE_ID_PRO_MONTH,
     subscription_data: { trial_period_days: 7 },
     payment_method_collection: 'if_required',
     client_reference_id = auth.uid() })
   │  returns session.url  →  client redirects to Stripe-hosted page
   ▼
Stripe  ──(events)──▶  POST /api/stripe/webhook   (Stripe-signature verified,
                       per-env secret via resolveWebhookSecret())
   │
   ├─ checkout.session.completed
   │    · verify subscription price == STRIPE_PRICE_ID_PRO_MONTH (else refuse Pro)
   │    · service_role UPDATE user_profiles SET plan='pro',
   │      stripe_customer_id, stripe_subscription_id,
   │      plan_expires_at = trial_end, payment_failed_at = null
   │    · idempotent: skip PostHog subscription_started if sub id unchanged
   │
   ├─ customer.subscription.updated
   │    · out-of-order guard: match BOTH stripe_customer_id AND subscription id
   │    · status active   → plan='pro', plan_expires_at = current_period_end,
   │                        payment_failed_at = null   (renewal / recovered)
   │    · status past_due → payment_failed_at = now()  (plan untouched — "grace")
   │    · status unpaid   → plan='free', payment_failed_at = null  (dunning exhausted)
   │    · cancel_at_period_end=true + still active → treated as normal active (keeps Pro)
   │
   └─ customer.subscription.deleted
        · out-of-order guard (same)
        · plan='free', payment_failed_at = null
```

**Business Rules:**

- **The webhook is the ONLY writer of subscription state** (`plan`, `plan_expires_at`, `stripe_customer_id`, `stripe_subscription_id`, `payment_failed_at`). Client writes to those columns are blocked by the `prevent_client_subscription_writes()` BEFORE UPDATE trigger, which allows only `auth.role() = 'service_role'` (`ADR-0007`; `20260818190000`, `20260819121500`).
- **Cancellation only takes effect when the paid period ends** (`customer.subscription.deleted`), not when the user requests it.
- **After signature verification, a downstream failure logs + still returns 200** — a non-2xx makes Stripe retry a bug; manual replay from the Stripe dashboard is the recovery path.
- **`/api/stripe/portal`** (manage/cancel) requires `plan = 'pro'` AND a stored `stripe_customer_id` — a downgraded user with a stale customer id is refused `404`.
- **Do not add a parallel `subscriptions` table** without superseding `ADR-0007`.

**Code Involved:** `app/api/stripe/checkout/route.ts`, `app/api/stripe/portal/route.ts`, `app/api/stripe/webhook/route.ts`, `lib/stripe.ts` (pure mappers + `resolveWebhookSecret()`), `lib/supabase/service.ts`, `supabase/migrations/20260818180000_add_stripe_columns_to_user_profiles.sql`, `20260818190000`, `20260819120000_add_payment_failed_at_to_user_profiles.sql`, `20260819121500`.

## 4. State Machines

### `meal_plan_recipes.estado` — `estado_receta_menu` (`pendiente | cocinada | descartada | sustituida | excluida`)

```
   (generation, planning_selection opt-out) ──▶ ┌──────────┐
                                                 │ excluida  │  (terminal — user chose
                                                 └──────────┘   not to plan this slot;
                                                                recipe_id = null)

   (generation, normal slot) ──▶ ┌────────────┐
                                  │ pendiente   │
                                  └──┬───┬───┬──┘
                mark cooked  ┌───────┘   │   └───────┐  mark discarded
                             ▼           ▼           ▼
                     ┌────────────┐ ┌────────────┐ ┌──────────────┐
                     │  cocinada   │ │ sustituida  │ │  descartada  │
                     │ (TERMINAL)  │ │ (neutral,   │ │  (TERMINAL)  │
                     └────────────┘ │  non-final) │ └──────────────┘
                                    └──┬────┬─────┘
                     mark cooked ──────┘    └────── mark discarded
                     (on new recipe)              (on new recipe)
                             ▼                            ▼
                        cocinada                     descartada

   NOTE: a drag-and-drop position swap (swap_meal_plan_slots) also moves
   (recipe_id, estado, rating) between two same-tipo_plato slots WITHOUT
   firing recipe_learning_trigger — see Flow 5a / ADR-0002.
```

**Transitions:**

| From | To | Triggering Event | Effects |
|---|---|---|---|
| *(generation)* | `pendiente` | Slot created in `generate-meal-plan` | Normal starting state |
| *(generation)* | `excluida` | Day/meal combo not in `user_profiles.planning_selection` (FRESCO-199) | `recipe_id = null`; slot renders as "no planeado", not draggable |
| `pendiente` | `cocinada` | `update-recipe-status` ✓, optional 1–5 `rating` | `recipe_learning_trigger`: `veces_cocinada += 1`, `ultima_vez_en_menu = current_date`, `rating_promedio` recomputed if rated |
| `pendiente` | `descartada` | `update-recipe-status` ✗ | `recipe_learning_trigger`: `veces_descartada += 1` |
| `pendiente` | `sustituida` | `update-recipe-status` with `estado='sustituida'` + `nueva_recipe_id` | `recipe_id` updated; **no statistics effect** (trigger no-ops on `sustituida`). *No live UI trigger for this path was found — the Edge Function accepts it but the calendar uses drag-swap instead (see §7).* |
| `sustituida` | `cocinada` / `descartada` | Later mark on the substituted recipe | Same trigger effect as from `pendiente`, applied to the new `recipe_id` |
| `cocinada` | *(none)* | — | **Terminal** — further `update-recipe-status` → `409` |
| `descartada` | *(none)* | — | **Terminal** — `409` |

**Business Rules:** `cocinada`/`descartada` are the only terminal states — a definitive signal is final and immutable, which keeps the aggregate counters trustworthy. `sustituida` is deliberately non-terminal and statistics-neutral. `rating` is only meaningful on `cocinada` and always optional.

```
                         checkout.session.completed

             │                                                  │ (past_due)
             │                                                  ▼
             │                              ┌───────────────────────────────────┐
             │  subscription.updated        │  pro + payment_failed_at = now()   │
```

**Transitions:**

| From | To | Event | Effects |
|---|---|---|---|
| `free` | `pro` (trial) | `checkout.session.completed`, price == Pro | `plan='pro'`, `stripe_customer_id`, `stripe_subscription_id`, `plan_expires_at = trial_end`, `payment_failed_at = null`; PostHog `subscription_started` (once) |
| `pro` | `pro` | `customer.subscription.updated`, `status='active'`, price OK | `plan_expires_at = current_period_end`, `payment_failed_at = null` |
| `pro` | `pro` + `payment_failed_at` | `...updated`, `status='past_due'` | `payment_failed_at = now()`; `plan` untouched (Stripe's own retry window is the grace period) |
| `pro` + failed | `pro` | `...updated`, `status='active'` | `payment_failed_at = null` (retry succeeded) |
| `pro` (± failed) | `free` | `...updated` `status='unpaid'`, OR `customer.subscription.deleted` | `plan='free'`, `payment_failed_at = null` |

**Business Rules:** all transitions are webhook-only (`ADR-0007`). Price is re-verified on activation and renewal — any non-Pro subscription is refused a Pro grant. Out-of-order deliveries are guarded by matching the event's subscription id against the stored one.

| `ON DELETE CASCADE` chains | Any `auth.users` delete (`delete-account`, guest-cleanup cron) | `user_profiles` → `meal_plans` → `meal_plan_recipes`; `shopping_lists`; `recetas_propias`; `favorites`; `push_subscriptions` | Full removal of a user's data footprint from one delete |
| `web-push` outbound | `send-weekly-reengagement-push` per subscription | VAPID-signed, `aes128gcm`-encrypted payload to each browser's push service endpoint | `push_subscriptions` row cleanup on dead-endpoint responses |

## 6. External Integrations

### Stripe (subscriptions)

```
   Client ──▶ POST /api/stripe/checkout ──▶ stripe.checkout.sessions.create() ──▶ Stripe-hosted page
   Client ──▶ POST /api/stripe/portal   ──▶ stripe.billingPortal.sessions.create()
   Stripe ──(events, signed)──▶ POST /api/stripe/webhook ──▶ service_role UPDATE user_profiles
```

**What it does:** the entire Pro subscription — hosted Checkout (`subscription` mode, 7-day trial, no card at signup), the Billing Portal (manage/cancel), and the webhook that projects Stripe's subscription state into `user_profiles`.
**How it affects data:** the webhook is the only writer of `user_profiles.plan` / `plan_expires_at` / `stripe_customer_id` / `stripe_subscription_id` / `payment_failed_at`.
**Flows that depend on this:** Flow 7 (lifecycle), Flow 2 step 5 (the Free/Pro fork reads `plan`), Flow 8 (payment-failed notice).
**Failure behavior:** Checkout/Portal creation failure → `500` with a user-facing message, no state change. Webhook signature failure → `400`, nothing written. Webhook downstream failure (after signature) → logged + `200` (no retry storm); recovery is manual replay from the Stripe dashboard. A missed webhook leaves `user_profiles` drifted from Stripe with **no reconciliation job** (see §7). Secrets: `STRIPE_SECRET_KEY`, `STRIPE_PRICE_ID_PRO_MONTH`, `STRIPE_WEBHOOK_SECRET_{DEV,PRE,PROD}` (per-env, `resolveWebhookSecret()`).

### PostHog (product analytics, EU Cloud)

```
   Client (posthog-js provider)  ──events──▶  PostHog EU
   Server (posthog-node, lib/posthog/server.ts, Stripe webhook)  ──events──▶  PostHog EU
```

**What it does:** makes the North-star KPI ("menús generados Y usados") and the 3-week repeat-usage hypothesis measurable (`ADR-0013`, FRESCO-240). Events: `menu_generation_started/completed`, `recipe_marked_cooked`, `user_signed_up`, `session_started`, `subscription_started`.
**How it affects data:** **no app-DB writes.** `identify()` is keyed on Supabase `auth.uid()` including guests, so a guest's pre-signup stream merges into her post-signup stream (`alias()` on the reassignment path).
**Flows that depend on this:** none functionally — analytics only. Autocapture is off (would scrape allergen/diet UI text).
**Failure behavior:** every capture is a silent no-op on failure or when `NEXT_PUBLIC_POSTHOG_KEY` is unset — an analytics outage never surfaces as an app error. Secrets: `NEXT_PUBLIC_POSTHOG_KEY`, `NEXT_PUBLIC_POSTHOG_HOST`.

### Sentry (error tracking, client/server/edge)

**What it does:** unhandled-error capture across all three Next.js runtimes via `instrumentation.ts` (`onRequestError`) + `sentry.{server,edge}.config.ts` + `instrumentation-client.ts`, plus production source-map upload via `withSentryConfig` (`ADR-0009`, FRESCO-242). Free tier, low `tracesSampleRate`, replay off.
**How it affects data:** no app-DB writes; outbound error events only.
**Failure behavior:** degraded observability only — the app is unaffected. If `SENTRY_AUTH_TOKEN` is absent, source-map upload silently fails and production stack traces stay minified. Secrets: `NEXT_PUBLIC_SENTRY_DSN`, `SENTRY_ORG`, `SENTRY_PROJECT`, `SENTRY_AUTH_TOKEN`.

### Browser Web Push services (FCM / Mozilla / Apple / …)

**What it does:** delivery endpoint for the weekly re-engagement notification (Flow 9). One outbound POST per `push_subscriptions` row.
**How it affects data:** `404`/`410` responses delete the corresponding `push_subscriptions` row (the only automatic writer of that table besides user opt-out).
**Flows that depend on this:** Flow 9 only.
**Failure behavior:** per-subscription — a transient 5xx/timeout logs and skips (row kept); a dead endpoint is pruned. One bad send never aborts the batch. Secrets: `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT` (Edge Function secrets).

### Supabase Auth (including Anonymous Sign-In)

**What it does:** the sole identity provider — email/password, anonymous (guest), password recovery, email-change OTP, `admin.deleteUser()`. Anonymous sign-in must stay enabled (`external_anonymous_users_enabled`, set via Management API, `ADR-0003`) or Guest Mode breaks.
**How it affects data:** `auth.users` is the cascade root for every user-owned table. `is_anonymous` gates the guest-cleanup cron and `reassign-guest-data`.
**Failure behavior:** anonymous sign-in is rate-limited (default 30/hour) — surfaced inline. Email delivery for OTP/recovery hits Supabase free-tier rate limits and rejects non-standard domains (`ADR-0003` — a named risk for the guest-upgrade path).

### Removed: Gemini / external LLM

`business-model.md` and pre-2026-08 maps described Gemini doing menu selection, aisle classification, and the Pro explanation text. **All three were replaced with deterministic in-process code on 2026-08-01** (`ADR-0005`, commits `c5dd2fc` / `ae3b560`). There is **zero external AI API dependency in the production system.** `recipes` catalog seeding was also historically Gemini-assisted but is an offline, manually-reviewed founder process, not a runtime integration.

## 7. Discovery Gaps

> Written even where the answer is "verified clean".

- **`delete-catalog-recipe` Edge Function is not deployed.** It is merged in the repo (FRESCO-237, PR #122) and wired from `app/(app)/admin/recipes/page.tsx` via `lib/api/edge-functions.ts`, but `mcp__supabase__list_edge_functions` for `jdqemhewjrjuopssdurn` returns only 7 functions and does not include it. Either it was never deployed, or it is deployed outside the tracked mechanism. Admin catalog delete therefore may not actually work in any live environment. **Verify deploy status.**
- **No OpenAPI spec exists.** The API contract lives in hand-maintained `api/schemas/*.types.ts` (`bun run api:sync` regenerates from `scripts/sync-openapi.ts`) plus `.context/SRS/api-contracts.md`. `business-api-map.md` treats those as the contract source.
- **No rate limiting on `generate-meal-plan` / `generate-shopping-list`.** SRS `NFR-SEC-6`, owned by `FRESCO-243` (branch `feat/FRESCO-243-rate-limiting-generacion-menu`, unmerged; carries an unmerged `rate_limits` table migration). No ADR, no mechanism chosen. Low risk at concierge scale, real cost/abuse exposure before public launch.
- **Subscription state has no reconciliation job.** `ADR-0007` accepts webhook-driven state as the single write path; a missed/failed webhook drifts `user_profiles` from Stripe with no scheduled re-sync. A `pg_cron` reconcile against the Stripe API is a candidate.
- **All three environments share one Supabase project** (`jdqemhewjrjuopssdurn`) — `local`, `staging` (`fresco-pre.vercel.app`), `production` (`fresco-pro.vercel.app`) all point at the same ref (`.agents/project.yaml` `environments:`, deliberate per `master-implementation-plan.md` §3). There is no data isolation between test and production traffic; the 23 profiles / 43 guests in the DB are a mix.
- **`lib/urls.ts` is stale on environment topology.** It still throws on `VERCEL_ENV=production` and only knows `local` / `staging`, while `.agents/project.yaml` now has a `production` block and `_shared/cors.ts` + `lib/stripe.ts` reference a fourth environment, `fresco-dev.vercel.app` (`dev` branch), that is not in `project.yaml` `environments:` at all. Environment resolution is inconsistent across these three files.
- **Duplicate aviso columns on `user_profiles`.** The code (`lib/api/user-profile.ts`) reads/writes `aviso_bienvenida_visto` / `aviso_rutas_descartado` (migrations `20260818090000` / `20260818100000`). The live schema **also** carries `centro_avisos_bienvenida_vista` / `centro_avisos_rutas_descartado` (same "FRESCO-224/225" comments) which no code path references — apparently dead columns from an earlier attempt.
- **0 Pro / Family subscribers in the live DB.** Every Pro-only path — `ADR-0006`/`ADR-0008` personal-history scoring, `explicacion_aprendizaje`, `get_user_recipe_engagement`, the Billing Portal, the payment-failed notice — is untested against real production data.
- **`meal_plans.completado` is written at insert (default `false`) but no read path consumes it** — likely a vestigial FR-2 field. `advertencias` and `explicacion_aprendizaje` are correctly kept as separate fields (distinct UI components).
- **No live UI trigger for the `sustituida` estado.** `update-recipe-status` accepts `estado='sustituida'` with `nueva_recipe_id`, but the calendar uses drag-and-drop `swap_meal_plan_slots` for reordering, and no component was found that issues the `sustituida` call. The state, the enum value, and the trigger no-op all exist; the entry point may be dead or planned.
- **The weekly-push job depends on a manually-created Vault secret** (`edge_function_secret_key`). `cron.job` shows the schedule and header wired, but this pass could not verify the secret's presence — if absent, the job runs and each send silently 401s.
- **PRD/SRS are partially stale vs. code** (Gemini still described as present in several FRs; `FR-8.1` two-layer guardrail is now one layer). Not regenerated here — noted for a `/project-foundation` pass. `.context/SRS/non-functional-requirements.md` §7 (Observability) was added by FRESCO-284 and is current.
- **`recetas_propias` UPDATE/DELETE**: RLS policies + grants were added (FRESCO-236, `20260821120000` / `20260821120100`), so the table now supports it; whether the recipe-detail UI exposes edit/delete was not verified this pass (`business-feature-map.md` 2026-08-07 still lists it as out of scope).
