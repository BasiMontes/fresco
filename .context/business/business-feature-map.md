- [ ] Enforce `409` — no silent overwrite of an existing plan for the requested `semana_iso`
- [ ] Enforce `422` — fail explicitly when fewer than 21 recipes survive the pre-filter

| Aspect | Value |

## 4. API Endpoint Inventory

There is no conventional HTTP REST API in this system — the entire backend surface is three authenticated Supabase Edge Functions (Deno runtime, separate from the Next.js/Vercel frontend) plus two direct-to-Postgres client calls that bypass the Edge Function layer entirely. All three Edge Functions are invoked via `POST` (Supabase Edge Functions are invoked, not GET-routed) even where the semantic verb is conceptually a PATCH.

| Method | Endpoint | Purpose | Auth | Handler (spec doc — no code exists) |
|---|---|---|---|---|
| `POST` | `/generate-meal-plan` | Orchestrates FEAT-002 through FEAT-006, FEAT-015, FEAT-016, FEAT-020–022: generates the 21-meal weekly menu | Required — `Authorization: Bearer <supabase-jwt>`; `401` if missing/invalid. **Guest-mode caller path unresolved (FEAT-018).** | `api-contracts.md` §1; `fresco-edge-function-generate.md` (`index.ts`/`prompt.ts`/`validator.ts`) |
| `POST` | `/generate-shopping-list` | Orchestrates FEAT-009–011: consolidates ingredients (pure code) then classifies aisles via Gemini | Required — same Bearer JWT scheme | `api-contracts.md` §2, §2a, §2b; `fresco-shopping-list.md` (`index.ts`/`consolidator.ts`/`prompt.ts`) |
| `POST` (semantic PATCH) | `/update-recipe-status` | Orchestrates FEAT-013: cooked/discarded/substituted state transition | Required — same Bearer JWT scheme | `api-contracts.md` §4; `fresco-aprendizaje.md` (`index.ts`) |
| n/a (direct Supabase client call) | `shopping_lists.update()` → `jsonb_set_comprado()` RPC | FEAT-012: targeted `comprado` boolean toggle | Required — RLS-scoped, `security definer` function | `api-contracts.md` §3; `fresco-shopping-list.md` |
| n/a (founder-operated, offline) | Manual Gemini prompt → `recipes` insert | FEAT-024: batch recipe-catalog seeding | `service_role` key, bypasses RLS, never from the client | `api-contracts.md` §5; `fresco-core-tecnico.md` §4–5 |

**Error shape** (all three Edge Functions, per `api-contracts.md` §0): every non-2xx response is `{ "error": string }`. Common statuses: `400` validation, `401` unauthorized, `403` forbidden, `404` not found, `409` conflict, `422` unprocessable, `502` upstream/LLM failure, `500` internal. `OPTIONS` preflight is handled for CORS (dev-time `Access-Control-Allow-Origin: *`, not scoped further for production in any source document).

## 8. Discovery Gaps

This entire map is **spec-level, not code-verified** — built from PRD/SRS/founder-technical-doc cross-reference, because no `/project-bootstrap` has run and no application code exists anywhere in this repository. Every "Evidence" citation above points to a specification section, never a `file:line` code reference, because no such reference can exist yet. **Recommended action: re-run `/business-feature-map` after `/project-bootstrap` scaffolds the codebase and after the first 1–2 `/sprint-development` cycles land real Edge Function / frontend code**, to re-validate every Planned status against actual implementation and to catch drift between what was specified here and what got built.

Top gaps, most actionable first:

1. **Guest-mode authentication mechanism is genuinely unresolved (FEAT-018, blocks EPIC-FRESCO-6 entirely).** The founder's own `generate-meal-plan` Edge Function draft hard-requires a Supabase Auth Bearer JWT and returns `401` when absent — but EPIC-FRESCO-6 requires unauthenticated generation. No source document (PRD, SRS, or founder technical brief) resolves whether guests get an anonymous Supabase session, a client-side-only generation path, or a guest-scoped token. **Ask**: the founder, before `/project-bootstrap` scaffolds auth — this blocks a literal implementation of Journey 1 (Guest Happy Path) as currently specified.
2. **The column-shape decision for the four not-yet-created tables (`user_profiles`, `meal_plans`, `meal_plan_recipes`, `shopping_lists`) is unresolved**, and it affects every "Planned" feature's eventual implementation shape. The one live table (`recipes`) uses a JSONB-flexible shape; the founder's fuller design doc (`fresco-schema-sql.md`) specifies a strongly-typed relational shape for the other four. **Ask**: `/project-bootstrap`, per `architecture.md` §4's own explicit deferral.
3. **The `recipes` learning columns (`veces_cocinada`, `veces_descartada`, `rating_promedio`, `ultima_vez_en_menu`) are confirmed absent from the live table.** FEAT-014, FEAT-004, FEAT-015, and FEAT-016 — the product's entire behavioral-learning moat (ADR-0001) — are inert until this migration runs. Not an oversight in this map; a required, named, pre-launch blocker.
4. **No `recipes` DELETE capability is specified anywhere**, despite the CRUD matrix cross-check (§3) surfacing it as a real gap. Given recipes are seeded via a manual, reviewed batch process (FEAT-024), a deprecation/removal path (e.g. a bad recipe slipping past review) has no documented mechanism. **Ask**: the founder — is this deliberate (recipes are append-only) or an oversight?
5. **No `meal_plans` DELETE endpoint is documented, yet the founder's own Edge Function error copy implies one exists** ("Ya existe un plan para la semana… Elimínalo antes de regenerar" — "delete it before regenerating"). This is a real inconsistency between UX copy and the documented API surface, not a hypothetical gap. **Ask**: the founder — where does this deletion happen, and should it be a fourth Edge Function or a direct client call like FEAT-012?
6. **No `user_profiles` UPDATE path is specified anywhere.** Once onboarding completes, there is no documented way for a user to edit their diet flags, allergens, budget, or household size — all real, expected user needs (diets and households change) with no owning epic or FR. **Ask**: product — is this deliberately deferred past MVP, or a gap in the SRS pass?
7. **The fate of an unsaved guest-generated menu is unspecified (FR-6.2)** — discarded, retained temporarily, or session-tied. Directly affects FEAT-018 and FEAT-019's implementation scope. Already flagged in `user-journeys.md` and `business-data-map.md`; carried forward unresolved here too.
8. **DESIGN.md documents two UI affordances with no backing functional requirement anywhere in the SRS**: (a) the heart/favorite `button-icon` on `recipe-card` — no FR describes a "favorites" feature distinct from the onboarding-time `cocinas_favoritas` field, though `fresco-edge-function-generate.md`'s own `types.ts` interestingly includes an `ingredientes_favoritos` field on `UserProfile` that appears in no other source document, ERD, or FR (a second, smaller gap nested inside this one); (b) the `button-action` "Cocinar ya" (Cook now) CTA — unclear whether this is a fourth distinct action or a UI shortcut for one of the three documented state transitions ("✓ Cocinada", "✗ Descartar", "↔ Cambiar"). **Ask**: design/founder — reconcile before these components get built literally as drawn.
