# Business API Map: Fresco

---

## 1. Executive Summary

An authenticated household turns a declared diet profile into a shoppable week in a handful of calls: request a menu (`generate-meal-plan`), request the matching shopping list (`generate-shopping-list`), and — across the week — tap a few `cocinada`/`descartada` toggles (`update-recipe-status`) that quietly make next week's menu better *if the household pays for Pro*. A first-time visitor does all of this with **no signup** — a real Supabase anonymous session is created transparently (`signInAnonymously()`, `ADR-0003`), and every Edge Function and RLS policy already accepts it because "authenticated" in this system has only ever meant "has a Supabase Auth JWT", never "has a password". She can later convert that guest session to a permanent account keeping the same `user_id`, or — if the email is already taken — reassign her generated data to the existing account after proving control of it with a session token she obtains from native Supabase Auth (`ADR-0022`, which revised ADR-0004's original server-side password check to close an unauthenticated password-oracle — audit-4 A4-L4).

What makes this API interesting from a business standpoint isn't its endpoint count — it's that `generate-meal-plan` **forks behavior by subscription tier without exposing that fork as a different endpoint, scope, or request field**. Free and Pro call the identical URL with the identical body; the only difference is a server-side `plan` read that decides whether three extra SQL history reads run and feed the deterministic menu-selection algorithm (`ADR-0001`, `ADR-0006`, `ADR-0008`). That branch *is* the Pro subscription's technical justification. Subscription state itself is set entirely out-of-band: Stripe calls `POST /api/stripe/webhook` (signature-authenticated, no user JWT) and that handler is the **primary** writer of `user_profiles.plan` (`ADR-0007`); a daily `pg_cron` reconciliation route (`GET /api/cron/stripe-reconcile`, `ADR-0015`) is the only other, and it re-derives the same state from live Stripe data to self-heal a missed webhook, including a customer who paid while the webhook never landed (it grants through the webhook's own `grantProFromCheckoutSession`).

The backend is two surface classes, not one. Nine **Supabase Edge Functions** (Deno, separate runtime) own the food-safety-critical and cross-user-privileged operations (including account deletion, which now ends the Stripe billing before it erases anything); eleven **Next.js Route Handlers** own Stripe (checkout, price summary, portal, webhook, and the daily reconciliation cron), consent recording, the pre-launch waitlist, the two public health probes, the RLS-scoped data export, and the auth-email confirmation redirect. Alongside them, several flows skip the backend entirely and call Postgres directly (RLS-scoped RPCs and table writes) for pure per-household state — favorites, the purchased-item toggle, personal recipes, deleting a week, putting a catalog recipe into an open slot. Menu selection and shopping-list classification are deterministic in-process algorithms: **there is no external LLM call anywhere in production** (`ADR-0005`).

## 2. Permission & Auth Model

Fresco's authorization is **row-ownership via `auth.uid()`, not roles** — there is no `admin`/`user` column anywhere in the schema (`.context/SRS/architecture.md` §5; `domain-glossary.md` §1 "RLS"). The tiers below are the real boundaries a caller crosses in code.

**Bot protection (not a tier):** the Supabase Auth calls that create or probe accounts (`signInAnonymously`, sign-up, password sign-in, password reset, resend) carry a Cloudflare Turnstile token as `captchaToken` (`lib/auth/captcha.ts`, `components/auth/captcha-field.tsx`, FRESCO-799). It is opt-in per build: with no `NEXT_PUBLIC_TURNSTILE_SITE_KEY` there is no widget and no token, and Supabase only enforces it once switched on in the hosted dashboard (not verifiable from code, see §7). The `delete-account` dialog also mints its `reauthToken` through a captcha-protected sign-in.

**Not a tier — a business-logic branch:** Free, Pro, and Family users are all the same `Authenticated` principal. `generate-meal-plan/index.ts` reads `profile.plan` and, for `'pro'` / `'family'`, runs three extra SECURITY DEFINER history reads that feed the (same) deterministic selector; Free never calls them. No auth scope, claim, endpoint, or RLS policy distinguishes the tiers — model it as a `plan`-column branch, never a permission (`ADR-0001`; `domain-glossary.md` §4 anti-glossary).

### Journey 1b — Guest data reassignment on email conflict

### Journey 2 — Weekly Menu Generation (Free tier)

**Business purpose:** deliver the core promise — a full week of meals, sub-second, at zero cost, stateless by design.

```
Client            generate-meal-plan Edge Fn                     Postgres
  │ POST {semana_iso, fecha_inicio} + JWT ─▶│                        │
  │                    1. requireAuthenticatedUser() — 401           │
  │                    2. load user_profiles ──────────────────────▶│ 404 if absent
  │                    3. existing plan this week? ─────────────────▶│ 409
  │                    4. get_filtered_recipes(uid) ───────────────▶│ SQL pre-filter,
  │                       < 21 → 422                                 │ 422 (Layer 1)
  │                    5. plan='free' → recentRecipeIds = []         │  (no history read)
  │                    6. selectMenu() — deterministic, in-process   │
  │                    7. service-role rpc create_meal_plan ────────▶│ plan + ≤21 slots in
  │◀── enriched menu + advertencias ────────┤                        │ ONE transaction
```

1–3. Auth, profile (`404` — onboarding must have run), no-silent-overwrite (`409`; the user resolves it via `deleteMealPlan()`, Journey J-aux).
4. **FR-8.1 Layer 1** — `get_filtered_recipes()` structurally removes allergen/diet/disliked-ingredient conflicts before selection; `422` if fewer than 21 survive. *Why:* since Gemini's removal this is the single food-safety enforcement point (see the guardrail sub-flow).
5. **The Free fork, structurally:** `plan='free'` → the three history reads are never issued; `recentRecipeIds` is `[]` (`ADR-0001`). This is the exact mechanism behind "Free never gets smarter."
6–7. Deterministic selection (`menu-selector.ts`) then persistence; a slot with no safe candidate becomes `NO_SAFE_RECIPE_SENTINEL` + an `advertencias` entry, not a hard failure. **Persistence is atomic since FRESCO-913:** `authenticated` has no INSERT on `meal_plans` / `meal_plan_recipes` (FRESCO-777), so the function calls the `service_role`-only RPC `create_meal_plan(p_user_id, p_semana_iso, p_fecha_inicio, p_advertencias, p_explicacion_aprendizaje, p_slots jsonb) returns uuid` with `user_id` from the verified JWT. It checks `semana_iso` is a real ISO week and `fecha_inicio` its Monday, requires a non-empty slot array, and writes plan and slots in one transaction, so a cut can no longer leave a slot-less plan that `unique_user_semana` turns into a permanent `409`. Errors: SQLSTATE `22023` → `400` (`semana_iso o fecha_inicio no son válidos`), `23505` (concurrent request for the same week) → `409`, anything else → `500`. The old compensating delete is gone.

**Endpoints:** `POST /generate-meal-plan` — `.context/SRS/api-contracts.md` §1; types in `api/schemas/meal-plan.types.ts`.
**Entities:** `user_profiles`, `recipes`, `meal_plans`, `meal_plan_recipes` — `business-data-map.md` §2, Flow 2.
**Feature IDs:** FEAT-016, FEAT-017 (quality heuristics), FEAT-019 (missing-safe-recipe warning), FEAT-020 (generate for a specific week).

### Journey 4 — Pro subscription lifecycle (Stripe Checkout + webhook)

**Business purpose:** self-serve upgrade to Pro — the epic (FRESCO-227) that reversed the MVP-scope deferral of self-serve payment (`ADR-0007`). Revenue-critical.

```

  │ (SSR session — 401 if none; guest 403; already Pro 409; 10/h per user 429)  │                        │

  │    mode:'subscription', price=STRIPE_PRICE_ID_PRO_MONTH,                   │
  │    subscription_data:{trial_period_days:7},                               │
  │    payment_method_collection:'if_required',                              │
  │    client_reference_id = auth.uid() })  ────────▶│ hosted page            │
  │◀── { url } ; client redirects ──────────────────┤                        │
  │                                                  │ checkout.session.      │
  │                                                  │ completed ────────────▶│ verify price ==
  │                                                  │ customer.subscription. │ Pro (else refuse)
  │                                                  │ updated / deleted ────▶│ service_role
  │  return page re-reads user_profiles.plan          │                        │ UPDATE user_profiles
  │  (never writes)                                   │                        │ (plan, stripe ids,
  │                                                  │                        │  plan_expires_at,
  │                                                  │                        │  payment_failed_at)
  ── manage/cancel ──▶ POST /api/stripe/portal (plan must be 'pro' + stripe_customer_id → else 404)
  ── daily drift-correction ──▶ pg_cron ──▶ GET /api/cron/stripe-reconcile ──▶ for each user_profiles row with a
       stripe_subscription_id: stripe.subscriptions.retrieve() → resolveReconciledState() → service_role UPDATE

            subscription → grantProFromCheckoutSession() (fail-soft, errors to Sentry)
       then recordJobHeartbeat('stripe-reconcile') unless Stripe answered for none of the profiles
       → 200 { checked, reconciled, drifted, sweptOrphans, checkoutSweep, failures }
```

**Webhook events handled (FRESCO-816/900/909):** `checkout.session.completed` and `checkout.session.async_payment_succeeded` (same grant; a delayed payment method grants Pro only once paid), `customer.subscription.updated` (`past_due` sets `payment_failed_at`, `unpaid` downgrades, recovered `active` renews), `customer.subscription.deleted` (downgrade), and `charge.refunded` — a FULL refund of the current period's charge makes the handler cancel the Stripe subscription (`prorate:false, invoice_now:false`, comment `refund:<charge id>`); it never writes the profile itself, the resulting `deleted` event does. Partial refunds change nothing. Every handled event is claimed by `event.id` in `stripe_webhook_events` first: completed → `200` without re-running; claimed by a live run → `409` so Stripe keeps retrying; a claim with no completion older than the TTL is retaken; a handler error releases the claim and still answers `200`. `maxDuration = 60`.
**Checkout guards (FRESCO-778):** guests get `403`, a user already `pro` gets `409`, 10 sessions/hour per user via `check_and_increment_rate_limit` (fails closed: RPC error `500`). The 7-day card-less trial applies once per account: a profile that already carries a Stripe customer or subscription id re-subscribes through the same Checkout without a trial, with a card (`payment_method_collection: 'always'`), reusing the existing Stripe customer.

**Why client-unreachable writes only:** two client-reachable writers (browser + webhook) would race a failed/reversed payment into a stuck `plan:'pro'`. The `prevent_client_subscription_writes()` DB trigger enforces that only `service_role` writes the subscription columns, even against a compromised client (`ADR-0007`, `20260818190000`). There are exactly two `service_role` writers: `POST /api/stripe/webhook` (primary, event-driven) and `GET /api/cron/stripe-reconcile` (secondary, daily, drift-correcting — `ADR-0015`, reuses the webhook's `lib/stripe.ts` mappers so the two never diverge byte-for-byte). Full state machine: `business-data-map.md` §4, Flow 7b.
**Before the redirect (FRESCO-794, FRESCO-844):** the pre-contract summary calls `GET /api/stripe/pro-price?interval=month|year` (signed-in, non-guest, read-only: 401 without a session, 403 for an anonymous user). The amount, currency, billing period, whether the trial applies to THIS user and whether Stripe declares the price tax-inclusive come from `stripe.prices.retrieve()`, never from the UI, so the summary cannot drift from what the checkout charges. `interval=year` selects the annual price; any other value is monthly. `POST /api/stripe/checkout` takes the same optional `{ interval }` body (an annual price that is not configured is a `400`, a monthly one a `500`).
**Consent registry (FRESCO-794, `ADR-0040`):** `POST /api/consents` `{ kinds: ConsentKind[] }` records what the caller just accepted (`age_14`, `terms`, `privacy`, `health_data`, `withdrawal_waiver`). It works for a guest too (an anonymous session is an authenticated one). The version is NOT read from the body: the server stamps `LEGAL_TEXTS_VERSION`, so a client cannot claim a version it was never shown. The write goes through the cookie-scoped client, not `service_role`: RLS lets a user read and insert only their own `user_consents` rows, there is no UPDATE or DELETE policy, and the INSERT grant is column-level on `(kind, version)` so `user_id` and `accepted_at` cannot be forged. `401` without a session, `400` for a non-JSON or invalid body, `500` if the insert fails.
**Endpoints:** `POST /api/stripe/checkout`, `GET /api/stripe/pro-price`, `POST /api/stripe/portal`, `POST /api/stripe/webhook`, `GET /api/cron/stripe-reconcile`, `POST /api/consents`. No OpenAPI — see `app/api/stripe/*/route.ts`, `app/api/cron/stripe-reconcile/route.ts`, `app/api/consents/route.ts`.
**Entities:** `user_profiles` (subscription columns), `user_consents` — `business-data-map.md` §2. **Feature IDs:** FEAT-059–063 (`business-feature-map.md`, EPIC-FRESCO-227 — Suscripción Pro; FEAT-063 = the reconciliation job); FEAT-098 (consent registry; data-map Flow 14).
