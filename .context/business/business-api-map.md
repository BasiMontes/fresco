## 1. Executive Summary

Fresco's API lets a Spanish household turn a declared diet profile into a shoppable week in three authenticated calls: request a menu, request the matching shopping list, and — spread across the week that follows — tap a handful of cooked/discarded toggles that quietly make next week's menu better if the household pays for Pro. There is no conventional REST surface behind this: the entire backend is three Supabase Edge Functions (Deno, separate runtime from the Next.js frontend) plus two direct-to-Postgres client calls that bypass the Edge Function layer for pure state toggles (`business-feature-map.md` §4). A caller either has a valid Supabase Auth JWT or gets a `401` — there is no unauthenticated path through this API today, which is itself the single most consequential open gap in the whole system (see §2).

What makes this API interesting from a business standpoint isn't its endpoint count — it's that one of its three calls (`generate-meal-plan`) silently forks behavior by subscription tier without ever exposing that fork as a different endpoint, auth scope, or request field. Free and Pro users call the exact same URL with the exact same shape; the only difference is a server-side `isPro` boolean that decides whether two extra rows of SQL history get read and stitched into the AI prompt (`ADR-0001`). That one conditional *is* the Pro subscription's technical justification — everything Fresco charges €4.99/month for lives in a single branch inside a single Edge Function.

The other defining trait is where trust boundaries sit. Every write that touches `meal_plan_recipes` is ownership-checked against the caller's JWT (never a role check — Fresco has no admin/user role distinction, `architecture.md` §5), and the one place the system will not compromise under any load — allergen and hated-ingredient exclusion — is deliberately enforced twice, once cheaply in SQL before the AI model ever sees a recipe, once again inside the model's own instructions, so that a failure of either layer alone still doesn't produce an unsafe menu (FR-8.1). This map traces that mechanism end-to-end in §3, Journey 4, because a defect there is not an ordinary bug.

## 2. Permission & Auth Model

Fresco has exactly one authentication scheme — a Supabase Auth JWT — and no traditional role hierarchy. The Free/Pro distinction that looks like a permission tier from a product perspective is **not** an auth tier at all: both are the same `Authenticated` principal; the difference is a business-logic branch inside one handler (see §3, Journeys 1–2). Treating them as separate auth tiers would misrepresent how enforcement actually works, so this section names only the tiers that are real permission boundaries in code.

| Tier | Who it applies to | How to acquire | Where enforced (spec path) |
|---|---|---|---|
| **Authenticated** | Any signed-up user — Free or Pro, no distinction at this layer | Supabase Auth login/signup issues a JWT; frontend attaches it as `Authorization: Bearer <jwt>` on every call | Every Edge Function calls `supabase.auth.getUser()` before touching any data; missing/invalid → `401 { "error": "No autorizado" }` (`api-contracts.md` §0; `fresco-edge-function-generate.md` step 1) |
| **Owner-scoped** (a sub-condition of Authenticated, not a separate tier) | An authenticated user acting on their *own* rows only | Same JWT; ownership is checked by joining the target row back to `auth.uid()` | `update-recipe-status` explicitly verifies the slot's parent `meal_plan.user_id` matches the caller, `403` otherwise (`api-contracts.md` §4); `generate-shopping-list` verifies plan ownership, `404` otherwise if the plan isn't the caller's (`api-contracts.md` §2) |
| **Service** | The offline, founder-operated batch recipe-seeding pipeline only — never client-facing | `service_role` key, held only by the founder's manual tooling, bypasses RLS | `recipes` table writes only (`api-contracts.md` §5; `business-data-map.md` Flow 4); this is the one genuinely privileged operation in the system (`architecture.md` §5: "a `service_role` vs `authenticated` split for the one genuinely privileged operation") |
| **`[UNRESOLVED]` Guest / unauthenticated** | A first-time visitor, per EPIC-FRESCO-6 | **No mechanism is specified.** See callout below. | Not enforced anywhere — because it doesn't exist yet |

**Not a tier — a business-logic branch:** Free-tier and Pro-tier users are both `Authenticated`. The only difference is that `generate-meal-plan` reads a server-side `profile.plan` value and, if it equals `'pro'` (or `'family'`), fetches the last-2-weeks recipe history via `get_recent_recipe_ids()` before building the prompt; Free-tier requests never make that call, so `recentRecipeIds` is `[]` by construction (`fresco-edge-function-generate.md` index.ts step 6; `ADR-0001` Decision section). No separate auth scope, claim, or endpoint distinguishes Free from Pro — do not model this as a permission tier when implementing.

### Token flow — the only auth scheme in the system

```
   │                        │                        │                        │     .getUser(jwt)

```

No refresh-token recipe, no separate service-to-service exchange flow, and no session-cookie scheme coexist with this — it is the sole documented auth path (`architecture.md` §5: "Supabase Auth issues a JWT on signup/login; the frontend attaches it as a Bearer token; every Edge Function verifies it via `supabase.auth.getUser()` before touching any data").

**Resolved 2026-07-31 — see ADR-0003.** EPIC-FRESCO-6 (Guest Mode) requires a first-time visitor to generate a full menu with zero signup; every documented Edge Function, including `generate-meal-plan`, hard-requires the Bearer JWT above and returns `401` when it's absent. The mechanism is now decided: Supabase Anonymous Sign-In (`supabase.auth.signInAnonymously()`), verified live against this project's real instance and enabled via the Management API. An anonymous session is a fully-formed Supabase Auth JWT, so no Edge Function or RLS policy needs to change — `requireAuthenticatedUser()` already accepts it as-is. `.context/ADR/ADR-0003-guest-auth-anonymous-sign-in.md` has the full decision, the upgrade-to-permanent-account path (`updateUser()`, same `user_id` preserved), and a real risk this resolution surfaced: the upgrade's required email verification step hits the same email-deliverability friction (domain validation, rate limits) already observed live for regular signup this session.

## 3. Critical Business Journeys

Four journeys, selected for revenue impact (the Free/Pro fork), core product value (menu generation), and blast radius on failure (the food-safety guardrail). Capped below the command's 7-journey default because Fresco's real surface is only three Edge Functions — a 5th–7th journey would just be recombinations of the same two or three calls already traced below (see §7 for this cap decision, per the command's own instruction to document rather than silently expand). Guest mode is **not** traced as a fifth journey here, per the auth gap in §2 — tracing it would require inventing a mechanism no source document specifies.

### Journey 1 — Weekly Menu Generation (Free tier)

**Business purpose:** deliver the core promise — a full week of meals in under 30 seconds — to every user at zero cost, stateless by design.

```
Client              generate-meal-plan Edge Fn          Postgres              Gemini Flash
  │  POST + JWT               │                             │                       │
  ├──────────────────────────▶│                             │                       │
  │                           │ 1. getUser(jwt) — 401 if bad│                       │
  │                           │ 2. load user_profiles — 404 │                       │
  │                           ├────────────────────────────▶│                       │
  │                           │ 3. check no plan this week   │                       │
  │                           │    (409 if exists)            │                       │
  │                           │ 4. get_filtered_recipes()     │                       │
  │                           │    — SQL pre-filter (422 if   │                       │
  │                           │    <21 survive)                │                       │
  │                           │◀────────────────────────────┤                       │
  │                           │ 5. isPro=false → skip history  │                       │
  │                           │    fetch entirely; recentIds=[]│                       │
  │                           │ 6. build prompt, call Gemini ──┼──────────────────────▶│
  │                           │                                │  7. select 21 ids     │
  │                           │◀───────────────────────────────┼───────────────────────┤
  │                           │ 8. validate ids/repeats/budget  │                       │
  │                           │    retry ≤2 on failure (502)    │                       │
  │                           │ 9. persist meal_plans + 21 rows ▶│                       │
  │  10. enriched menu +      │                                │                       │
  │      advertencias         │                                │                       │
  │◀──────────────────────────┤                                │                       │
```

1. A signed-up Free user, post-onboarding, requests this week's menu — **why**: this is the product's entire value proposition, and it must work with zero prior data.
2. Auth and profile load happen exactly as in §2's token flow — **why**: nothing downstream can run without a valid identity and a completed onboarding profile.
3. `409` on an existing plan for the week — **why**: regeneration is never a silent overwrite; a user's existing plan is not disposable state (FR-2.1).
4. SQL pre-filter excludes allergen/diet/hated-ingredient conflicts before the model ever sees the catalog — **why**: this is Layer 1 of the two-layer safety invariant traced fully in Journey 4; it doubles here as the ordinary quality filter.
5. **The Free-tier fork, structurally**: `isPro` is false, so `get_recent_recipe_ids()` is never called — not toggled off, never invoked — meaning `recentRecipeIds` is `[]` by construction (ADR-0001 Decision). This is the exact mechanism, not a UX choice, behind "Free never gets smarter."
6–8. Prompt build, Gemini call, and output validation are identical machinery to Journey 2 below — the fork is entirely upstream of this point.
9–10. Persistence and response shape are also identical to Journey 2 — the two journeys are the same call chain with one input differing.

**Edge Functions involved**: `POST generate-meal-plan` — full spec in `.context/SRS/api-contracts.md` §1.
**Entities touched**: `user_profiles`, `recipes`, `meal_plans`, `meal_plan_recipes` — see `.context/business/business-data-map.md` §2 Entity Map.
**Feature IDs**: FEAT-002 (Weekly Menu Generation), FEAT-003 (Budget Ceiling), FEAT-005 (Quality Heuristics), FEAT-006 (Warnings Surfacing) — `.context/business/business-feature-map.md` §2.

### Journey 2 — Weekly Menu Generation (Pro tier) — where the moat gets operationalized

**Business purpose:** the same generation promise as Journey 1, plus the one mechanism Fresco actually charges for — this is ADR-0001's moat made concrete at the API boundary.

```
Client              generate-meal-plan Edge Fn          Postgres              Gemini Flash
  │  POST + JWT               │                             │                       │
  ├──────────────────────────▶│                             │                       │
  │                           │  1-4. identical to Journey 1  │                       │
  │                           │◀────────────────────────────┤                       │
  │                           │ 5. isPro=true →               │                       │
  │                           │    get_recent_recipe_ids()    │                       │
  │                           │    (last 2 weeks)              │                       │
  │                           ├────────────────────────────▶│                       │
  │                           │◀────────────────────────────┤                       │
  │                           │ 6. build prompt WITH history   │                       │
  │                           │    section + Pro explanation   │                       │
  │                           │    addendum, call Gemini ──────┼──────────────────────▶│
  │                           │                                │ 7. select 21 ids,     │
  │                           │                                │    avoid history,     │
  │                           │                                │    populate           │
  │                           │                                │    advertencias with   │
  │                           │                                │    explanation text    │
  │                           │◀───────────────────────────────┼───────────────────────┤
  │                           │  8-10. identical to Journey 1  │                       │
  │  11. menu + Pro-only      │                                │                       │
  │      explanation card     │                                │                       │
  │◀──────────────────────────┤                                │                       │
```

1–4. Identical to Journey 1 — auth, profile, conflict check, SQL pre-filter.
5. **The fork lands here**: `isPro = true` triggers `get_recent_recipe_ids(user_id, weeks=2)` — the single extra SQL call that constitutes Fresco's entire paid feature (`fresco-edge-function-generate.md` index.ts step 6). **Why**: ADR-0001's core bet is that this signal is cheap to capture and expensive for a stateless competitor to replicate — the cost of delivering it is genuinely one query.
6. The prompt-builder includes a `HISTORIAL RECIENTE` section listing recipe IDs the model must not repeat, plus a Pro-only instruction to populate `advertencias` with 2–3 warm, specific sentences explaining what changed — but only when real history exists, never on a Pro user's first week (FR-5.5) — **why**: the moat is worthless if it isn't *felt*; the explanation text is the product's answer to the named risk that Pro's improvement goes unnoticed (`market-context.md` Risks, cited in ADR-0001 Consequences).
7. Gemini applies the priority-ordered signal table from FR-5.4 (allergen > hated-ingredient > discarded>2x > history-repeat > low-rating > high-rating > favorite-cuisine) — **why**: the priority order itself is a business decision (safety signals always outrank preference signals), not an implementation detail.
8–10. Identical validation/persistence/enrichment machinery to Journey 1.
11. The response's `advertencias` array, when populated with the Pro explanation, renders as the `card-insight` UI component — **why**: this is the one visible artifact a Pro subscriber gets in exchange for the subscription; if this rendering pipeline breaks, the Pro tier has no perceptible value that week.

**Edge Functions involved**: `POST generate-meal-plan` (same endpoint as Journey 1, tier-branched internally) — `.context/SRS/api-contracts.md` §1, §1a (nested prompt contract).
**Entities touched**: same as Journey 1, plus reads aggregate learning fields on `recipes` (`veces_cocinada`, `veces_descartada`, `rating_promedio`, `ultima_vez_en_menu`) — `.context/business/business-data-map.md` §2.
**Feature IDs**: FEAT-004 (Pro-Tier 2-Week No-Repeat), FEAT-015 (Pro-Tier History-Informed Generation), FEAT-016 (Learning Explanation Card) — `.context/business/business-feature-map.md` §2.

### Journey 3 — Cooked/Discarded Feedback Loop (the learning input, universal across tiers)

**Business purpose:** capture the raw behavioral signal every journey above eventually consumes — this is the write path that feeds Journey 2's history fetch, and it is security-relevant because it is the one place a user directly mutates another table's downstream aggregate.

```
Client         update-recipe-status Edge Fn      meal_plan_recipes      recipe_learning_trigger
  │  PATCH + JWT          │                             │                        │
  ├──────────────────────▶│                             │                        │
  │                       │ 1. getUser(jwt) — 401        │                        │
  │                       │ 2. join slot → meal_plan     │                        │
  │                       │    → verify user_id matches  │                        │
  │                       │    caller — 403 otherwise ───▶│                        │
  │                       │ 3. reject if already terminal│                        │
  │                       │    (cocinada/descartada, 409)│                        │
  │                       │ 4. UPDATE estado ────────────▶│                        │
  │                       │                              │ 5. AFTER UPDATE fires ─▶│
  │                       │                              │                        │ 6. veces_cocinada++
  │                       │                              │                        │    or veces_descartada++
  │  7. { ok: true }      │                              │                        │    (global aggregate)
  │◀──────────────────────┤                              │                        │
```

1. Auth is identical to Journeys 1–2 — **why**: no anonymous write path exists for this either.
2. **The ownership check is the security-critical step in this journey**: the Edge Function joins the target `meal_plan_recipes` row back to its parent `meal_plans.user_id` and rejects with `403` on mismatch (`api-contracts.md` §4) — **why**: without this join, any authenticated user could mutate any other user's slot state and pollute the global aggregate that feeds every Pro user's next generation (Journey 2, step 7). This is the one place in the system where a missing authorization check would have a cross-user, product-wide blast radius, not just a single-account one.
3. Terminal-state rejection (`409` on an already-`cocinada`/`descartada` slot) — **why**: prevents double-counting the same signal into the aggregate via repeated toggling (FR-5.1).
4–5. The actual write and the trigger firing are ordinary database mechanics — but **why they're split this way matters**: the aggregate update is the database's responsibility, not the API's, specifically so it fires identically regardless of which future code path (Edge Function, admin tool, migration script) ever performs the `UPDATE` (`api-contracts.md` §4: "the learning side effect is the database's responsibility, not the API's").
6. Recording is unconditional across every tier — Free users' toggles are captured exactly like Pro's — **why**: this is the deliberate ADR-0001 split between *recording* (universal) and *application* (Pro-only); recording costs nothing and keeps the door open for a future pricing change without a data migration.
7. The `{ ok, estado }` response carries no aggregate data back — the caller never sees the updated `veces_cocinada` directly, only its downstream effect the next time a menu is generated.

**Edge Functions involved**: `PATCH update-recipe-status` — `.context/SRS/api-contracts.md` §4.
**Entities touched**: `meal_plan_recipes` (write), `recipes` (trigger-driven aggregate update) — `.context/business/business-data-map.md` §4 State Machines, §5 Automatic Processes.
**Feature IDs**: FEAT-008 (Meal Substitution, when `estado='sustituida'`), FEAT-013 (Cooked/Discarded/Substituted State Recording), FEAT-014 (Recipe Aggregate Learning Statistics) — `.context/business/business-feature-map.md` §2.

### Journey 4 — Food-Safety Guardrail Escalation (sub-flow of Journeys 1–2, traced separately — highest blast radius in the system)

**Business purpose:** guarantee that a declared allergy or hated ingredient never reaches a user's plate via a generated menu — a failure here is a health/safety incident, not a UX defect, which is why it earns its own entry even though it has no endpoint of its own.

```
generate-meal-plan Edge Fn                    Postgres                          Gemini Flash
        │                                          │                                  │
        │  LAYER 1 — structural, before the model ever runs                          │
        │  get_filtered_recipes(user_id) ─────────▶│                                  │
        │    excludes any recipe where               │                                  │
        │    alergenos ∩ user.alergenos ≠ ∅           │                                  │
        │    OR ingredientes_principales ∩            │                                  │
        │       user.ingredientes_odiados ≠ ∅          │                                  │
        │◀─────────────────────────────────────────┤                                  │
        │  IF <21 recipes survive → 422 (hard stop,                                    │
        │  catalog too small for this profile — no unsafe menu is ever generated)      │
        │                                          │                                  │
        │  LAYER 2 — semantic, model-level, defense in depth                          │
        │  system prompt "REGLAS ABSOLUTAS" 1-2:                                       │
        │  "NUNCA incluyas una receta que contenga                                     │
        │   alguno de los alérgenos del usuario"          ─────────────────────────────▶│
        │                                                                              │
        │                                          model selects only from the         │
        │                                          already-filtered catalog, and is    │
        │                                          separately instructed never to      │
        │                                          violate the same two rules          │
        │◀─────────────────────────────────────────────────────────────────────────────┤
        │  IF the model reports it could not honor a mandatory filter for any          │
        │  slot → non-empty advertencias entry, flagged P0 (not a log line)            │
        │                                          │                                  │
        │  → surfaced to caller as a prominent, blocking-style warning (FEAT-022),     │
        │    never presented as a safe-by-default menu (FR-8.2)                        │
```

1. **Layer 1 fires first, cheaply, before any AI cost is spent**: `get_filtered_recipes()` is a SQL pre-filter, not a suggestion — a recipe whose `alergenos` overlaps the user's declared allergens, or whose `ingredientes_principales` overlaps their hated ingredients, is structurally absent from the catalog the model ever receives (FR-8.1 Layer 1). **Why**: this is the cheapest possible enforcement point and it fails closed — if too few recipes survive, the call returns `422` rather than proceeding with a degraded-safety catalog.
2. **Layer 2 repeats the same exclusion inside the model's own instructions**, as "REGLAS ABSOLUTAS" rules 1–2 (`fresco-edge-function-generate.md` prompt.ts) — **why**: neither layer is trusted alone (`ADR-0001`; `architecture.md` §5). If Layer 1 is ever bypassed or misconfigured by a future code change, Layer 2 is the last line of defense, and vice versa — this two-layer redundancy is itself the architectural invariant, promoted to ADR-0001 specifically because it's the one decision in the system too consequential to leave undocumented.
3. **Escalation, not silence, on partial failure**: if the model's own `advertencias` output reports it could not honor a mandatory filter for some slot, the backend must treat that as a P0 safety signal — never discard it, never log-and-continue (FR-2.10, FR-8.2). The affected menu is never presented to the user as safe-by-default (FEAT-022) — it must render as a blocking-style warning, visually distinct from the ordinary insight-card treatment Journeys 1–2 use for quality warnings.
4. **This code-level mechanism does not yet replace the manual backstop**: during the current pre-launch/concierge-validation stage, a founder-run manual checklist still runs before every menu delivery, independent of whether FR-8.1/FR-8.2 are implemented in code yet (FR-8.3, FEAT-023) — **why this matters for a developer**: shipping Layer 1 and Layer 2 does not retire the manual process; they are additive, not a replacement, per explicit product decision.

**Edge Functions involved**: `POST generate-meal-plan` — same call as Journeys 1–2, this is the safety sub-flow inside it. `.context/SRS/api-contracts.md` §1, §1a.
**Entities touched**: `user_profiles.alergenos` / `.ingredientes_odiados`, `recipes.alergenos` / `.ingredientes_principales` — `.context/business/business-data-map.md` §2.
**Feature IDs**: FEAT-020 (Allergen Exclusion, two-layer), FEAT-021 (Hated-Ingredient Exclusion, two-layer), FEAT-022 (Safety-Critical Warning Escalation), FEAT-023 (Manual Food-Safety Review) — `.context/business/business-feature-map.md` §2.

## 4. Architecture Behind the API

```
          ▼

   │  generate-meal-plan · generate-shopping-list ·   │

   └───────┬───────────────────────────────┬──────────┘
           │                               │
           ▼                               ▼
   ┌──────────────────┐          ┌──────────────────────┐
   │  SQL pre-filter /  │          │  Gemini Flash          │
   │  aggregate reads   │          │  (menu selection,      │
   │  (get_filtered_    │          │   aisle classify,       │
   │  recipes, get_     │          │   batch recipe gen)     │

   └─────────┬──────────┘          │  googleapis.com          │
```

| Component | Role | Persistence/Integrations touched | Why it matters for dev |
|---|---|---|---|
| Client (Next.js, Vercel) | Holds the JWT, calls Edge Functions directly via `supabase.functions.invoke()` | none directly — all writes go through the Edge Function or a scoped RPC | Two separate release pipelines: a frontend deploy and an Edge Function deploy are independent events (`architecture.md` §6) — a broken Edge Function doesn't require a frontend redeploy to fix, and vice versa |
| Supabase Edge Functions (Deno) | Auth validation, orchestration, prompt building, output validation, persistence | Postgres (read/write), Gemini Flash (outbound) | This is where every new endpoint or business-rule change belongs — it's the only layer that owns cross-cutting logic (auth, validation, retries); **do not** put business rules in the client or in raw RPC calls |
| SQL functions (`get_filtered_recipes`, `get_recent_recipe_ids`) + `recipe_learning_trigger` | Cheap structural filtering and unconditional aggregate recording | Postgres only | Anything that must hold true regardless of which Edge Function or future caller triggers it belongs here, not in application code — this is exactly why the learning aggregate is a trigger, not API logic (`api-contracts.md` §4) |
| Gemini Flash | External LLM — menu selection (`temp 0.7`), aisle classification (`temp 0.2`), offline batch recipe generation | none — stateless per call, no persistence of its own | What you have to mock when unit-testing any Edge Function: a `fetch()` call to `generativelanguage.googleapis.com`, no SDK wrapper (`business-feature-map.md` §6) |
| Postgres (5 tables, 1 live) | System of record | `recipes` (LIVE, ~35 seeded rows); `user_profiles`, `meal_plans`, `meal_plan_recipes`, `shopping_lists` (designed, not yet created) | The column-shape decision (typed relational vs. JSONB) for the four not-yet-created tables is unresolved and deferred to `/project-bootstrap` (`architecture.md` §4) — do not assume either shape when scaffolding |

There is no API gateway, load balancer config, or multi-service mesh to document — the entire backend is these three functions plus the database they share, deployed as independent Supabase artifacts (`supabase functions deploy`), consistent with a solo-founder, pre-launch operating scale.

## 5. External Integrations

| Service | Trigger | Direction | Failure mode (user-visible) | Journeys affected |
|---|---|---|---|---|
| Gemini Flash | `POST generate-meal-plan` (menu selection, `temperature: 0.7`) | Outbound sync | Non-2xx from Gemini → immediate `502`, no retry of the transport failure itself (`fresco-edge-function-generate.md` index.ts: `if (!geminiResponse.ok) return errorResponse(...)`); malformed/invalid JSON output → up to `MAX_RETRIES = 2` retries, then `502` if still invalid — no menu is ever persisted in a partial state | Journey 1, Journey 2, Journey 4 (the model itself is Layer 2 of the safety guardrail) |
| Gemini Flash | `POST generate-shopping-list` (aisle classification, `temperature: 0.2`) | Outbound sync | Same retry ceiling (`MAX_RETRIES = 2`); additionally, output is rejected and retried if fewer than 90% of the consolidated ingredient count survives classification (`api-contracts.md` §2b) — the model is never trusted to invent or drop items | Not one of the 4 traced journeys directly, but shares the same failure posture; see `business-data-map.md` Flow 3 |
| Gemini Flash | Founder-operated batch recipe generation (offline, not a live Edge Function) | Outbound sync, manual trigger | No automated failure handling — output is manually reviewed against an 8-point checklist before any `service_role` insert; a bad generation is simply not approved (`business-data-map.md` Flow 4) | None of the 4 live-call journeys; feeds the `recipes` catalog all of them read from |

Gemini Flash is the only third-party service reached from this API (`business-feature-map.md` §6). `GEMINI_API_KEY` is stored exclusively as a Supabase Edge Function secret, never exposed to the client (NFR-SEC-3, `architecture.md` §5). No payment, email, analytics, or monitoring SDK is integrated at the API boundary — Supabase Auth itself is treated as core platform, not an external integration line item.

Remaining risk carried forward by the ADR, not solved by it: the account-upgrade step's required email verification hits the same deliverability friction already observed live for regular signup this session (domain validation, rate limits) — flag this explicitly in FRESCO-7's Stage 1 plan.
2. **No OpenAPI spec exists yet, and this entire map substitutes `.context/SRS/api-contracts.md` for one** (see the Source Substitution Note at the top of this document). This is a legitimate, session-consistent substitution for a pre-implementation project, but it means every "endpoint" reference above is a specification pointer, not a `file:line` or schema-registry reference. **Recommended action**: re-run `/business-api-map` after `/project-bootstrap` generates a real OpenAPI spec via `bun run api:sync`, to re-validate every journey and auth claim against actual deployed code.
3. **No rate-limiting or abuse-prevention mechanism is mentioned anywhere in any source document for the two LLM-calling endpoints** (`generate-meal-plan`, `generate-shopping-list`). Both call an external, presumably metered/billed API (Gemini Flash) on every authenticated request with no documented per-user or per-IP throttle. At concierge-validation scale (8–10 users) this is low-risk, but it is a real, currently-undocumented cost and abuse exposure that will matter before any public launch. **Ask**: the founder or `/project-bootstrap` — worth a line item before the first public (non-concierge) cohort.
4. **The four not-yet-created tables' column shape (typed relational vs. JSONB) is unresolved**, which means every journey traced above that touches `user_profiles`, `meal_plans`, `meal_plan_recipes`, or `shopping_lists` is tracing against a *contract*, not a committed schema — carried forward from both `business-data-map.md` and `business-feature-map.md`, restated here because it directly affects how literally the request/response shapes in `.context/SRS/api-contracts.md` will map to real Postgres columns once `/project-bootstrap` runs.
5. **No `meal_plans` DELETE endpoint is documented**, yet the founder's own Edge Function error copy in `generate-meal-plan` implies one exists ("Ya existe un plan para la semana… Elimínalo antes de regenerar" — delete it before regenerating). This gap is already flagged in `business-feature-map.md` §8 and is restated here because it directly affects Journey 1/2's `409` branch: a user who hits that conflict currently has no documented API path to resolve it. **Ask**: the founder — should this be a fourth Edge Function, or a direct client call like the `comprado` toggle pattern?
6. **CORS is dev-time-only (`Access-Control-Allow-Origin: *`) with no production scoping specified anywhere** (`api-contracts.md` §0). Not a blocker for the current concierge stage, but worth flagging before a public deploy, since it is presently undifferentiated between `local`/`staging`/a future `production` environment (`architecture.md` §6, which itself notes no `production` environment is yet defined in `.agents/project.yaml`).
