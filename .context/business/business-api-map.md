# Business API Map: Fresco

---

## 1. Executive Summary

An authenticated household turns a declared diet profile into a shoppable week in a handful of calls: request a menu (`generate-meal-plan`), request the matching shopping list (`generate-shopping-list`), and — across the week — tap a few `cocinada`/`descartada` toggles (`update-recipe-status`) that quietly make next week's menu better *if the household pays for Pro*. A first-time visitor does all of this with **no signup** — a real Supabase anonymous session is created transparently (`signInAnonymously()`, `ADR-0003`), and every Edge Function and RLS policy already accepts it because "authenticated" in this system has only ever meant "has a Supabase Auth JWT", never "has a password". She can later convert that guest session to a permanent account keeping the same `user_id`, or — if the email is already taken — reassign her generated data to the existing account after proving control of it with a session token she obtains from native Supabase Auth (`ADR-0022`, which revised ADR-0004's original server-side password check to close an unauthenticated password-oracle — audit-4 A4-L4).

What makes this API interesting from a business standpoint isn't its endpoint count — it's that `generate-meal-plan` **forks behavior by subscription tier without exposing that fork as a different endpoint, scope, or request field**. Free and Pro call the identical URL with the identical body; the only difference is a server-side `plan` read that decides whether three extra SQL history reads run and feed the deterministic menu-selection algorithm (`ADR-0001`, `ADR-0006`, `ADR-0008`). That branch *is* the Pro subscription's technical justification. Subscription state itself is set entirely out-of-band: Stripe calls `POST /api/stripe/webhook` (signature-authenticated, no user JWT) and that handler is the **primary** writer of `user_profiles.plan` (`ADR-0007`); a daily `pg_cron` reconciliation route (`GET /api/cron/stripe-reconcile`, `ADR-0015`) is the only other, and it re-derives the same state from live Stripe data to self-heal a missed webhook.

The backend is two surface classes, not one. Eight **Supabase Edge Functions** (Deno, separate runtime) own the food-safety-critical and cross-user-privileged operations; six **Next.js Route Handlers** own Stripe (checkout, portal, webhook, and the daily reconciliation cron), the RLS-scoped data export, and the auth-email confirmation redirect. Alongside them, several flows skip the backend entirely and call Postgres directly (RLS-scoped RPCs and table writes) for pure per-household state — favorites, the purchased-item toggle, personal recipes, deleting a week. Menu selection and shopping-list classification are deterministic in-process algorithms: **there is no external LLM call anywhere in production** (`ADR-0005`).

## 2. Permission & Auth Model

Fresco's authorization is **row-ownership via `auth.uid()`, not roles** — there is no `admin`/`user` column anywhere in the schema (`.context/SRS/architecture.md` §5; `domain-glossary.md` §1 "RLS"). The tiers below are the real boundaries a caller crosses in code.

| Tier | Who it applies to | How to acquire | Where enforced (code path) |
|---|---|---|---|
| **Public / unauthenticated** | Any visitor | — | `/` (landing), `/qa` (testability guide), `GET /auth/confirm` (verifies the Supabase token itself, `app/auth/confirm/route.ts`), and `POST /api/stripe/webhook` (authenticated by Stripe signature, not a session) |
| **Anonymous (guest)** | First-time visitor | `supabase.auth.signInAnonymously()` on `/onboarding` mount (`app/onboarding/page.tsx`, `ADR-0003`) | Identical to Authenticated — an anonymous JWT carries a real `auth.uid()` with `is_anonymous = true`; `requireAuthenticatedUser()` (`supabase/functions/_shared/auth.ts`) accepts it unmodified; every RLS policy is `auth.uid()`-scoped |
| **Authenticated** | Any signed-up user — Free, Pro, or Family, no distinction at this layer | Supabase Auth login/signup issues a JWT; the frontend attaches `Authorization: Bearer <jwt>` (Edge Functions) or a cookie-scoped SSR client (Route Handlers) | Every Edge Function calls `requireAuthenticatedUser()` first → `401 { "error": "No autorizado" }`. Route Handlers call `supabase.auth.getUser()` on the SSR client → `401` |
| **Owner-scoped** (sub-condition of Authenticated) | An authenticated user acting on her *own* rows | Same JWT; ownership checked by joining the target row to `auth.uid()` | `update-recipe-status` joins the slot to `meal_plans.user_id` → `403`; `generate-shopping-list` filters the plan by `user_id` → `404`; `swap_meal_plan_slots()` / `jsonb_set_comprado()` / `jsonb_add_item()` re-check `auth.uid()` inside the SECURITY DEFINER body; RLS `*_own` policies back every direct table call |
| **Admin allowlist** | The founder only | `user.id` must be in the `ADMIN_USER_ID` env allowlist (comma-separated) | `requireAdminUser()` (`supabase/functions/_shared/admin.ts`) → `403`. Gates `delete-catalog-recipe` and `/admin/recipes`. **Not** a DB role — an env-var allowlist (FRESCO-237) |
| **Service role** | Server code that must cross the row-ownership boundary | `SUPABASE_SERVICE_ROLE_KEY` (Edge Function client / `lib/supabase/service.ts`) — bypasses RLS, but **not** triggers | `reassign_guest_data()` (`EXECUTE` granted only to `service_role`); `get_push_subscriptions_without_current_plan()` (same); `auth.admin.deleteUser()` in `delete-account` / `reassign-guest-data`; the Stripe webhook's `user_profiles` writes; `delete-catalog-recipe`'s `recipes` write |
| **Per-user rate limit** (not a tier — a throttle inside Authenticated) | Any authenticated caller of a limited function | automatic; keyed on `auth.uid()` + endpoint | `enforceRateLimit()` (`_shared/rate-limit.ts`, atomic `check_and_increment_rate_limit` RPC, `ADR-0010`) — `update-recipe-status` 60/hour (FRESCO-362) and `reassign-guest-data` 5/hour (`ADR-0022`), both fail-closed → `429`. `generate-meal-plan` has its own 5/hour limit (`generate-meal-plan/rate-limit.ts`, FRESCO-243). `generate-shopping-list` still unthrottled (§7) |
| **Service secret key** (`apikey` header) | The `pg_cron` job that invokes an Edge Function over HTTP | `SUPABASE_SECRET_KEYS.default` (`sb_secret_...`), read from Supabase Vault by the cron migration, sent on `apikey` | `requireServiceRoleCaller()` — `send-weekly-reengagement-push` is deployed `verify_jwt: false` and does its own check → `401` (`ADR-0011`, `20260823234500`) |
| **Cron shared secret** (`Authorization: Bearer`) | The `pg_cron` job that invokes a Next.js Route Handler over HTTP (`GET /api/cron/stripe-reconcile`) | `CRON_SECRET` — a plain shared secret (not a Supabase key), set in the Vercel Production scope and mirrored into Supabase Vault (`stripe_reconcile_cron_secret`) for the cron migration to read | The route compares the bearer token to `CRON_SECRET` → `401`; returns `500` if `CRON_SECRET` is unset (`app/api/cron/stripe-reconcile/route.ts`, `ADR-0015`, `20260828174500`) |
| **Stripe webhook signature** | Stripe's servers only | `STRIPE_WEBHOOK_SECRET_{DEV,PRE,PROD}` (per-environment, `resolveWebhookSecret()`) | `stripe.webhooks.constructEvent(rawBody, sig, secret)` in `app/api/stripe/webhook/route.ts` → `400` on failure |

**Not a tier — a business-logic branch:** Free, Pro, and Family users are all the same `Authenticated` principal. `generate-meal-plan/index.ts` reads `profile.plan` and, for `'pro'` / `'family'`, runs three extra SECURITY DEFINER history reads that feed the (same) deterministic selector; Free never calls them. No auth scope, claim, endpoint, or RLS policy distinguishes the tiers — model it as a `plan`-column branch, never a permission (`ADR-0001`; `domain-glossary.md` §4 anti-glossary).

### Second scheme — Stripe webhook signature (inbound, no session)

```
   Stripe ──POST /api/stripe/webhook──▶ Next.js Route Handler
                                          │ request.text()  (raw bytes — required for verification)
                                          │ stripe.webhooks.constructEvent(raw, stripe-signature, resolveWebhookSecret())
                                          │   · verified → route on event.type → service_role UPDATE user_profiles
                                          │   · unverified → 400, nothing written
                                          ▼
                                        200 { received: true }   (always, once verified — even on a downstream error)
```

### Third scheme — machine secrets for scheduled jobs (inbound, `pg_cron` only)

```
   pg_cron ──net.http_post(apikey = vault secret)──▶ send-weekly-reengagement-push  (Edge Fn, verify_jwt: false)
                                                       requireServiceRoleCaller(): apikey == SUPABASE_SECRET_KEYS.default ? proceed : 401

   pg_cron ──net.http_get(Authorization: Bearer <vault secret>)──▶ GET /api/cron/stripe-reconcile  (Next.js Route Handler)
                                                       token == CRON_SECRET ? proceed : 401   (500 if CRON_SECRET unset)
```

There is no refresh-token recipe, session-cookie scheme for the API, or service-to-service OAuth exchange beyond the above. `@supabase/ssr` handles JWT refresh transparently client-side.

## 3. Critical Business Journeys

Six journeys, plus one sub-flow. Selected for: signup-free core value (J1), the Free/Pro fork (J2, J3), the cross-user-blast-radius write (J3), revenue (J4), and the two scheduled/inbound machine-to-machine paths (J5, J6). The food-safety guardrail is traced as a sub-flow of J2/J3 because a defect there is a health/safety incident, not a UX bug.

### Journey 1 — Guest happy path: onboard → menu → keep it

```
  │ 2. upsertUserProfile() ─────┼──────────────────────┼────────────────────▶│ insert user_profiles (RLS own)
  │ 3. generateMealPlan(jwt) ───┼─────────────────────▶│ 4. get_filtered_    │
  │                             │                      │    recipes → 422 if │
  │                             │                      │    < 21 survive     │
  │                             │                      │ 5. selectMenu()      │
  │                             │                      │ 6. insert plan +     │
  │                             │                      │    ≤21 slots         │
  │◀── enriched menu ───────────┼──────────────────────┤                     │
```

**Why the steps:** step 1 must succeed before onboarding step 3 or `handleGenerate()` has no token; step 4 is FR-8.1 Layer 1 and fails closed; the conversion in step 8 keeps the same `user_id` so no data move is needed — unless the email is taken, which routes into Journey J1b.

### Journey 1b — Guest data reassignment on email conflict

**Business purpose:** a guest whose chosen email already belongs to a different account is not stuck at a dead end (`ADR-0004`, FRESCO-20).

```
/signup (email_exists branch)       reassign-guest-data Edge Fn        Postgres
  │ client first: signInWithPassword(email,pw) on a throwaway in-memory       │
  │ client (persistSession:false) → targetAccessToken; guest session stays    │
  │ live on the main client                                                   │
  │ POST { targetAccessToken } + guest anon JWT ─▶│                           │
  │                        1. caller.is_anonymous ? else 400                  │
  │                        2. enforceRateLimit(guest.id, 5/hour) else 429     │
  │                        3. verify token: Bearer(targetAccessToken).getUser()
  │                           → 401 if invalid (generic, no enumeration)       │
  │                           → 400 if target is_anonymous / target == guest   │
  │                        4. service_role reassign_guest_data(from,to) ──────▶│ move meal_plans
  │                           (skip weeks the target already has)              │ + shopping_lists,
  │                        5. service_role auth.admin.deleteUser(guest.id)     │ delete guest profile
  │◀── { reassigned: true } ──────────────────────┤                           │
  │ 6. client switches main client to the target account → /menu
```

**Endpoints:** `POST /reassign-guest-data` — body `{ targetAccessToken }` (`api/schemas/api-contracts.types.ts` `ReassignGuestDataRequest`, `ADR-0022`). **Entities:** `meal_plans`, `shopping_lists`, `user_profiles`, `auth.users`. **Feature ID:** FEAT-004. **Security:** the only cross-user write in the system; `reassign_guest_data()` `EXECUTE` is `service_role`-only. Ownership is proven by **verifying a session token the caller already obtained from native Auth**, not by a server-side password sign-in — the old `{email, password}` contract was an unauthenticated password-verification oracle outside Auth's own protections (A4-L4). A 5/hour per-guest rate limit (`_shared/rate-limit.ts`) caps abuse of the endpoint itself.

### Journey 2 — Weekly Menu Generation (Free tier)

**Business purpose:** deliver the core promise — a full week of meals, sub-second, at zero cost, stateless by design.

```
Client            generate-meal-plan Edge Fn                     Postgres
  │ POST {semana_iso, fecha_inicio} + JWT ─▶│                        │
  │                    1. requireAuthenticatedUser() — 401           │
  │                    2. load user_profiles ──────────────────────▶│ 404 if absent
  │                    3. existing plan this week? ─────────────────▶│ 409
  │                    4. get_filtered_recipes(uid) ───────────────▶│ SQL pre-filter,
  │                       < 21 → 422                                 │ 422 (Layer 1)
  │                    5. plan='free' → recentRecipeIds = []         │  (no history read)
  │                    6. selectMenu() — deterministic, in-process   │
  │                    7. insert meal_plans + ≤21 meal_plan_recipes ▶│ compensating
  │◀── enriched menu + advertencias ────────┤                        │ delete on slot error
```

1–3. Auth, profile (`404` — onboarding must have run), no-silent-overwrite (`409`; the user resolves it via `deleteMealPlan()`, Journey J-aux).
4. **FR-8.1 Layer 1** — `get_filtered_recipes()` structurally removes allergen/diet/disliked-ingredient conflicts before selection; `422` if fewer than 21 survive. *Why:* since Gemini's removal this is the single food-safety enforcement point (see the guardrail sub-flow).
5. **The Free fork, structurally:** `plan='free'` → the three history reads are never issued; `recentRecipeIds` is `[]` (`ADR-0001`). This is the exact mechanism behind "Free never gets smarter."
6–7. Deterministic selection (`menu-selector.ts`) then persistence; a slot with no safe candidate becomes `NO_SAFE_RECIPE_SENTINEL` + an `advertencias` entry, not a hard failure.

**Endpoints:** `POST /generate-meal-plan` — `.context/SRS/api-contracts.md` §1; types in `api/schemas/meal-plan.types.ts`.
**Entities:** `user_profiles`, `recipes`, `meal_plans`, `meal_plan_recipes` — `business-data-map.md` §2, Flow 2.
**Feature IDs:** FEAT-016, FEAT-017 (quality heuristics), FEAT-019 (missing-safe-recipe warning), FEAT-020 (generate for a specific week).

### Journey 3 — Weekly Menu Generation (Pro tier) + the learning write path

**Business purpose:** the same promise plus the one mechanism Fresco charges €4.99/month for — and the write path that feeds it, which is the highest-blast-radius authorization check in the system.

```
Client        generate-meal-plan Edge Fn                        Postgres
  │ POST + JWT ──▶│  1-4. identical to Journey 2                     │
  │               │  5. plan in ('pro','family') → Promise.all([     │
  │               │       get_recent_recipe_marks(uid, 2 weeks),     │ SECURITY DEFINER,
  │               │       get_user_recipe_engagement(uid) ])  ──────▶│ auth.uid() checked
  │               │  6. selectMenu({ recentRecipeIds, userEngagement})│
  │               │     · cocinada/descartada last 2w REMOVED from    │
  │               │       candidate pool (hard filter, ADR-0005)      │
  │               │     · personal engagement nudges scoreRecipe()    │  (ADR-0008)
  │               │  7. get_user_cooked_recipe_ids(uid) →            │
  │               │     buildLearningExplanation()  (deterministic)   │
  │               │  8-10. insert; response carries explicacion_      │
  │◀── menu + explicacion_aprendizaje card ─┤     aprendizaje (Pro)   │

  ── the feeder write (update-recipe-status) ──────────────────────────
Client        update-recipe-status Edge Fn        meal_plan_recipes   recipe_learning_trigger
  │ POST {meal_plan_recipe_id, estado, rating?} + JWT ─▶│                │
  │              1. auth — 401                          │                │
  │              2. join slot → meal_plans.user_id      │                │
  │              3. slot.user_id != caller → 403  ◀── the security-critical step
  │              4. estado already terminal → 409       │                │
  │              5. UPDATE estado ─────────────────────▶│ 6. AFTER UPDATE ▶ veces_cocinada++
  │◀── { ok: true, estado } ───────────────────────────┤   (global aggregate on recipes)
```

**Why step 3 of the feeder matters:** without the ownership join, any authenticated user could mutate any slot and pollute the **global** aggregate (`recipes.veces_cocinada` etc.) that every Pro user's next generation reads — a cross-user, product-wide blast radius, not a single-account one. The terminal-state `409` (step 4) prevents double-counting the same signal.
**Feeder hardening (FRESCO-362, audit-4 A4-H1/H2/L7):** `update-recipe-status` now whitelists `estado` against the enum (rejects arbitrary values → `422`), coerces `rating` to an integer in range, re-runs the allergen filter on `nueva_recipe_id` for a `sustituida` swap (a substitute can't reintroduce an allergen) and rejects a duplicate of an existing slot, and carries a 60/hour per-user `enforceRateLimit` (`_shared/rate-limit.ts`) → `429`.
**Why the Pro reads are three separate functions:** `get_recent_recipe_marks` (2-week window, exclusion), `get_user_recipe_engagement` (all-time counts, scoring nudge), `get_user_cooked_recipe_ids` (all-time set, "destacadas" for the explanation) — different windows and semantics, deliberately not one parameterized function (`ADR-0006`, `ADR-0008`).

**Endpoints:** `POST /generate-meal-plan`, `POST /update-recipe-status` — `.context/SRS/api-contracts.md` §1, §4.
**Entities:** as Journey 2, plus `meal_plan_recipes` (write) and `recipes` (trigger-driven aggregate) — `business-data-map.md` §4 (state machine), §5 (triggers).
**Feature IDs:** FEAT-018 (Pro 2-week no-repeat), FEAT-025 (mark cooked/discarded), FEAT-029 (aggregate learning stats), FEAT-030 (Pro history-informed generation), FEAT-031 (learning explanation card), FEAT-032 (free-tier learning notice).

### Journey 4 — Pro subscription lifecycle (Stripe Checkout + webhook)

**Business purpose:** self-serve upgrade to Pro — the epic (FRESCO-227) that reversed the MVP-scope deferral of self-serve payment (`ADR-0007`). Revenue-critical.

```
/profile CTA ──▶ POST /api/stripe/checkout        Stripe            POST /api/stripe/webhook
  │ (SSR session — 401 if none)  │                   │                        │
  │  stripe.checkout.sessions.create({               │                        │
  │    mode:'subscription', price=STRIPE_PRICE_ID_PRO_MONTH,                   │
  │    subscription_data:{trial_period_days:7},                               │
  │    payment_method_collection:'if_required',                              │
  │    client_reference_id = auth.uid() })  ────────▶│ hosted page            │
  │◀── { url } ; client redirects ──────────────────┤                        │
  │                                                  │ checkout.session.      │
  │                                                  │ completed ────────────▶│ verify price ==
  │                                                  │ customer.subscription. │ Pro (else refuse)
  │                                                  │ updated / deleted ────▶│ service_role
  │  return page re-reads user_profiles.plan          │                        │ UPDATE user_profiles
  │  (never writes)                                   │                        │ (plan, stripe ids,
  │                                                  │                        │  plan_expires_at,
  │                                                  │                        │  payment_failed_at)
  ── manage/cancel ──▶ POST /api/stripe/portal (plan must be 'pro' + stripe_customer_id → else 404)
  ── daily drift-correction ──▶ pg_cron ──▶ GET /api/cron/stripe-reconcile ──▶ for each user_profiles row with a
       stripe_subscription_id: stripe.subscriptions.retrieve() → resolveReconciledState() → service_role UPDATE
```

**Why client-unreachable writes only:** two client-reachable writers (browser + webhook) would race a failed/reversed payment into a stuck `plan:'pro'`. The `prevent_client_subscription_writes()` DB trigger enforces that only `service_role` writes the subscription columns, even against a compromised client (`ADR-0007`, `20260818190000`). There are exactly two `service_role` writers: `POST /api/stripe/webhook` (primary, event-driven) and `GET /api/cron/stripe-reconcile` (secondary, daily, drift-correcting — `ADR-0015`, reuses the webhook's `lib/stripe.ts` mappers so the two never diverge byte-for-byte). Full state machine: `business-data-map.md` §4, Flow 7b.
**Endpoints:** `POST /api/stripe/checkout`, `POST /api/stripe/portal`, `POST /api/stripe/webhook`, `GET /api/cron/stripe-reconcile`. No OpenAPI — see `app/api/stripe/*/route.ts`, `app/api/cron/stripe-reconcile/route.ts`.
**Entities:** `user_profiles` (subscription columns) — `business-data-map.md` §2. **Feature IDs:** FEAT-059–063 (`business-feature-map.md`, EPIC-FRESCO-227 — Suscripción Pro; FEAT-063 = the reconciliation job).

### Journey 5 — Weekly re-engagement web push (scheduled, machine-to-machine)

**Business purpose:** nudge the "planificar cada domingo" habit for users who haven't planned this week (FRESCO-241).

```
pg_cron (Sun 18:00 UTC) ──net.http_post(apikey = vault secret)──▶ send-weekly-reengagement-push  (verify_jwt:false)
  1. requireServiceRoleCaller() — apikey == SUPABASE_SECRET_KEYS.default ? else 401
  2. VAPID setup (VAPID_* Edge Function secrets) — else 500
  3. get_push_subscriptions_without_current_plan(iso_week)  (service_role-only RPC)
  4. per row: webpush.sendNotification(...)  ──▶ browser push service (FCM/Mozilla/…)
       404/410 → DELETE push_subscriptions row ; other error → log + skip
  5. { semana_iso, users_targeted, notifications_sent, stale_subscriptions_removed }
```

Opt-in is a per-device toggle on `/profile` that inserts a `push_subscriptions` row directly (RLS `own`, `lib/api/push-subscriptions.ts`).
**Endpoints:** `send-weekly-reengagement-push` (no browser caller); direct `push_subscriptions` insert/delete. **Entities:** `push_subscriptions`, `meal_plans`. **Feature ID:** FEAT-067. **ADRs:** `ADR-0011` (scheduler), `ADR-0012` (`web-push`).

### Journey 6 — Shopping list for the week

**Business purpose:** turn the menu into a shoppable, aisle-ordered, costed list.

```
Client ──▶ POST /generate-shopping-list {meal_plan_id} + JWT
  1. auth — 401
  2. plan.user_id == caller — 404
  3. list already exists — 409
  4. load slots' recipes → consolidateIngredientes() (deterministic) → 422 if empty
  5. classifyShoppingList() (static aisle map + per-unit price) → coste_estimado_min/max
  6. insert shopping_lists.items (jsonb)
  ── later ──▶ jsonb_set_comprado() RPC (toggle) / jsonb_add_item() RPC (add a suggestion) — direct, RLS-scoped
  ── suggestions ──▶ POST /get-shopping-list-suggestions {shopping_list_id} — favorites-derived, real data only
```

**Endpoints:** `POST /generate-shopping-list`, `POST /get-shopping-list-suggestions`; RPCs `jsonb_set_comprado`, `jsonb_add_item`. — `.context/SRS/api-contracts.md` §2–§3; `api/schemas/shopping-list.types.ts`.
**Entities:** `meal_plans`, `meal_plan_recipes`, `recipes`, `shopping_lists`, `favorites`. **Feature IDs:** FEAT-026–028, FEAT-194-carousel.

### Sub-flow (of J2/J3) — Food-safety guardrail

**Business purpose:** a declared allergen or hated ingredient must never reach a plate via a generated menu — a failure here is a health/safety incident.

```
generate-meal-plan                              Postgres
  get_filtered_recipes(user_id) ──────────────▶ structural SQL exclusion:
    not (recipes.alergenos ?| profile.alergenos)
    AND (dieta_* flags satisfied)
    AND not (recipes.ingredientes_principales ?| profile.ingredientes_odiados)
  IF < 21 survive → 422 (hard stop — no degraded menu is ever generated)
  IF a single slot's scored pool is empty → NO_SAFE_RECIPE_SENTINEL
    + a templated advertencias entry → surfaced as a prominent AlertBanner (FR-8.2)
```

**Now single-layer.** The prior design had a second, model-prompt layer ("REGLAS ABSOLUTAS"); it went away with Gemini (`ADR-0005`; `business-feature-map.md` FEAT-058 flags this explicitly). `get_filtered_recipes()` is the sole enforcement point, and it fails closed. The founder-run manual food-safety checklist (FR-8.3) is an additional, out-of-band backstop, not part of the API.
**Code:** `supabase/migrations/20260725120100_create_fresco_core_tables.sql` (`get_filtered_recipes`), `20260726000000_fix_get_filtered_recipes_keto_halal.sql`, `20260804010000_add_recipe_id_param_to_get_filtered_recipes.sql`.
**Feature IDs:** FEAT-058 (allergen), FEAT-059 (hated-ingredient).

| Component | Role | Persistence / Integrations touched | Why it matters for dev |
|---|---|---|---|
| Client (Next.js / Vercel) | RSC pages do RLS-scoped reads directly; client components call Edge Functions + RPCs; holds the JWT via `@supabase/ssr` | Postgres (RLS reads), Edge Functions, Route Handlers | Frontend and Edge Functions are **separate deploys** — an Edge Function fix doesn't need a frontend redeploy. A `401` from any Edge Function is caught once in `lib/api/edge-functions.ts` and redirects to `/login?session_expired=1` |
| Supabase Edge Functions (Deno) | Auth, ownership checks, orchestration, deterministic selection/consolidation, persistence, and every cross-user-privileged operation | Postgres (read/write via request-scoped or service-role client), `web-push` (one function), and — since 2026-08-30 — Sentry + PostHog EU as outbound telemetry from every function | **This is where a new food-safety-critical or cross-user endpoint belongs.** Unit-testing one means mocking a Supabase client *and* stubbing the Sentry/PostHog transports (`_shared/sentry.ts` fires on unexpected 500s via `_shared/http.ts`; both silent on failure). CI type-checks + lints them via `deno.json` + the `deno:check` gate (FRESCO-375); an edge-function-drift gate redeploys changed functions on `push: [staging]` (FRESCO-414) |
| Next.js Route Handlers | Stripe session creation + webhook + daily reconciliation cron, RLS-scoped data export, auth-email confirmation | Stripe SDK (`lib/stripe.ts`), Postgres (SSR client for reads, `lib/supabase/service.ts` for the webhook's and the reconcile cron's writes) | New payment/billing logic and anything needing Node APIs or the Stripe SDK goes here, not an Edge Function. `lib/supabase/service.ts` (RLS-bypassing) is imported from exactly two Route Handlers — the Stripe webhook and `GET /api/cron/stripe-reconcile` — both writers of the subscription columns (`ADR-0007`, `ADR-0015`) |
| Direct-to-Postgres (RPC + table) | Pure per-household state with no cross-cutting rule: favorites, purchased-item toggle, personal recipes, delete-a-week, push opt-in, aviso dismissal | Postgres only, RLS `*_own` policies / SECURITY DEFINER ownership re-checks | **Do not** route these through an Edge Function — there's no orchestration to own. New RPCs must follow `20260801010000_harden_security_definer_functions.sql`: explicit `revoke ... from public` then `grant` to the intended role, and an `auth.uid()` check in the body |
| Postgres (1 project) | System of record + scheduler + secret store | `pg_cron`, `pg_net`, `supabase_vault`, `pg_trgm`; `recipe_learning_trigger` owns the learning aggregate; `prevent_client_subscription_writes` owns the ADR-0007 invariant | Business rules that must hold regardless of caller live in triggers/DEFINER functions, not app code. All three environments hit the **same** DB — a staging test writes production rows |

There is no API gateway, load balancer config, or service mesh. Deploys are independent Supabase artifacts (`supabase functions deploy`) + one Vercel deploy — consistent with a solo-founder operating scale.

## 7. Discovery Gaps

> MANDATORY — anything not verified end-to-end.

1. **No OpenAPI spec.** Every "endpoint" reference above points at `.context/SRS/api-contracts.md` or `api/schemas/*.types.ts`, not a schema registry. `bun run api:sync` maintains the types by hand from a script, not from a spec. Re-run this map if a real spec appears.
2. **`generate-shopping-list` has no rate limiting yet.** `generate-meal-plan` got its 5 req/user/hour limit deployed 2026-08-28 (`FRESCO-243` / `ADR-0010` — shared `rate_limits` table + atomic `check_and_increment_rate_limit` RPC, `cleanup-expired-rate-limits` `pg_cron`, 4 test-account UIDs short-circuited). `generate-shopping-list` is the obvious next adopter of the same RPC (SRS `NFR-SEC-6`).
3. **Subscription reconciliation — RESOLVED (`FRESCO-301`, `ADR-0015`), two residual unknowns.** The "missed webhook drifts `user_profiles` silently and forever" gap is closed: `GET /api/cron/stripe-reconcile` runs daily via `pg_cron` + `pg_net` and self-heals drift within 24h (§3 J4, §5, `20260828174500`, `data-map.md` Flow 7b). Residual: (a) the route's `Authorization: Bearer <CRON_SECRET>` check depends on a Vercel Production env var + a matching Supabase Vault secret (`stripe_reconcile_cron_secret`), both manual out-of-band steps — the `cron.job` row was confirmed present via Supabase MCP but neither secret's population was verified this pass; if either is missing the job `401`/`500`s and silently no-ops daily. (b) `ADR-0015`'s own Status field still reads `Proposed` despite the migration + route being live — a doc/reality mismatch worth closing. **The same is now true of `ADR-0022`** (guest reassignment via session token): the `{targetAccessToken}` contract is deployed and verified in code this pass, but the ADR is still `Proposed`.
4. **One Supabase project for all three environments.** `local`, `staging` (`fresco-pre.vercel.app`), and `production` (`fresco-pro.vercel.app`) all use ref `jdqemhewjrjuopssdurn` (`.agents/project.yaml`, deliberate). Any staging API call mutates production data. The live DB holds 20 `user_profiles` / 27 `auth.users` (20 anonymous guest sessions) as of 2026-09-03 (`supabase db query --linked`) — a test/production mix, trimmed down from the 2026-08-30 snapshot by the nightly abandoned-guest cron.
5. **No single environment resolver.** `lib/urls.ts` was deleted (dead code). `lib/stripe.ts` `resolveWebhookSecret()` resolves the Stripe secret per `VERCEL_ENV` + branch; `_shared/cors.ts` carries its own hardcoded origin allowlist; `.agents/project.yaml` `environments:` has `local`/`staging`/`production` but no `dev`. Each concern resolves its own environment — worth consolidating.
6. **`delete-catalog-recipe` is deployed** (`verify_jwt: true`, version 3, `status: ACTIVE` — re-confirmed via Supabase MCP `list_edge_functions` this pass, commit `81f8bd6`), gated by `requireAdminUser()` against the `ADMIN_USER_ID` allowlist (`hola.frescoapp+admin@gmail.com`). Full `/admin/recipes` delete flow still wants an in-app test with a real admin session.
7. **`send-weekly-reengagement-push` auth depends on a manually-created Vault secret** (`edge_function_secret_key`, `sb_secret_...`). `cron.job` shows the schedule + `apikey` header wired; the secret's actual presence in `vault.decrypted_secrets` was not verifiable this pass. If absent, the job runs weekly and every send silently 401s.
8. **`sustituida` estado has no live API caller found.** `update-recipe-status` accepts `estado='sustituida'` + `nueva_recipe_id`, but the calendar uses `swap_meal_plan_slots` for reordering and no component issuing the `sustituida` call was located. Possibly dead or planned.
9. **`update-recipe-status` is a `POST` acting as a semantic `PATCH`** (per `api-contracts.md` §4 and `business-feature-map.md` §4). Documented, but worth noting for anyone generating a client from method semantics.
10. **`/auth/confirm` open-redirect guard** rejects protocol-relative `next` paths (`//evil.com`) and only accepts in-app relative paths (`app/auth/confirm/route.ts`) — verified in code, no separate test evidence reviewed.
11. **0 Pro/Family users in the live DB** (re-confirmed 2026-09-03 — `select count(*) from user_profiles where plan in ('pro','family')` → 0) — the entire Pro API surface (the fork in J3, the Billing Portal in J4, `get_user_recipe_engagement`, the payment-failed path) is unexercised against real subscription data.

Guest reassignment (J1b) and the guardrail are documented as sub-flows rather than padding the count.
