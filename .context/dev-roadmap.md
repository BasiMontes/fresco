## 2. Epic backbone — the schema-forced spine

**Master Sprint 0** (`EPIC-FRESCO-4`, `EPIC-FRESCO-6`, `EPIC-FRESCO-8`), **Master Sprint 1** (`EPIC-FRESCO-10`, `EPIC-FRESCO-12`, `EPIC-FRESCO-14`), and **Master Sprint 2** (`EPIC-FRESCO-16` Guest Mode, `EPIC-FRESCO-18` Progressive Signup) are all now seeded in the issue tracker — Master Sprint 2 was seeded since this doc's last sync but never reflected here (found this pass via a full `issuelinks` re-fetch; see §3 for the recovered edges).

Master Sprint 0 spine forced by `business-data-map.md` §2 entity topology: `user_profiles` (Onboarding) and the allergen/disliked-ingredient exclusion guarantee that filters `recipes` (Food-Safety Guardrail) both must exist before `meal_plans` / `meal_plan_recipes` can be created (AI Weekly Menu Generation) — neither predecessor depends on the other.

Master Sprint 1's three epics all extend the same table `meal_plan_recipes` that Menu Generation creates as a side effect of persisting a plan (`master-implementation-plan.md` §4) — none of the three needs the others to exist, they only share the one upstream predecessor.

Master Sprint 2's two epics are sequential, not parallel: Progressive Signup is literally "what happens after a guest sees value" (`master-implementation-plan.md` §3) — there is no guest flow to attach a signup prompt to until Guest Mode exists.

Two epics — **EPIC-FRESCO-49** (Información Legal y Contacto) and **EPIC-FRESCO-50** (Recuperación de Contraseña) — were added in an earlier pass via `/product-management` Workflow B. Neither is part of the original 8-epic MVP plan in `master-implementation-plan.md`; both are organic post-MVP additions with no Master Sprint assignment.

**EPIC-FRESCO-54** (Panel de Inicio) was seeded AND fully shipped earlier in this same 2026-08-03 session, but this doc's own "re-run at the end of every Workflow B/C" trigger (§7) was missed until now — recorded retroactively. Its 5 stories read across three existing domains (`user_profiles` for the greeting, `get_filtered_recipes()` for the recipe-count and latest-recipes cards, `meal_plans` for the Calendar-suggestion banner's target screen) without writing new schema — a redesign/aggregation epic, not a new-entity one, so it has no single forced predecessor the way Master Sprint 0→1 does. It depends on the three epics whose data it reads.

**EPIC-FRESCO-64** (Biblioteca de Recetas) is new this later pass, also via Workflow B — user mockup: search, meal-type tabs, cuisine/diet/allergen filters, and a personal "create your own recipe" capability over `/recipes`, reframed from "recipes you've cooked" (`getUserRecipes()`) to full-catalog discovery ("Biblioteca — inspiración basada en tu stock"), consistent with the `get_filtered_recipes()` pattern EPIC-FRESCO-54 already established. A real architectural gap was resolved BEFORE story-writing, not invented: `recipes` is documented (`business-api-map.md`) as owned by exactly 3 actors (generator, learning trigger, founder's batch-seed) — a user-authored recipe would be a 4th, undocumented actor. User confirmed (AskUserQuestion) a created recipe is personal-library-only, never feeds the AI generator, and needs none of the catalog's food-safety fields — this keeps the new capability structurally separate from `recipes` (a new table, out of `get_filtered_recipes()`'s reach entirely) rather than extending the founder-owned catalog.

**EPIC-FRESCO-60** (Control del Menú Semanal) is new this pass — also via Workflow B. It extends `/calendar` with week navigation, plan deletion, and on-demand regeneration for any viewed week. All three capabilities reuse existing infrastructure verified during this pass's Phase 1 complexity analysis: `getMealPlanForWeek(client, semanaIso)` already accepts an explicit week, `meal_plans` already has `delete` granted + an RLS `delete_own` policy, and `generate-meal-plan`'s Edge Function already takes `semana_iso`/`fecha_inicio` as parameters (not hardcoded to "this week") and already guards against regenerating over an existing plan. It is a frontend-wiring epic on top of EPIC-FRESCO-6's data model — same forcing relationship as Master Sprint 1's three epics, not a new spine branch.

**EPIC-FRESCO-81** (Cuenta y Sesión) is new this pass (2026-08-08). Reads the existing auth session (`auth.uid()`, `user_profiles.plan`) — no new table, no new RLS. No epic-level Jira link created (matches how FRESCO-54/60/64 are also reasoned from the data-map rather than a literal epic-to-epic link).
