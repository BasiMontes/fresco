## §1. Where This App Actually Is

Read `business-feature-map.md` before this document if you haven't — it's the ground truth this plan is built on. The short version: Fresco has 61 catalogued features across 15 domains, 47 of them "Stable" and exercised by a QA regression suite with 100 scenarios. Onboarding, deterministic menu generation, the editable calendar, the shopping list, the recipe catalog (1000 recipes) plus a personal-recipe library, favorites, full profile self-service (including account deletion and JSON export), and the Pro-tier learning loop are all live in production-adjacent staging. Guest mode and progressive signup — the two epics the pre-code version of this plan flagged as blocked on an unresolved auth decision — shipped via ADR-0003 and ADR-0004. Gemini, the only external AI dependency this system ever had, was fully removed from the generation and shopping-list paths on 2026-08-01 (ADR-0005) and from the Pro-tier explanation text the same day (`ae3b560`); Fresco today makes zero external LLM calls in production. Two full QA sweeps (20 tickets, then 9 more) found and closed real defects, the most significant being ADR-0006 — a same-week fix that made the Pro "learns from what you cook" promise literally true instead of aggregate/copy-only.

## §3. What To Implement First And Why

### Production environment provisioning (Master Sprint 0)

**Why it matters:** `mvp-scope.md`'s entire Success Criteria section is written in terms of a concierge cohort "paying and repeating 3+ weeks" — a metric that requires a real environment distinct from the founder's own staging/testing target. This has been an open gap since the very first version of this plan (§12 there, unresolved for two weeks of shipping) and nothing about it is blocked on code; it's the one item on this list that is purely a provisioning decision, which is exactly why it's first.

**What it unblocks:** every other production-readiness item on this list (legal sign-off has no launch to gate; photo-backfill "completeness" has no real audience yet) and, transitively, the MVP's own go/no-go decision.

**Dependencies:** none technical. `lib/urls.ts` already deliberately throws on `VERCEL_ENV=production` rather than guessing a URL — the code is written defensively for this day, it's just never been given a real target.

**How an experienced engineer would scope it:**
- Smallest credible slice: a second Vercel project (or a `production` target on the existing one) + a decision on whether production gets its own Supabase project or a hardened version of the current one, then fill the `production:` block in `.agents/project.yaml`.
- Likely scope creep: don't let this balloon into "redesign the whole environments model" — the `local`/`staging` split already works, this is additive.
- Boundary with next sprint: this item stops at "a real URL exists and the app runs against it." It does not include the legal or photo-completeness gates below — those are separate checklist items that happen to share a launch date, not the same piece of work.

### Legal content sign-off (Master Sprint 0)

**Why it matters:** the app's own UI (`LegalModal`) tells every visitor the Terms/Privacy content is a draft pending legal review. Onboarding a real paying cohort against that banner is a real business risk, not a cosmetic one.

**What it unblocks:** production launch to anyone outside the founder.

**Dependencies:** production environment existing to launch into (no point finalizing copy for a target that doesn't exist yet, though the review itself can happen in parallel).

**How an experienced engineer would scope it:**
- Smallest credible slice: get the existing draft reviewed and either approved or corrected — the content structure (`components/legal/legal-modal.tsx`) already exists and doesn't need rebuilding, only its text does.
- Likely scope creep: resist rewriting the modal's UI/UX while you're in there — this is a content task, not a feature task.
- Boundary with next sprint: once the banner comes down, this is done. Don't fold in a real contact-form build (`FEAT-050`'s `mailto:` link is explicitly descoped and out of scope here too).

### Recipe photo backfill completion (Master Sprint 0)

**Why it matters:** this is the one item on the list that's already a running, well-understood process — `fetch-recipe-photos.ts` (v8) is a mature script with real learnings baked in (query translation, Unsplash burst-limiter pacing, duplicate-avoidance), not a design problem. 663/1000 recipes have photos; a food-planning app's first impression on a real cohort benefits from a visually complete catalog.

**What it unblocks:** nothing else technically depends on this — it's parallel, ungated work, same as the old plan's batch-seeding track — but it's worth finishing before, not after, a real cohort sees the catalog.

**Dependencies:** none beyond Unsplash's free-tier rate limit (50 req/hour), which is the reason this has been running in ~30-recipe batches across multiple sessions rather than as a single job.

**How an experienced engineer would scope it:**
- Smallest credible slice: keep running the existing batch process until the remaining 337 are exhausted or the pool of matchable queries runs dry — no new code needed.
- Likely scope creep: don't build a "photo re-review/replace" UI for this — that's a different, unrequested feature.
- Boundary with next sprint: this has no "next sprint" boundary — it's the one item here that's genuinely just finishing an in-flight task, not scoping a new one.

### `recipes` DELETE path (Master Sprint 0)

**Why it matters:** every other user-owned or system-owned entity in the CRUD matrix has a real path to every verb except `recipes` — and that gap has been carried forward, unresolved, since before the catalog even had 35 rows. At 1000 rows the absence is more consequential: a bad or duplicate AI-generated recipe (FRESCO-122 already found and fixed one class of data-quality issue at this scale — a `dificultad` enum mismatch affecting 228 recipes) has no fix path except undocumented raw SQL against `service_role`.

**What it unblocks:** real catalog maintainability without a human needing direct DB access for routine curation.

**Dependencies:** a founder decision, not an engineering unknown — is manual `service_role` SQL an acceptable permanent answer (matching Flow 4's existing human-in-the-loop posture for recipe *creation*), or does this need a real admin path?

**How an experienced engineer would scope it:**
- Smallest credible slice: if the founder wants a real path, a `service_role`-only admin script (mirroring the existing batch-seeding tooling's trust model) is far cheaper than an in-app admin UI and matches how every other recipe-catalog write already happens.
- Likely scope creep: do not build a full admin dashboard for this unless explicitly asked — the existing pattern (offline, founder-operated, `service_role`) has held for every other catalog-write operation so far.
- Boundary with next sprint: this is scoped to `recipes` only — `recetas_propias`' missing UPDATE/DELETE (next sprint) is a different table with a different trust model (user-owned, not founder-curated) and should not be solved by the same mechanism.

### `recetas_propias` UPDATE/DELETE (Master Sprint 1)

**Why it matters:** this is the one CRUD gap in the entire app that isn't a deliberate scope cut with a documented reason — `recipe-detail.tsx:133`'s "OOS" comment covers edit/delete/rate/menu-add/share together, but delete-your-whole-account is a disproportionate fix path for "I made a typo in my own recipe."

**What it unblocks:** self-service parity — every other user-owned table (`user_profiles`, `favorites`, `meal_plans`) already has this.

**Dependencies:** none structurally new — `recetas_propias` already has RLS `own` policies for INSERT/SELECT; UPDATE/DELETE policies follow the same pattern.

**How an experienced engineer would scope it:**
- Smallest credible slice: reuse `CreateRecipeForm`'s validation (name ≤100 chars, touched-gating) in an edit mode, plus a delete confirmation matching the existing `DeleteAccountDialog`/`DeleteWeekButton` conventions (this codebase alternates between immediate-delete and confirm-gated delete depending on reversibility — a personal recipe delete is closer to `DeleteWeekButton`'s "immediate, no dialog" precedent than `DeleteAccountDialog`'s "type your email" one, since it's not irreversible-and-account-wide).
- Likely scope creep: don't reopen "add rate/menu-add/share" — those stay out of scope per the existing documented decision; this item is UPDATE/DELETE only.
- Boundary with next sprint: stops at the personal-recipe table. Does not touch `recipes` (previous sprint, different trust model).

### Notifications: build minimal-real or retire the slot (Master Sprint 1)

**Why it matters:** this is the one place in the shipped app where a real, always-visible piece of UI (the bell icon, wired into both `Sidebar` and `BottomTabBar` navigation) does structurally nothing. That's a worse trust signal than not having the feature at all — a user who taps it and finds a permanent empty state may reasonably wonder what else in the app is decorative.

**What it unblocks:** either removes a "looks broken" surface from the shipped app, or opens a genuine, currently-unplanned engagement channel (e.g., "your weekly menu is ready," "you haven't marked anything cooked this week" — real events the app already has data for, unlike the mockup's pantry-expiration framing which was confirmed to have no backing feature).

**Dependencies:** a product decision first (§9) — this is not an engineering unknown, it's a scope question nobody has explicitly answered yet.

**How an experienced engineer would scope it:**
- Smallest credible slice, if building: pick one real, already-available event (menu-generation completion is the cheapest — the data already exists at the moment `generate-meal-plan` succeeds) rather than designing a general notification system.
- Smallest credible slice, if retiring: remove the nav icon and route, or replace it with an honest "Próximamente" treatment matching FEAT-048's existing pattern for the Pro upsell card — that pattern already exists in this codebase for exactly this situation.
- Likely scope creep: a general-purpose notification *system* (preferences, push, email digests) is a much bigger build than either option above — don't let "let's build notifications" become that without an explicit ask.
- Boundary with next sprint: this item stops at a decision + its minimal implementation. It does not extend into the guest-cleanup or personalization items below.

### Guest anonymous-session cleanup (Master Sprint 1)

**Why it matters:** ADR-0003 named this explicitly as a real, unsolved operational task — Supabase provides no built-in garbage collection for anonymous users, and every guest who generates a menu but never converts leaves a permanent row in `auth.users`. This has been true since guest mode shipped and has had no urgency at staging-only traffic, but that changes once real cohort traffic exists.

**What it unblocks:** bounded `auth.users` growth ahead of real launch traffic — not urgent today, genuinely relevant once production exists.

**Dependencies:** production environment existing first — there's little value cleaning up staging test accounts on a schedule.

**How an experienced engineer would scope it:**
- Smallest credible slice: a scheduled job (Supabase's `pg_cron` extension, already available on the platform per the `supabase` skill's own coverage) that deletes anonymous `auth.users` rows older than some threshold with no linked identity — reuses `auth.admin.deleteUser()`, the same primitive `delete-account`/`reassign-guest-data` already call.
- Likely scope creep: don't build a general "data retention policy" system — this is one narrow, named cleanup task.
- Boundary with next sprint: this is infrastructure hygiene, not user-facing — it has no interaction with the Notifications or `recetas_propias` items above.

## §4. Master Sprint Structure

**Master Sprint 0 — Make the app launchable, not just built.** Scope: production environment provisioning, legal sign-off, recipe photo backfill completion, and a decision on `recipes` DELETE. None of these four are interdependent in the code sense — they're grouped because they're all prerequisites to the same event (a real cohort seeing the product), not because one blocks another technically. "Done" looks like: a production URL exists, the legal banner is gone, the catalog is visually complete enough to show a stranger, and the founder has a real answer (even if "raw SQL is fine for now") to "how do I remove a bad recipe." Size signal: three of the four items are decisions/provisioning, not code — this sprint is lighter on engineering effort than any prior Master Sprint in this project's history, and heavier on founder/product decisions.

**Master Sprint 1 — Close the remaining self-service and trust gaps.** Scope: `recetas_propias` UPDATE/DELETE, the Notifications decision + minimal build, and guest-session cleanup. These three are genuinely independent of each other — grouped only because they're the next tier of "real, named, currently-open gaps" after Master Sprint 0's launch blockers. "Done" looks like: a user can fix her own typo'd recipe without nuking her account, the bell icon either does something real or honestly says it doesn't yet, and abandoned guest sessions stop accumulating unbounded. Size signal: comparable to a single prior epic (e.g., EPIC-FRESCO-14's learning toggle) in total scope, spread across three small, unrelated slices.

**Deferred, not scheduled — `scoreRecipe()` per-user personalization.** ADR-0006 named this explicitly and explicitly declined to scope it alongside the FRESCO-120 fix ("a separate, larger change"). It doesn't get a Master Sprint number here because there's no committed timeline for it — it's flagged so a future planning pass doesn't have to re-discover it from the ADR.

## §5. Features / State Machines That Block ≥2 Other Features

- **`recipes` as shared infrastructure — now with a fourth owner.** The prior version of this plan named three owners (`generate-meal-plan` reads it, `recipe_learning_trigger` writes aggregate columns, the founder's batch-seeding process writes new rows). A fourth is now real: the photo-backfill script (`fetch-recipe-photos.ts`) writes `foto_url` directly via `service_role`, and FRESCO-122's `dificultad` data-migration already had to touch this same table independently of all three other owners. Any future schema change to `recipes` — including the proposed `recipes` DELETE path above — has to be checked against all four write paths, none of which is aware of the others by construction.
- **`auth.users` / anonymous-session identity** blocks or touches five separate features that don't otherwise share code: guest logout confirmation (FEAT-010), guest-to-account conversion (FEAT-003), guest-data reassignment on email conflict (FEAT-004), account deletion (FEAT-011), and the proposed guest-session cleanup job (§3). A change to how anonymous identity is represented would ripple through all five without any single owning epic.
- **`meal_plan_recipes.estado`** remains the single most load-bearing state machine in the system (unchanged from the prior plan's finding) — and is now also the direct dependency of any future `scoreRecipe()` personalization work, since a per-user quality signal would have to be derived from exactly this table, the same one the calendar (EPIC-3) and learning loop (EPIC-5/ADR-0006) already both depend on.

## §6. Hidden Dependencies

**The `recipes` table's four owners are on a collision course the moment DELETE is built.** If `recipes` DELETE ships (Master Sprint 0), it must account for: rows currently referenced by `meal_plan_recipes` (historical menus shouldn't break), rows referenced by `favorites`, and rows the photo-backfill script has mid-batch open in a separate process. None of these three consumers currently has a reason to know a delete path exists — this is exactly the kind of cross-epic coordination cost the prior plan's §6 warned about for schema changes, now concretely relevant to a specific upcoming item rather than a hypothetical.

**Notifications, if built for real, inherits every domain it would notify about.** A "your menu is ready" notification needs to hook into `generate-meal-plan`'s success path (Menu Generation domain); "you haven't marked anything cooked" needs read access to `meal_plan_recipes.estado` (Calendar + Learning domains). This means the Notifications decision in §3 isn't actually a standalone Profile/Navigation-domain feature the way FEAT-051's current placement suggests — building it for real would make it a cross-cutting consumer of at least two other domains' internal state, which is exactly the kind of coupling that doesn't show up if it's scoped in isolation from wherever it happens to be triaged.

**Guest-session cleanup and account deletion share a primitive but not a trust boundary.** Both ultimately call `auth.admin.deleteUser()`, but `delete-account` is user-initiated and RLS/ownership-checked at the Edge Function layer, while a cleanup cron would need to run with `service_role` on a schedule, selecting *which* anonymous users qualify without any user in the loop to confirm. Reusing the same underlying call is fine; conflating the two code paths' trust models would not be — worth naming explicitly since a hasty implementation might reach for `delete-account`'s existing code as a shortcut when it isn't actually the same operation.

## §9. Edge Implementation Cases

- **`scoreRecipe()` personalization is a named-but-unscoped architectural decision, not a normal backlog item.** ADR-0006 states plainly that making the global quality heuristic per-user "would need per-user rating storage, not just the aggregate `recipes` columns" and calls it out of scope for that fix. Whoever picks this up next should treat it as requiring its own ADR-style design pass (schema shape for per-user stats, how it interacts with the existing `recipe_learning_trigger`), not as a drop-in enhancement to `menu-selector.ts`.
- **Notifications is genuinely undecided between two legitimate approaches**, not a case where one option is obviously correct: build a minimal real notification type (engineering cost, real engagement value) vs. formally retire the nav slot (near-zero cost, removes a "looks broken" surface but forecloses the channel). `business-feature-map.md` §8 gap #8 explicitly frames this as "track as a genuine backlog item, not a defect" — meaning nobody has made this call yet, and it shouldn't get made implicitly by whoever happens to touch that file next.
- **`recipes` DELETE sits at a genuine permission-boundary question.** Every other write to `recipes` (create via batch-seeding, aggregate-column updates via the learning trigger) is either `service_role`-only or system-triggered — there is no precedent anywhere in this schema for an authenticated (non-founder) user having any write access to this table. Building anything beyond a `service_role` admin script would be introducing a new permission tier that doesn't exist yet anywhere else in the app, worth flagging explicitly before it's built as a side effect of "just add a delete button."
- **Guest anonymous-session cleanup has no existing precedent for "who decides the retention threshold."** ADR-0003 flags the gap but doesn't propose a number of days — this is a genuine open question (too aggressive and a guest who returns after a week loses her menu; too lenient and the table grows unbounded) that needs an explicit answer, not a default picked silently inside a migration.
- **Free/Pro remains a business-logic branch, not an auth tier** (restated from the prior plan, still true, and newly relevant to the Notifications decision above) — if a "you're eligible for the Pro learning explanation" notification is ever built, it must reuse the same server-side `isPro` check every other Pro-gated surface uses, not introduce a new permission concept.

## §10. Pre-Ship Checklist

- Every new migration in `supabase/migrations/` must be confirmed applied against the real DB (`list_migrations` via Supabase MCP) before a story is called done — the repo can silently hold `.sql` files that were never run.
- Every new or changed Edge Function must be confirmed deployed and `ACTIVE` (`list_edge_functions` via Supabase MCP) — code can exist in the repo and never reach production.
- Any new table with RLS needs **both** the RLS policies **and** the table-level `GRANT` to `authenticated` (and `anon` if the table is guest-reachable) — RLS without the GRANT blocks everything just as thoroughly as the GRANT without the right policy does; this exact gotcha is already documented as a live-testing finding in `regression.feature`'s infrastructure notes.
- Any new `security definer` function that crosses a caller/target-user boundary must replicate the `auth.uid()` ownership check pattern established by `swap_meal_plan_slots` (ADR-0002), `reassign_guest_data` (ADR-0004), and `get_recent_recipe_marks`/`get_user_cooked_recipe_ids` (ADR-0006) — `security definer` bypasses RLS, so this check is the only thing standing between the function and a cross-user data leak.
- Any write path that relocates an existing `meal_plan_recipes.recipe_id` between slots without a genuine cook/discard action must disable `recipe_learning_trigger` for that transaction (ADR-0002's invariant) — a new feature that "moves" a recipe (e.g., a future substitute affordance) that skips this will silently corrupt the Pro-tier learning counters.
- No Free-tier code path may pass cooked/discarded history into generation — this is now a hard filter, not a prompt instruction (ADR-0005), but the invariant itself (ADR-0001) still has to be verified explicitly on any change to `menu-selector.ts`, not assumed correct because the `isPro` branch exists.
- A component with an `onClick`/event handler, rendered directly from a Server Component page without `'use client'`, compiles and typechecks cleanly but crashes the entire page at runtime ("Event handlers cannot be passed to Client Component props") — this is a real bug class found live in this codebase (`RecipeCard`, undetected from FRESCO-69 in 2026-08-03 until a live QA pass days later); typecheck-clean is not sufficient evidence a new component is safe.
- Confirm the legal-content draft banner is removed only after real sign-off, not as part of an unrelated content edit that happens to touch `LegalModal`.
- Confirm `.agents/project.yaml`'s `production` block is filled and `vars:check` passes before pointing any real traffic at it.
- Any Unsplash-key-bearing script (`fetch-recipe-photos.ts`) must never run from client code or a public route — it's already correctly isolated as a local dev script, verify any future automation of it preserves that.
- Before extending the `recipes` schema for any reason (DELETE support included), check it against all four current write owners named in §5 — generation reads, the learning trigger, the founder's batch-seeding process, and the photo-backfill script.
- If a guest-session cleanup job ships, dry-run it against a read-only query first and confirm the retention threshold (§9) was an explicit decision, not a default.

## §11. What Is NOT In Scope

This document sequences **what** to build and **why it's next**, not **how** to build each item. The following belong to other tools/skills in this workflow, not to this plan:

- Per-story implementation plans, acceptance criteria, and code-level scoping → `/sprint-development` (Planning stage)
- Story refinement, INVEST/AC quality, edge-case enumeration → `/product-management`
- Ticket-level dependency sequencing and execution-sprint ordering (which Jira story unblocks which, in what order) → `/dev-roadmap`
- Entity/flow/state-machine detail → `business-data-map.md`
- Feature-by-feature inventory and CRUD/API detail → `business-feature-map.md`, `business-api-map.md`

### Deferred / won't-do

- **Self-serve Pro payment/billing integration** — `mvp-scope.md` is explicit that this belongs to the founder's manual concierge process for the life of this MVP; the disabled "Próximamente" card (FEAT-048) is the intended, permanent-for-now state, not a placeholder awaiting a build.
- **Curated, professionally-photographed recipe library** — cut for cost reasons at MVP scale (`mvp-scope.md` — Deferred to P1); the AI-generation-plus-manual-review process plus the ongoing Unsplash backfill are the deliberate substitute for this MVP's lifetime.
- **Receipt scanning, price comparison, pantry/inventory management, aggressive push notifications, voice operations, complex local-first architecture, price learning, leftover-ingredient AI, batch-cooking mode, expiration alerts, supermarket integrations, gamification, community/social features, recipe marketplace, native app before 1,000 paying users, B2B before B2C validated** — the full `mvp-scope.md` Out-of-Scope Blacklist, unchanged; none of it is reconsidered by anything in this plan, and all of it stays excluded until both MRR > €5,000 and 30-day retention > 50% are met.
- **A general-purpose notification system** (preferences, push, email digests) — only a single minimal real notification type, if any, is in scope per §3; a full system is explicitly not being proposed here.

## §12. Implementation Gaps

- **Spike: production environment topology.** Decide separate-vs-shared Supabase project, real domain, and Vercel production target; fill `.agents/project.yaml`'s `production` block. **Blocks Master Sprint 0** — every other item in that sprint is more urgent once a launch date exists, and this is the one item with zero code dependency standing in the way.
- **Spike: `recipes` DELETE mechanism.** Founder decision needed — is `service_role`-only raw SQL (matching the existing recipe-creation trust model) acceptable long-term, or does this need a real admin path? Genuinely unresolved, not an engineering unknown.
- **Spike: `recetas_propias` UPDATE/DELETE design.** RLS policy shape + which existing delete-confirmation pattern (`DeleteWeekButton`'s immediate delete vs. `DeleteAccountDialog`'s type-to-confirm) fits a personal-recipe delete before writing any code.
- **Spike: Notifications — build-minimal-real vs. formally retire.** No decision exists yet; `business-feature-map.md` explicitly flags this as an open backlog item, not a defect with an obvious fix.
- **Spike: guest anonymous-session cleanup job design.** Retention threshold, cron mechanism (`pg_cron` vs. a manually-triggered script), and confirmation that it can't be conflated with `delete-account`'s user-initiated, RLS-scoped trust model (§6).
- **Spike: legal content real review.** Not an engineering task at all, but it's a real, named blocker to production launch and belongs on this list so it isn't silently forgotten once the technical items are done.
- **Spike: `scoreRecipe()` per-user personalization.** Explicitly deferred by ADR-0006 as "a separate, larger change" needing new per-user rating storage — worth a dedicated design pass (possibly its own ADR) before any implementation attempt, not a drop-in change to the existing scoring function.
- **Spike: numeric capacity/latency targets.** Carried forward from the pre-code plan, still genuinely open — there is still no defined concurrent-user capacity target or p50/p99 latency figure for either generation (now sub-second per ADR-0005, but no formal target was ever set) or shopping-list generation specifically. Lower urgency now that generation is empirically fast, but still a real gap worth naming before any post-launch scale-up planning.
