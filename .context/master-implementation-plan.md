## §1. Where This App Actually Is

Read `business-data-map.md` (rebuilt from running code on 2026-08-28) and `business-feature-map.md` before this document — they are the ground truth this plan sits on. The short version, updated since the 2026-08-08 plan:

**Production exists now.** `.agents/project.yaml` carries a real, auto-following `production` environment (`https://fresco-pro.vercel.app`) that always tracks the latest `main` Production deploy, alongside `staging` (`https://fresco-pre.vercel.app`). Production and staging deliberately share one Supabase project (a founder decision recorded in the prior version of this §3 — no isolation split). That decision was formally ratified and closed as **FRESCO-328** (2026-08-31, `Finalizada`, label `gated-pro`): isolation is deferred until real launch, when the org moves to Supabase Pro anyway — an extra reason being that Supabase Free pauses a project after 7 days of inactivity, so an isolated pre-launch prod project would keep going dark. The single biggest blocker in the last plan — "there has never been a place to run the concierge cohort" — is resolved.

**Fresco is monetized.** EPIC-FRESCO-227 shipped the entire Pro subscription path (`ADR-0007`, data-map Flow 7): Stripe hosted Checkout (`POST /api/stripe/checkout`), a webhook that is the **sole writer** of subscription state onto `user_profiles` (guarded by the `prevent_client_subscription_writes()` BEFORE UPDATE trigger), the Billing Portal (`/api/stripe/portal`), failed-payment / dunning handling (`payment_failed_at`), a 7-day no-card trial, and a daily reconciliation cron that re-syncs `user_profiles` against Stripe for any missed webhook (FRESCO-301, `ADR-0015`). There are **0 Pro subscribers** so far — the machinery is live, the cohort is not.

**The app is instrumented.** Sentry error tracking across client/server/edge (FRESCO-242, `ADR-0009`, free tier) and PostHog product analytics in the EU region for the North-star KPI and retention cohorts (FRESCO-240, `ADR-0013`) are both active. This is genuinely new since the last plan — that version listed no observability at all.

**The notification surface is real.** The last plan's "build minimal-real or retire the slot" question is answered: the bell-icon slot now renders the **Centro de Avisos** — passive in-app notices (EPIC-FRESCO-223, data-map Flow 8): a payment-failed notice, a one-time welcome card, a dismissable routes guide, and up to 3 safety-filtered recipe recommendations, with server-side dismissal flags on `user_profiles`. Separately, a **weekly re-engagement Web Push** ships a Sunday reminder to households with no plan for the current week (FRESCO-241, `ADR-0011` pg_cron/pg_net, `ADR-0012` `web-push` VAPID). The email variant of that re-engagement loop is still blocked on the known Resend owned-domain constraint.

**Other closures since 2026-08-08:**
- `recipes` DELETE path — **done**. `/admin/recipes` + the `delete-catalog-recipe` Edge Function, gated by an `ADMIN_USER_ID` env allowlist (`requireAdminUser()`, no `is_admin` DB column), pre-checking `meal_plan_recipes` references and returning `409` if any exist (FRESCO-237, deployed 2026-08-28).
- `scoreRecipe()` per-user personalization — **done** (`ADR-0008`), the item the prior plan explicitly deferred as "a separate, larger change."
- Guest anonymous-session cleanup — **done**. `cleanup-abandoned-guest-users` is a scheduled `pg_cron` job (`ADR-0011`).
- Generation rate limiting — 5 req/hour/user, atomic Postgres counter (FRESCO-243, `ADR-0010`), with a hardcoded test-account exemption array.
- Motion & transitions polish across every shipped surface (EPIC-FRESCO-244).
- CI hardening — required status checks on `dev` / `staging` / `main`, a blocking end-to-end job (FRESCO-266 / FRESCO-279), with the shared-Supabase-backend race between overlapping CI runs flagged as a known risk (FRESCO-289).

**Unchanged:** Gemini / any external LLM remains fully removed from production (`ADR-0005`) — Fresco makes zero external AI API calls. The deterministic menu selector and shopping-list classifier are still the whole generation engine.

## §3. What To Implement First And Why

### Legal content real sign-off (Master Sprint 0)

**Why it matters:** the app's own UI tells every visitor the Terms/Privacy content is a draft pending legal review. In August the draft was substantively improved — 8 material GDPR gaps were closed (special-category basis for allergy data under Art. 9, applicable-law/jurisdiction clause, explicit legal-entity placeholder rather than a fabricated one, the missing GDPR rights, retention period, a user-content clause for `recetas_propias`, international transfers) — but the banner is deliberately still up because content hardening is not a lawyer's sign-off.

**What it unblocks:** onboarding a real paying cohort. Everything in Master Sprint 2 is gated on this.

**Dependencies:** a legal review. Not an engineering task at all — it is on this list so it does not silently fall off once the technical items are done.

**How an experienced engineer would scope it:**
- Smallest credible slice: get the existing (now much stronger) draft reviewed by someone qualified, apply corrections, remove the banner.
- Likely scope creep: resist rewriting the modal UI while in there — this is a content/compliance task.
- Boundary: once the banner comes down this is done. Do not fold in a real contact-form build (`FEAT-050`'s `mailto:` is deliberately descoped).

### `master-design-plan.md` creation (Master Sprint 0)

**Why it matters:** CLAUDE.md Rule 14 (UI Fidelity Contract) requires every UI story to be built against a per-screen spec in `.context/design/master-design-plan.md` with a US→Screen map. That file has never existed (FRESCO-294). Every UI story shipped so far has fallen back to LIVE-UI-FIRST — building against the current live UI as the fidelity source — which has worked, but leaves the contract's §8 map and the dev-roadmap's §5 mockup-gate registry permanently empty and unenforceable.

**What it unblocks:** any future UI story that genuinely needs a ratified spec rather than "match what's already on screen"; a populated mockup-gate registry in `dev-roadmap.md`.

**Dependencies:** the `/design-system` screen-mapping phase (opt-in). No code.

**How an experienced engineer would scope it:**
- Smallest credible slice: run the screen-mapping phase against the *already-shipped* screens — this is a documentation-of-reality pass first, a forward-looking spec second. Do not try to redesign anything.
- Likely scope creep: this is not a rebrand or a DESIGN.md rewrite. Frozen tokens already exist; this is the per-screen layer on top.
- Boundary: stops at "every shipped screen has an entry and every open UI story maps to one." Retroactively spec'ing screens nobody is about to touch is lower value than covering the open backlog.

### Close the audit-remediation epic FRESCO-278 (Master Sprint 0)

**Why it matters:** the August technical re-audit produced a remediation epic with ~25 children. Most have shipped — CI required checks (FRESCO-279), blocking e2e (FRESCO-266), structured QA Jira fields (FRESCO-281), defect-to-story traceability (FRESCO-282), the full WCAG AA contrast series (FRESCO-283 / 285 / 288 / 293 / 299 / 303), foundation-map sync (FRESCO-284), the Stripe reconciliation job (FRESCO-301), tap-target accessibility (FRESCO-288). **What it unblocks:** audit sign-off; a clean baseline before the next feature push.

**Dependencies:** none code-level. This is tooling, CI config, and documentation work.

**How an experienced engineer would scope it:**

### `recetas_propias` UPDATE/DELETE (Master Sprint 1)

**Why it matters:** this is the last real CRUD gap in the app that is not a deliberate, documented scope cut. `recipe-detail.tsx:133` bundles edit/delete/rate/menu-add/share as "OOS," but delete-your-whole-account is a disproportionate fix path for "I made a typo in my own recipe." Every other user-owned table (`user_profiles`, `favorites`, `meal_plans`) already has UPDATE and DELETE.

**What it unblocks:** self-service parity.

**Dependencies:** none structurally new — `recetas_propias` already has RLS `own` policies for INSERT/SELECT; UPDATE/DELETE follow the same pattern.

**How an experienced engineer would scope it:**
- Smallest credible slice: reuse `CreateRecipeForm`'s validation in an edit mode, plus a delete confirmation. This codebase alternates immediate-delete (`DeleteWeekButton`) and confirm-gated delete (`DeleteAccountDialog`) by reversibility — a personal-recipe delete is closer to the immediate-delete precedent (not account-wide, not irreversible in a scary way), though a lightweight confirm is defensible.
- Likely scope creep: do not reopen rate / menu-add / share — those stay out of scope per the existing documented decision.
- Boundary: personal-recipe table only. Does not touch `recipes` (founder-curated, different trust model, already has its own admin delete path now).

### Recipe photo backfill + quality audit (Master Sprint 1)

**Why it matters:** a food-planning app's first impression on a real cohort benefits from a visually complete catalog. The backfill script (`fetch-recipe-photos.ts`) is mature; the work is running it. The subtlety since the last plan: a quality audit (FRESCO-192) found ~99 photos that did not actually match their recipe and nulled them, so the "with a photo" count went from ~700 down to ~601 and is now climbing again in ~25-per-batch increments (~650/1000 as of late August). 14 recipes are flagged QUESTIONABLE for manual review.

**What it unblocks:** nothing else technically depends on it — parallel, ungated work — but worth finishing before a real cohort sees the catalog.

**Dependencies:** Unsplash free tier (50 req/hr), hence the multi-session batch cadence. Hit rate is falling as the easy name-buckets saturate.

**How an experienced engineer would scope it:**
- Smallest credible slice: keep running the existing batch process; resolve the 14 QUESTIONABLE by hand.
- Likely scope creep: do not build a photo re-review UI. If the fallback-query pool dries up before 1000, accept the icon/placeholder degradation that already exists for photoless recipes rather than lowering the match bar.
- Boundary: this is finishing an in-flight task, not scoping a new one.

## §5. Features / State Machines That Block ≥2 Other Features

- **`user_profiles` is now triple-duty and the single most contended row in the system.** It carries (a) onboarding output, (b) subscription state (`plan`, `plan_expires_at`, `stripe_customer_id`, `stripe_subscription_id`, `payment_failed_at`) written *only* by the Stripe webhook and the reconciliation job, and (c) Centro de Avisos dismissal flags (data-map §`user_profiles`). Every generation call, every SQL pre-filter, account deletion, guest cleanup, the subscription state machine, and the notifications page all key off this one row. Any migration touching it must preserve the `prevent_client_subscription_writes()` trigger, or an authenticated user can self-grant Pro.
- **`recipes` now has five writers, not four.** Generation reads it; `recipe_learning_trigger` writes aggregate columns; the founder's batch-seeding process inserts rows; the photo-backfill script writes `foto_url` via `service_role`; and now the `delete-catalog-recipe` Edge Function hard-deletes rows (`ON DELETE RESTRICT` against `meal_plan_recipes`, so it pre-checks and 409s). None of the five is aware of the others by construction — any schema change has to be checked against all five.
- **`auth.users` / anonymous-session identity** still blocks or touches guest logout confirmation, guest→account conversion, guest-data reassignment on email conflict, account deletion, and the now-shipped `cleanup-abandoned-guest-users` cron. A change to how anonymous identity is represented ripples through all five with no single owning epic.
- **`meal_plan_recipes.estado`** remains the most load-bearing state machine — the calendar, the learning loop (`ADR-0006`), and the now-shipped per-user `scoreRecipe()` nudge (`ADR-0008`) all derive from it.

## §6. Hidden Dependencies

**The Stripe webhook and the reconciliation job are two writers to the same columns and must not fight.** `ADR-0007` makes the webhook the sole writer of subscription state; `ADR-0015` adds a daily cron that also writes those columns when it detects drift between `user_profiles` and Stripe. The invariant that keeps this safe is that the job only *reconciles toward Stripe* (Stripe is source of truth) and runs idempotently — any future change to either path has to preserve that, or the two writers can oscillate. Both are guarded by the same `service_role`-only trigger, which is the coordination point.

**Centro de Avisos reads Flow 7's output — it is a cross-domain consumer, not a standalone Profile-domain feature.** The payment-failed notice on `/notifications` reads `user_profiles.payment_failed_at`, which only the Stripe webhook sets (data-map Flow 8 explicitly depends on Flow 7). Its recipe-recommendation card reads `get_filtered_recipes()` — the food-safety RPC (EPIC-FRESCO-8). So the notifications surface silently couples the Subscription domain and the Food-Safety domain; a change to either can break a notice without touching the notifications code.

**The Motion epic decorates every shipped surface, and reduced-motion is cross-cutting.** EPIC-FRESCO-244's stories layer transitions onto the sidebar, calendar, library, Centro de Avisos and the Pro upsell. FRESCO-249 (respect `prefers-reduced-motion`) is not a screen — it is a system-wide invariant every animated component has to honor. Any new animated component added later has to re-satisfy it or it regresses silently; the pre-ship checklist below now names this.

**`recetas_propias` UPDATE/DELETE shares the delete-confirmation-pattern question with the rest of the app.** This codebase has two established delete UX patterns (immediate vs. type-to-confirm); picking the wrong one for personal recipes creates an inconsistency users feel. Cheapest coordination: follow the reversibility heuristic already implicit in `DeleteWeekButton` vs `DeleteAccountDialog`.

## §9. Edge Implementation Cases

- **`recetas_propias` UPDATE/DELETE — the confirmation-pattern choice is the real decision, not the RLS.** The policy is a copy of the existing `own` pattern. What needs an explicit call is whether a personal-recipe delete is immediate (`DeleteWeekButton` precedent) or type-to-confirm (`DeleteAccountDialog` precedent). Cheapest way to defer: ship UPDATE first (no destructive-confirmation question), add DELETE in a follow-up.
- **`master-design-plan.md` — retrofit-everything vs. cover-the-open-backlog.** Spec'ing all ~15 shipped screens is a large pass; spec'ing only the screens with open UI stories is a small one that still satisfies Rule 14 for anything actually about to be built. Cheapest way to lock it down: do the open-backlog subset now, backfill shipped screens opportunistically when a story touches them.
- **PRD/SRS Gemini de-scope — a doc-only change to the "source of truth."** No code moves, but these are the documents `/project-foundation` and downstream planning treat as authoritative. The risk is doing a shallow find-replace that leaves dangling references to Gemini-era constraints (latency budgets, API-key handling, prompt-injection threat model) that no longer apply. Cheapest way to lock it down: treat it as a real editing pass keyed to `ADR-0005`, not a keyword sweep.
- **CI shared-backend race (FRESCO-289) — accept-and-serialize vs. isolate.** Two overlapping CI runs mutate the same Supabase project. Cheapest deferral: serialize the e2e job (concurrency group) so runs never overlap. Cheapest real fix: an ephemeral branch database per run — larger, and only worth it if CI volume grows.
- **Free/Pro is still a business-logic branch, not an auth tier** (restated, still true) — any new Pro-gated surface (a future Pro-only notice, say) must reuse the same server-side `isPro` / `plan` check every other Pro surface uses, not introduce a new permission concept. The webhook + `prevent_client_subscription_writes()` trigger are the only things that make `plan` trustworthy.

## §10. Pre-Ship Checklist

- Verify every new migration in `supabase/migrations/` is actually applied against the shared Supabase project (`list_migrations` via Supabase MCP) — the repo can hold `.sql` files that never ran.
- Verify every new or changed Edge Function is deployed and `ACTIVE` (`list_edge_functions` via Supabase MCP).
- Verify any new table with RLS has **both** the RLS policies **and** the table-level `GRANT` to `authenticated` (and `anon` if guest-reachable) — this exact gotcha is a documented live-testing finding.
