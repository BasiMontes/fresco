## §1. Executive Summary

Fresco is pre-implementation: one table (`recipes`) is live, everything else — four tables, three Edge Functions, one trigger, the entire frontend — is a confirmed design waiting to be built. That gives this plan an unusually clean starting condition: there is no legacy code to route around, no partial migration to reconcile, and no feature to reverse-engineer priority for. The only real asset already in production is the recipe catalog itself, seeded through the founder's manual batch-generation-plus-review process (`business-data-map.md` Flow 4) — a process that keeps running in parallel with every Master Sprint below, independent of application code.

The founder's own priority ordering of the 8 PRD epics (`mvp-scope.md`) is treated here as a strong prior, not a starting point to re-derive from scratch. This plan does not reorder any epic relative to that list. What it adds is dependency and readiness information the PRD's flat list doesn't carry: which epics share infrastructure, which are gated by an unresolved product decision, and which can only produce user-visible value after real usage time has passed regardless of when the code ships. Those three factors are what separate the founder's epic-priority order from this plan's Master-Sprint grouping — the epics stay in the founder's order, they are simply clustered into three delivery waves along the seams where a genuine infrastructure or product-decision boundary already exists.

## §2. Value & Priority Map

The founder's stated priority order is EPIC-1 → EPIC-2 → EPIC-3 → EPIC-4 → EPIC-5 → EPIC-6 → EPIC-7, plus EPIC-8 as a cross-cutting P0 that rides inside EPIC-2 rather than standing alone in the sequence (`mvp-scope.md`: "This epic is explicitly excluded from the Out-of-Scope Blacklist... it does not wait for product code to exist"). Three natural clusters fall out of that order without reshuffling it:

- **The single core promise (EPIC-1, EPIC-2, EPIC-8).** Onboarding exists only to feed generation; generation is worthless without the two-layer allergen/hated-ingredient guardrail built inside its own Edge Function (`business-data-map.md` Flow 1, step 5 and step 7; `architecture.md` §5). These three are not independently shippable — a working EPIC-2 without EPIC-1 has no profile to read, and a working EPIC-2 without EPIC-8 is a menu-generation feature the founder has explicitly said cannot ship. The MVP success metric itself — 3 of 10 concierge users paying and repeating for 3+ weeks (`executive-summary.md` — Success Metrics) — cannot be measured until this cluster works end to end.
- **Completing the weekly loop (EPIC-3, EPIC-4, EPIC-5).** Once a menu exists, three things extend it: making it editable, turning it into a shopping list, and starting to capture the signal the Pro tier is sold on. All three read from `meal_plan_recipes`, the table the first cluster creates as a side effect of persisting a generated plan (`architecture.md` §3.1 step 9) — none of them can start before that table exists, and none of them blocks the first cluster from shipping. EPIC-5 sits in this Master Sprint for a second, distinct reason argued in §3 below: even a day-one-perfect implementation of the learning loop cannot demonstrate improvement until a household has at least two weeks of cooked/discarded history — the value is time-gated by definition, not by implementation effort (FR-5.4, "last-2-weeks" window).
- **Funnel expansion (EPIC-6, EPIC-7).** Guest mode and progressive signup exist to widen the top of the funnel once the core loop is provably worth funneling people into. Both are also the only two epics blocked by a genuinely unresolved product decision rather than an engineering task — see §3 and §12.

Recipe-catalog-adjacent work (the founder's own batch-seeding process) sits outside this three-cluster structure entirely: it already has a head start no other piece of infrastructure has, and it runs on its own cadence in parallel with all three Master Sprints, not gated by or gating any of them beyond the ~230-recipe target needed for catalog depth (`architecture.md` §4; NFR-SCALE-2, per `business-data-map.md`).

## §3. What To Implement First And Why

**Master Sprint 0 is EPIC-1 + EPIC-2 + EPIC-8, and nothing else, because none of the three is separately useful.** A profile with nowhere to feed it, a generator with no safety guarantee, and a safety guarantee with no generator to protect are each a dead end on their own. The founder's own framing makes EPIC-2 the product's central promise and EPIC-8 a same-day-ship non-negotiable (`mvp-scope.md`), which together mean Master Sprint 0's exit criterion is a single, testable outcome: a user completes 3-step onboarding and receives a 21-meal weekly menu, in under 30 seconds, that structurally cannot contain a declared allergen or hated ingredient.

Two pieces of supporting infrastructure belong inside Master Sprint 0, not as separate epics but as prerequisites the cluster cannot function without:

- The four not-yet-created tables (`user_profiles`, `meal_plans`, `meal_plan_recipes`, `shopping_lists`) must exist before generation can persist anything — this is where the column-shape decision (typed relational vs. JSONB, flagged unresolved in `architecture.md` §4) has to be made and executed, since it blocks literally every write EPIC-2 performs.
- Gemini Flash should be wired and smoke-tested in isolation — against the ~35 recipes already seeded — before the onboarding-to-generation UI chain is built on top of it. Testing the external dependency before building the feature that calls it catches integration failures (auth, JSON-mode behavior, latency against the 30-second budget) while the blast radius is a standalone script, not a half-built user-facing flow. Full reasoning in §7.

**Master Sprint 1 is EPIC-3 + EPIC-4 + EPIC-5**, in that order of internal priority, because all three extend a loop that Master Sprint 0 already made real, and none of them can start earlier. EPIC-3 (editable calendar) and EPIC-4 (shopping list) are pure extensions with no external blocker beyond `meal_plan_recipes` existing. EPIC-5 (the learning toggle) is the one epic in this Master Sprint that needs its own justification for not being in Master Sprint 0 despite being P0 in the founder's list: the toggle itself (`FEAT-013`, recording cooked/discarded state) is cheap and could technically ship earlier, but the feature it feeds — history-informed generation and the Pro-only explanation card (`FEAT-004`, `FEAT-015`, `FEAT-016`) — reads a **last-2-weeks** window (FR-5.4) that literally cannot contain data until two weeks after a user's first generation. Shipping EPIC-5 inside Master Sprint 0 would not make the Pro moat demonstrable any sooner; it would only add scope to the sprint whose sole job is proving the core promise works at all.

**Master Sprint 2 is EPIC-6 + EPIC-7**, held back not because they're low-value but because EPIC-6 (guest mode) has no resolved technical path — every documented Edge Function hard-requires a Supabase Auth JWT, and no source document says how a guest without one is meant to call `generate-meal-plan` (`business-api-map.md` §2, top Discovery Gap). Building EPIC-7 (progressive signup) before that's resolved is not possible, since EPIC-7 is literally "what happens after the guest sees value" — there's no guest flow yet to attach a signup prompt to. This Master Sprint's real first task is not code, it's a product/technical decision: resolve the guest-auth mechanism, then implement both epics against it.

## §4. Master Sprint Structure

**Master Sprint 0 — Prove the core promise, safely.**
Scope: EPIC-FRESCO-1 (Onboarding), EPIC-FRESCO-2 (AI Weekly Menu Generation), EPIC-FRESCO-8 (Food-Safety Guardrail, built inside EPIC-2's Edge Function, not as a separate deliverable). Supporting infrastructure: the four not-yet-created tables (column-shape decision resolved and executed), the `generate-meal-plan` Edge Function, `get_filtered_recipes()`, an isolated Gemini Flash integration test preceding the full UI chain. Exit criterion: a user completes onboarding and receives a safety-guaranteed 21-meal menu in under 30 seconds. This is also the earliest point at which the MVP's own success metric (3 of 10 concierge users paying and repeating 3+ weeks) becomes measurable at all.

**Master Sprint 1 — Complete the weekly loop.**
Scope: EPIC-FRESCO-3 (Editable Calendar), EPIC-FRESCO-4 (Shopping List), EPIC-FRESCO-5 (Cooked/Discarded Learning Toggle, recording + Pro-tier application). Supporting infrastructure: `update-recipe-status` and `generate-shopping-list` Edge Functions, the `recipe_learning_trigger`, the `aprendizaje` columns migration on `recipes` (a prerequisite for EPIC-5, detailed as a spike in §12). Exit criterion: a generated menu can be rearranged, converted into an aisle-grouped shopping list, and marked cooked/discarded — with Pro users seeing a visible, correctly-timed explanation once real history exists.

**Master Sprint 2 — Expand the funnel.**
Scope: EPIC-FRESCO-6 (Guest Mode), EPIC-FRESCO-7 (Progressive Signup). Prerequisite, not infrastructure: a resolved guest-auth mechanism (see §9, §12) — this Master Sprint cannot be scoped into stories until that decision is made. Exit criterion: a first-time visitor generates one menu with zero signup, and is prompted to keep their account only after seeing that menu.

**Parallel, ungated track — Recipe Catalog Depth.**
The founder's batch-generation-plus-manual-review process (`FEAT-024`) continues independently of all three Master Sprints, growing the catalog from ~35 toward the ~230-recipe target. It shares no Edge Function, no Master Sprint gate, and no code dependency with the three waves above — its only coupling to them is the shared `recipes` table, discussed as a coordination risk in §6.

## §5. Features / State Machines That Block Others

- **`meal_plan_recipes.estado`** (`pendiente → cocinada | descartada | sustituida`) is the single most load-bearing piece of state in the system. It is written by Master Sprint 0's generation flow (initial `pendiente` rows), read and transitioned by Master Sprint 1's calendar (EPIC-3, via `sustituida`) and learning toggle (EPIC-5, via `cocinada`/`descartada`), and is the direct input to `recipe_learning_trigger`. Any story that touches this state machine without reading `business-data-map.md` §4 first risks breaking either the terminal-state guarantee (no double-counting) or the neutrality guarantee (`sustituida` must never affect statistics).
- **`user_profiles`** blocks every generation call (EPIC-2), the entire safety guardrail (EPIC-8, both layers key off `alergenos`/`ingredientes_odiados`), and is the unresolved anchor for guest mode (EPIC-6) — a guest, by definition, doesn't have an `auth.users` row to key this table on, which is part of why EPIC-6 is gated on a product decision, not just an engineering task.
- **The `recipes` table** blocks generation (EPIC-2 reads it), the learning trigger (EPIC-5 writes aggregate columns to it), and the founder's own batch-seeding process (writes new rows to it). Three independent write/read paths converging on one table is a coordination-cost pattern in its own right — expanded in §6.
- **The two-layer allergen/hated-ingredient filter** (SQL pre-filter + Gemini system-prompt rule) is not a standalone feature to schedule — it is built inside `generate-meal-plan` and blocks EPIC-2 from being shippable at all, per the founder's explicit "ships day one, not staged" stance on EPIC-8.
- **The guest-mode auth mechanism** (unresolved) blocks EPIC-6 outright and, transitively, EPIC-7, since EPIC-7 has no guest flow to attach a signup prompt to without EPIC-6 existing first.

## §6. Hidden Dependencies

**Three owners, one table.** `recipes` is written by three structurally different actors that will never be coordinated by a single code review: (1) `generate-meal-plan` (EPIC-2) *reads* it on every generation call; (2) `recipe_learning_trigger` (EPIC-5) *writes* aggregate columns to it automatically, triggered by user action, with no API surface of its own; (3) the founder's own batch-seeding process *writes* new rows to it directly via `service_role`, entirely outside application code (`business-data-map.md` Flow 4). A schema change to `recipes` made for one of these three purposes — say, adding a column to support better generation filtering — has to be checked against the other two before it ships, because none of the three owners is aware of the others by construction. This is exactly the kind of coordination cost that doesn't show up in any single epic's scope but will bite whichever Master Sprint 1 story first touches the `recipes` schema for the `aprendizaje` migration.

**One filtering rule, two independently-maintained enforcement points.** The allergen and hated-ingredient exclusion logic is conceptually a single rule — "never serve a recipe that conflicts with `user_profiles.alergenos` or `.ingredientes_odiados`" — but it is implemented twice: once as a SQL pre-filter (`get_filtered_recipes()`, EPIC-2) and once as Gemini system-prompt instructions (EPIC-8's model-level layer). Both read from the same two `user_profiles` columns, and both must be updated together any time the allergen/hated-ingredient data model changes — e.g. adding a new declared-restriction type. `ADR-0001` and `architecture.md` §5 already name this as an architectural invariant ("touch both layers or neither"); the risk this section flags is specifically the *maintenance* cost of two independently-written rule implementations drifting apart over time, not the initial build.

**The `meal_plan_recipes` table is shared load-bearing infrastructure for three separate epics that don't otherwise interact.** EPIC-2 creates its 21 rows per plan; EPIC-3 reorders/substitutes them; EPIC-5 transitions their `estado`. None of these three epics needs to know about the others' code, but all three need to agree on the same table shape, the same `unique_slot` constraint, and the same terminal-state semantics — a schema decision made while scoping EPIC-2 in Master Sprint 0 will constrain what EPIC-3 and EPIC-5 can do in Master Sprint 1 without a second migration.

## §7. External Integrations Roadmap

Gemini Flash is the only third-party service anywhere in Fresco (`business-feature-map.md` §6) — there is no payment provider integration in this MVP's scope (Stripe/payment-links appear only in the Constitution as the founder's own manual concierge-validation-phase tooling, never as an in-app EPIC; `mvp-scope.md` does not list a payments epic, and none should be invented here).

Recommended sequencing: wire and smoke-test Gemini Flash in isolation — a standalone call against the ~35 already-seeded recipes, exercising both the menu-selection prompt (`temperature: 0.7`) and the aisle-classification prompt (`temperature: 0.2`) — **before** building the onboarding-to-generation UI chain that depends on it. This is the practical application of "integrate a service one Master Sprint before the feature that needs it": because Gemini is needed by Master Sprint 0's own centerpiece feature, there is no earlier sprint to place the integration test in, so it becomes the literal first task inside Master Sprint 0, ahead of any UI work. Validating the integration in isolation first — confirming JSON-mode output shape, retry behavior on malformed output, and real-world latency against the 30-second budget — means a failure surfaces against a throwaway test script, not a half-built onboarding flow with a broken generation step at the end of it.

No further integration work is needed for Master Sprint 1 (the shopping-list classification call reuses the same wired connection) or Master Sprint 2 (guest mode and progressive signup call no new external service — the blocker there is internal, an auth-mechanism decision, not a third-party integration).

## §9. Edge Implementation Cases

- **The column-shape decision for the four not-yet-created tables is a pending architectural decision, not a solved detail.** The live `recipes` table uses a JSONB-flexible shape; the founder's fuller design doc specifies a strongly-typed relational shape for `user_profiles`, `meal_plans`, `meal_plan_recipes`, and `shopping_lists` (`architecture.md` §4). Master Sprint 0 cannot scaffold generation persistence without resolving this first — treat it as a pre-Master-Sprint-0 spike, not something to decide implicitly while writing the first migration.
- **Guest-mode auth is a scope-ambiguous feature, not a normal engineering unknown.** Every documented Edge Function hard-requires a Bearer JWT; EPIC-6 requires a caller with none. No source document — PRD, SRS, or founder brief — picks between an anonymous Supabase session, a client-side-only generation path that bypasses the Edge Function entirely, or a guest-scoped token (`business-api-map.md` §2). This has to be resolved as a product/technical decision before Master Sprint 2 can be scoped into stories at all — it is not something an implementer should resolve unilaterally mid-sprint.
- **The two-layer safety filter's failure mode is intentionally a hard stop, not a soft degrade.** If fewer than 21 recipes survive the SQL pre-filter for a given profile, `generate-meal-plan` returns `422` rather than proceeding with a partially-filtered catalog (`business-data-map.md` Flow 1, step 5). Implementers should not "fix" this into a best-effort fallback — the fail-closed behavior is the safety guarantee, and any change to it is a food-safety-relevant decision, not a UX polish.
- **Free/Pro is a business-logic branch, not an auth tier.** Both are the same `Authenticated` principal; the only difference is a server-side `isPro` check inside `generate-meal-plan`'s prompt-building step (`business-api-map.md` §2). Implementers scoping EPIC-5 should not model this as a permission system — there is no separate scope, claim, or endpoint to build.

## §10. Pre-Ship Checklist

- Onboarding cannot be completed in more than 3 steps (hard cap, `mvp-scope.md` US 1.2) — verify this before any UI polish pass.
- Every generated menu must pass through both layers of the allergen/hated-ingredient filter with no code path that can bypass either layer (`ADR-0001`, `architecture.md` §5) — this is the one invariant in the system too consequential to regress silently.
- A non-empty `advertencias` entry reporting an unmet mandatory filter must render as a prominent, blocking-style warning, never a silently logged event (FR-8.2) — verify this renders correctly before any concierge-stage menu delivery.
- The founder's manual food-safety checklist continues to run before every concierge-stage menu delivery regardless of code-level enforcement status — code shipping does not retire this manual backstop (FR-8.3).
- No Free-tier code path may pass cooked/discarded history into a generation prompt — this is the entire technical basis for the Pro tier's pricing and must be verified explicitly, not assumed correct because the `isPro` branch exists (`ADR-0001` — "the invariant every feature must uphold").
- The Pro-tier explanation card (`card-insight`) must never fire on a Pro user's first week (no history exists yet) and must use warm, specific, non-robotic copy — a weak or missing card directly undermines the product's entire monetization thesis (FR-5.5, `ADR-0001` named risk).
- `GEMINI_API_KEY` must never be reachable from client code — verify this explicitly before any deploy, not just at initial wiring (NFR-SEC-3).
- Before the first concierge cohort goes live, confirm the recipe catalog has enough depth and category variety for the declared allergen/diet/budget combinations in that cohort — the `422` fail-closed path exists precisely because catalog-too-small-for-profile is a real, not hypothetical, failure mode at ~35 seeded recipes.

## §11. What Is NOT In Scope

The following are explicitly excluded from this MVP's roadmap, per `mvp-scope.md`'s Out-of-Scope Blacklist, and remain excluded until both **MRR > €5,000** and **30-day retention > 50%** are met: receipt scanning, price comparison, pantry/inventory management, aggressive push notifications, voice operations, Wake Lock API / background device APIs, complex local-first architecture, JSON/CSV export, price learning, leftover-ingredient AI, batch-cooking mode, expiration alerts, supermarket integrations, complex glassmorphism UI, gamification, community/social features, recipe marketplace, a native app before 1,000 paying users, and B2B before B2C is validated. No in-app payments/subscription-billing epic exists in this MVP's scope either — Stripe/payment-link handling belongs solely to the founder's manual concierge-validation-phase process, not to any of the three Master Sprints above.

### Deferred to P1

**Curated recipe library (50–100 recipes with photography).** Cut for cost reasons, not product-priority reasons — a solo, part-time founder with no budget cannot afford professional curation/photography at MVP scale. The founder's batch-generation-plus-manual-review process (§4's parallel track) is the deliberate substitute for the life of this MVP; promoting the curated library out of P1 is a scope decision for a later planning pass, not something this plan schedules into any Master Sprint.

## §12. Implementation Gaps

- **Guest-mode authentication mechanism — unresolved, blocking Master Sprint 2.** No source document specifies how an unauthenticated guest is meant to call an Edge Function that hard-requires a Bearer JWT. This blocks EPIC-6 and, transitively, EPIC-7 from being scoped into stories at all. Flagged as the top gap in both `business-data-map.md` and `business-api-map.md`; carried forward here as a Master-Sprint-2 blocker, not a Master-Sprint-0 one, since neither epic is scheduled before the first two waves ship.
- **`aprendizaje` columns migration — a required spike inside Master Sprint 1, not yet written.** `veces_cocinada`, `veces_descartada`, `rating_promedio`, and `ultima_vez_en_menu` are absent from the live `recipes` table. `ADR-0001` — the highest-leverage, hardest-to-reverse decision in this system — is `Status: Proposed` specifically because this migration hasn't run yet. This does not block Master Sprint 0 (generation works without it; the Free/Pro fork is structural, not schema-dependent, for the "never call history" side of the branch), but it is a hard prerequisite for any of EPIC-5's Master Sprint 1 work and should be scheduled as the first task of that sprint, not discovered mid-sprint.
- **Recipes column-shape decision — a pending architectural decision blocking Master Sprint 0's own start.** Typed relational vs. JSONB for the four not-yet-created tables is unresolved (`architecture.md` §4). Unlike the two gaps above, this one sits directly in Master Sprint 0's critical path: generation cannot persist anything until the four tables exist in some shape.
- **No numeric capacity or latency target exists beyond the qualitative "under 30 seconds" generation promise.** There is no defined concurrent-user capacity target, no percentile breakdown of the 30-second budget (p50 vs. p99), and no numeric latency target at all for shopping-list generation specifically (`business-data-map.md` §7; `non-functional-requirements.md` NFR-PERF-2, per `architecture.md`). This is acceptable at concierge-cohort scale (8–10 users) but should be named explicitly before any post-MVP scale-up planning, since none of the three Master Sprints above currently carries a load-testing task.
- **No `production` environment is defined in `.agents/project.yaml`.** Only `local` and `staging` exist, both pointing at the same Supabase project reference (`architecture.md` §6). This does not block any of the three Master Sprints' development work, but it does mean none of them currently has a real production deployment target to ship to — worth resolving before Master Sprint 0's exit criterion is demonstrated to anyone outside the founder.
